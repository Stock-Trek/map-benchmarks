## 3. Cross-operation patterns

### 3.1 Who is fastest most often?

Two implementations dominate, in different arenas: **txmap** (fastest in 35 of 48 concurrent configurations) and **rustc-hash** (fastest in 26 of the 37 serial default-hasher configurations). `txmap` (like the other concurrent maps) also runs in the serial benchmarks — it is measured in all 112 configurations — but all 35 of its wins are in concurrent ones, and it is the fastest in none of the serial same-hasher or default-hasher runs. `rustc-hash` does not participate in same-hasher or concurrent benchmarks, so the raw all-configuration counts are arena-dependent. Split by arena: serial default-hasher (37 configs) → rustc-hash 26, indexmap 4, intmap 3, rpds 3, immutable-chunkmap 1; serial same-hasher (27 configs) → indexmap 8, std 7, ahash 5, hashbrown 5, horde 2; concurrent default-hasher (48 configs) → txmap 35, leapfrog 9, scc 2, dashmap 1, papaya 1.

### 3.2 Recommendations by use case

| Use case | Recommended implementation(s) |
|---|---|
| Single-threaded, default settings ("just fast") | `rustc-hash` (cheap FxHash), or `ahash`/`hashbrown`/`std` if you want a hardened hasher |
| Single-threaded with your own hasher / fair comparison | `std`, `ahash`, `hashbrown` (all within ~3% on u64 and ~3–10% on String for most ops) |
| Insertion-ordered semantics + fast iteration + String-key bulk build | `indexmap` |
| Iteration performance above all | `indexmap` (3.4–4.2× faster than the field) |
| `u64`-only keyed hot paths (lookup/remove) | `intmap` |
| Cheap clones / fork-like snapshots | `rpds`, `immutable-chunkmap`, `imbl` (O(1) clone); `starshard` if you also need a shared-mutable API |
| Map pooling (clear and refill) | `rustc-hash` (default hasher) or `std`/`ahash`/`hashbrown` (same hasher) |
| Concurrent read-heavy / balanced / general mixed | `txmap` |
| Concurrent `u64`-keyed hot / skewed write loads | `leapfrog` (esp. Zipfian-heavy) |
| Concurrent String write-heavy | `scc` (3 threads) / `txmap` |
| Extreme single-key contention | `txmap`/`leapfrog` (reads/writes respectively); `dashmap`/`scc` for String write-only |

### 3.3 Trade-offs and consistent performers

* **Different implementations excel in different operations — the largest trade-off is persistent vs mutable.** `rpds`/`imbl`/`immutable-chunkmap` win clone/create but are typically 3–29× slower on write ops (insert/growth/remove) and up to ~34× slower on single-threaded mixed throughput; `imbl` is only ~1.5× behind on the String balanced workload. `indexmap` wins iteration and String insertion-order growth but is mid-pack on lookup and slow to clone (deep copy). `intmap` is unbeatable for u64 point ops but unavailable for String keys and slower at bulk inserts/growth. `leapfrog` (Copy keys only) and `txmap` split the concurrent crown by key type and skew.
* **std / ahash / hashbrown are the consistent "all-rounders":** once the hasher is the same, they are within ~3% of each other on almost every serial operation (lookup hit/miss, insert, growth u64, get-or-insert, key-sensitivity) and are never far behind the winner. `horde` is consistently close to the fastest in several same-hasher serial ops (growth u64 ~1.07–1.10×, remove) despite never winning those categories outright.
* **The concurrent maps form a clear pecking order:** `txmap` ≳ `leapfrog` (u64) / `scc` (String writes) > `dashmap` > `papaya` > `starshard` ≫ `crossbeam-skiplist`, `concurrent-map`. The two ordered concurrent maps are never within 10% of the fastest: `crossbeam-skiplist` trails by ~3–15× in concurrent workloads (and ~76× when iterating) and `concurrent-map` by up to ~39× — confirming that ordered/log-structured concurrency is a poor fit for these map workloads.

## 4. Stability

Criterion's `median_abs_dev` (MAD) is the robust scatter measure; relative MAD = MAD ÷ median. Across all 1,403 measurements the median relative MAD is **0.6%**, the 90th percentile **2.2%** and the 99th **7.4%** — i.e. the large majority of measurements are tight. Concurrent benchmarks (thread scheduling) and very fast sub-µs benchmarks are noisier than serial bulk ones.

### High-variance measurements (relative MAD ≥ 10%)

Only 9 of 1,403 measurements exceed 10% relative MAD, and **none of them belongs to the fastest implementation in its benchmark** — the leaders are consistently stable:

| Benchmark | Implementation | Median | rel. MAD |
|---|---|---|---|
| growth size=100K · out-of-the-box u64 | `imbl` | 9.26 ms | 22.5% |
| clone-then-write size=1K | `dashmap` | 7.3 µs | 18.0% |
| clone-then-write size=1K | `concurrent-map` | 47.2 µs | 17.9% |
| clone-then-write size=10K | `rpds-hash-trie-map` | 342.8 µs | 17.6% |
| iterate size=100K · same-hasher | `rpds-hash-trie-map` | 1.54 ms | 17.4% |
| remove · same-hasher u64 | `imbl` | 4.74 µs | 15.4% |
| synchronization · 3 threads String read-only | `crossbeam-skiplist` | 1.96 ms | 15.4% |
| clone-then-write size=1K | `rpds-hash-trie-map` | 17.8 µs | 14.0% |
| iterate size=100K · out-of-the-box | `rpds-hash-trie-map` | 1.66 ms | 12.6% |

### Patterns

* **`rpds-hash-trie-map` is the noisiest implementation overall** (median rel. MAD 0.97%, four measurements > 12%), all in iterate / clone-then-write — consistent with allocation/reclamation churn in its persistent trie. It never leads those benchmarks, so rankings are unaffected.
* **`imbl` (median 0.78%, two > 15%)** is similarly noisy on persistent-data-structure work.
* **`dashmap` and `concurrent-map`** show 15–18% scatter in tiny clone-then-write runs — sub-µs-to-µs measurements amplified by allocator noise.
* **Fastest implementations with noticeable (but still moderate) noise:** `txmap`'s worst relative MAD is 7.4% (sync write-mostly u64 3 threads) and `scc`'s 8.7% (String write-heavy 3 threads); both remain clearly separated from the pack, so conclusions hold.
* Per-implementation median relative MAD is lowest for `leapfrog` (0.33%), `immutable-chunkmap` (0.43%), `horde` (0.47%), `std` (0.50%) and highest for `starshard` (0.97%), `rpds` (0.97%), `dashmap` (0.86%), `txmap` (0.78%).
* Ratios within ~2% between leaders (e.g. `std` vs `ahash` at 1.00×) should be read as *statistically indistinguishable*, not as a real ordering.

## 5. Implementation limitations (from `src/maps/` wrappers)

Unless noted, values are `u64` in every benchmark; several wrappers additionally demand `V: Clone` simply because the harness clones values out of the map (`BenchMapGetCloned`).

* **`std`** — requires `K: Hash + Eq` for all ops, `V: Clone` for reads/get-or-insert. Configurable hasher (default `RandomState`/SipHash). No `Send`/`Sync` bounds needed for serial use; `clear` implemented. Baseline reference implementation.
* **`ahash`** — identical trait surface to `std`; default hasher `ahash::RandomState`. All operations including `clear` supported.
* **`hashbrown`** — same trait surface; default hasher ahash-based `DefaultHashBuilder`.
* **`hashlink`** — `LinkedHashMap` (insertion-ordered); same bounds as above plus `K: Hash + Eq`. Iteration is insertion-order (the wrapper's `for_each` has no extra bounds).
* **`indexmap`** — insertion-ordered; **`remove` uses `swap_remove`**, i.e. removal is O(1) but *does not preserve order* of the remaining elements (order-preserving removal would be O(n)). Clone is a deep copy.
* **`btreemap`** — `K: Ord`; **no hasher** (never appears in same-hasher benchmarks); `V: Clone` bounds. O(log n) operations and ordered iteration.
* **`intmap`** — keys must be `intmap::IntKey` (integer types only): **no String keys**, no hasher. Lookups/removes take `*key` by value internally.
* **`leapfrog`** — requires **`K: Copy + Hash + Eq` and `V: leapfrog::Value` (Copy-ish)**; hence u64 keys only. No `Clone` for the map and **no `clear`** (absent from clone and clear-and-reuse). `get_or_insert` is expressed via `try_insert` (returns existing on conflict). Provides `&self` mutation (used in concurrent benches).
* **`rustc-hash`** — `FxHashMap` with a **fixed FxHasher; no configurable hasher**. No `Send/Sync` requirement in wrapper. All ops incl. `clear`.
* **`imbl`** — persistent hash map; mutation requires **`&mut`** and `K: Hash + Eq + Clone`, `V: Clone`. Supports `clear` and custom hashers. Clones share structure (O(1)).
* **`immutable-chunkmap`** — persistent, **`K: Clone + Ord`** (no hasher); COW mutations (`insert_cow`/`remove_cow`/`get_or_insert_cow`) via `&mut`. **No `clear`** (absent from clear-and-reuse).
* **`rpds-hash-trie-map`** — persistent HAMT (`RcK` pointers); mutations (`insert_mut`, `remove_mut`) via `&mut`; get returns cloned values. **No `clear`, no get-or-insert API** (absent from those benchmarks). Custom hasher supported. Clone is an O(1) Rc bump.
* **`horde`** — `SyncTable`: **reads require a hazard-pointer pin**; **writes go through the writer lock and the wrapper only exposes them via `&mut self`**, so horde is excluded from all shared-`&self` concurrent benchmarks. No get-or-insert API. `clear` implemented by replacing the table with an empty one.
* **`dashmap`** — sharded concurrent map; `&self` insert/remove/get-or-insert; custom hasher; `clear` and deep-copy `Clone` supported. Requires `K: Hash + Eq`, `V: Clone` where values are read out.
* **`papaya`** — lock-free; **all ops go through `pin()` guards** (the wrapper hides this, but callers must be prepared for guard/pin semantics and the crate's reclamation model). `&self` ops, custom hasher, `clear`.
* **`scc`** — the wrapper uses the crate's `*_sync` variants (`read_sync`, `upsert_sync`, `entry_sync`, `iter_sync`, `clear_sync`) — deterministic single-call synchronous operations rather than the async/await API. `&self` ops; custom hasher.
* **`starshard`** — wrapper hard-codes **8 shards** (`with_shards_and_hasher(8, …)`); requires **`K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`**, and a `Clone + Send + Sync` hasher (default FxBuildHasher) — the strictest bounds of any wrapper. `Clone` is copy-on-write (O(1)).
* **`txmap`** — transactional map built with `TxMapBuilder`, `MutexPolicy` (one `parking_lot::Mutex` per shard) and **rapidhash** default. `get_or_insert` implemented via `get_with_or_insert(&key, |v| v.clone(), default)`. `&self` ops; custom hasher; `clear`.
* **`crossbeam-skiplist`** — `K: Ord` ordered lock-free skiplist; **no hasher**, **no `Clone`** (absent from clone/clone-then-write). `&self` ops incl. atomic `get_or_insert`.
* **`concurrent-map`** — the most unusual wrapper. The crate's `ConcurrentMap` is **`Send` but not `Sync`** (EBR state lives in a `RefCell`), so the wrapper keeps a master map behind a `Mutex` and **lazily clones it into a thread-local** (`thread_local!` + type-erased box) on first use per wrapper instance; shared-`&self` ops route through that private clone. Consequence: in per-iteration benchmarks that publish a fresh map, **one full O(n) clone of the master occurs inside the timed region** on each iteration, and concurrent mutations act on *per-thread private clones*, not on one shared map (§6). Ordered key requirement (`Minimum` = `Ord`); no hasher; no `clear`; no get-or-insert.
* **Excluded from the run entirely:** `concread` (`K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync`; the **extra `Debug` bound** and COW write/commit flow) and `flurry` (epoch-based; wrapper requires `K: Sync + Send + Clone + Hash + Ord` even for inserts and a `pin()` for every op). Bench sources exclude them as "too slow"; `create.rs` notes flurry "creates a seize::Collector per map".

## 6. Recommendations and follow-up

### Implementations / benchmarks worth investigating further

* **`txmap`'s concurrent dominance.** It wins read-heavy, balanced *and* write-heavy concurrent workloads even though its `MutexPolicy` serialises every shard access. Its rapidhash default gives it a hashing advantage over SipHash-default `dashmap`/`papaya`/`scc` (see measurement caveat below), but a 1.1–1.9× edge over `scc`/`leapfrog` on write-heavy u64 is large enough to merit profiling (shard count, lock hold time, hash quality) before treating it as a general recommendation.
* **`horde`'s same-hasher remove win** (clearly ahead of std/ahash/hashbrown by ~20–50%) is surprising for a concurrent table and only appears in serial `&mut` runs; verify it isn't a wrapper artefact (e.g. `clear` via table replacement vs in-place delete semantics).
* **`concurrent-map` should be re-benchmarked with a different harness strategy.** Its per-iteration clone-inside-timing design and private per-thread clones mean its concurrent numbers (§2, often 4–40× slower than the pack) reflect the adaptation cost, not the crate's actual concurrent behaviour. Either pre-clone per worker *outside* the timed region or measure a genuinely shared-map API.
* **The ordered concurrent maps** (`crossbeam-skiplist`, `btreemap`-style ordered designs) never approach the fastest in any operation here; consider dropping them from future runs or giving them workloads with ordered-range queries where their structure pays off.
* **`indexmap` vs hashbrown on String growth:** `indexmap` being clearly ahead (up to 1.35× at 1M String) is worth confirming with a capacity-hinted build and profiling — if real, it recommends `indexmap` for large String-keyed tables built once and iterated.

### Measurement quality issues that could affect conclusions

1. **No common-hasher variants for concurrent benchmarks.** Contention, synchronization and 2–3-thread throughput all use each map's default hasher (`txmap` = rapidhash, `starshard` = FxHash, `dashmap`/`papaya`/`scc` = SipHash `RandomState`, `leapfrog` = `std::DefaultHasher`). For String keys this mixes hashing speed into the concurrency result and may overstate `txmap`/`starshard`. A shared-hasher concurrent run (or a SipHash-forced run of txmap/starshard) is needed before the concurrent ordering is treated as definitive.
2. **`create` measures a batch of 10,000 `Map::new()` calls.** For zero-allocation constructors the per-map cost implied by the medians (<1 ns) is below what the harness can meaningfully time (the compiler can largely hoist pure constructions out of the loop modulo `black_box`), so only order-of-magnitude differences (e.g. sharded maps) are trustworthy.
3. **Sub-ns / few-ns medians** (`clone` for `rpds` at ~1.7 ns, `intmap` hit/miss at ~1.4–1.8 ns per lookup) sit near the timing floor; their *ratios* are meaningful but small absolute differences between near-identical leaders (ratios of 1.00–1.03) should not be over-interpreted.
4. **Aggregate-per-iteration timings.** Lookup/remove iterate over 100 keys, growth over N inserts, throughput over 10K mixed ops — medians are per iteration, not per element. All comparisons are within-variant, which is valid; do not compare absolute numbers across variants.
5. **Concurrent timings scale total work with thread count** (threads × 10K ops), so 3-thread numbers are naturally larger than 2-thread numbers; only within-thread-count rankings should be compared.
6. **Measurement protocol:** 1 s warm-up, 2 s measurement (3 s concurrent), wall-clock timings, threads CPU-pinned for concurrent runs. The concurrent benches' higher MAD (up to ~15% for outlier impls) means small margins (≤ ~7%) between concurrent maps should be treated as noise-level until confirmed.
7. **Iteration can be vectorised.** The iterate benchmark sums all values and only `black_box`es the final sum; contiguous-layout maps (`indexmap`) let the compiler vectorise, which amplifies its already-expected advantage. If the goal is to measure iteration *overhead*, an opaque per-entry operation would be a fairer probe.
