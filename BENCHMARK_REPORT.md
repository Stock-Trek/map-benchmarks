### 3.2 Recommended implementation by use case

| Use case | Recommended | Why |
|---|---|---|
| Default `u64` or trusted-string keys, single thread | **`rustc-hash`** (`FxHashMap`) | Fastest in 26/64 serial variants; wins most write, growth and get-or-insert work. Caveat: FxHash is not DoS-resistant. |
| Default keys, untrusted input / safety | **`std`**, **`hashbrown`**, or **`ahash`** | All within 10% of the fastest in 18–23 serial variants; DoS-resistant hashers and no dependency risk. |
| Same-hasher "fair" comparison | **`std`** / **`hashbrown`** / **`ahash`** | With a common hasher these three converge; each wins 4–8 variants and is within 10% of the fastest in 18–23. |
| Full-map iteration | **`indexmap`** (ordered alternatives: `btreemap`, `hashlink`) | Wins all six iterate variants by 2.8–3.4×; contiguous storage is decisive. |
| Cheap clone / persistent snapshots | **`rpds-hash-trie-map`**, then **`immutable-chunkmap`** / **`imbl`** | O(1)/structural-sharing clone (2.2 ns for `rpds`); `clone` wins all three sizes. These are not competitive on mutation. |
| Concurrent, general purpose | **`txmap`** | Fastest in 33/48 concurrent variants and within 10% in 39/48; strong across read and write mixes. |
| Concurrent, `u64` keys | **`leapfrog`** | Wins 12 concurrent variants, all `u64`; scales best on hot integer keys. |
| Concurrent, write-heavy especially with `String` keys | **`scc`** | `scc` wins the `String<32>` write-only/write-heavy cases (e.g. `synchronization/threads-2` and `throughput/threads-3`); its margin over `txmap` is 9–15%. |
| Single hot key (lock/synchronization stress) | **`txmap`**, **`leapfrog`** (u64) | `txmap` wins 16/24 synchronization variants; `leapfrog` takes 6 (all `u64`), with single wins from `papaya` and `scc`. |
| Remove-heavy | **`horde`** (same-hasher), **`intmap`**/`rustc-hash` (u64) | `horde` is clearly ahead under a common hasher; `intmap`/`rustc-hash` lead for u64. |
| Fastest map construction | **`immutable-chunkmap`** | 3.12 µs to create 10,000 maps (effectively lazy/zero-alloc). |

### 3.3 Trade-offs between operations

- **Iteration vs point operations.** `indexmap` wins iteration by a wide margin (2.8–3.4×) but never leads any other operation. If a workload iterates often and mutates rarely, `indexmap` is the clear choice; otherwise it is middling.
- **Default hasher vs map design.** `rustc-hash`'s out-of-the-box dominance is largely its FxHash hasher, not its table: many same-hasher rows show `std`/`hashbrown`/`ahash` either winning or matching. Teams using `rustc-hash` are buying a fast (but non-DoS-resistant) hasher.
- **Concurrency key-type split.** "Fastest concurrent map" depends on key type: `leapfrog` for `u64`, `txmap` for `String<32>` and mixed workloads, `scc` for some write-heavy String cases. There is no single winner.
- **Persistent clones vs mutation cost.** `rpds-hash-trie-map` and `immutable-chunkmap` clone in nanoseconds but lose badly on writes and are far slower on iteration. They are specialised, not general-purpose.
- **Specialised integer maps.** `intmap` wins several `u64` lookup/remove variants but cannot store non-integer keys at all and must be excluded from every string-key test.
- **Hot-key vs spread contention.** Under a single hot key, `txmap`/`leapfrog` stay best; under uniform spread, `scc`/`dashmap` become more relevant, especially for writes. Sharding alone (`dashmap`, `starshard`) does not win hot-key benchmarks, as expected.

### 3.4 Consistently close to the fastest

- **`ahash`**: within 10% in 23/64 serial variants despite winning only 5. It is rarely the winner and rarely far off.
- **`hashbrown`**: within 10% in 21/64 serial variants (4 wins) — the closest general-purpose alternative to `ahash`/`std`.
- **`std`**: within 10% in 18/64 and winner in 8; the strongest "safe default" across serial work.
- **`txmap`**: within 10% in 39/48 concurrent variants (winner in 33); it is both the leader and the safe pick.
- **`leapfrog`**: within 10% in 17/48 concurrent variants, entirely on `u64`.

## 5. Implementation Limitations

Findings from the wrappers in `src/maps/`. "Interior mutability" means mutation through `&self`.

- **`ahash`** (`ahash_benchmap.rs`): requires `K: Hash + Eq`; `V: Clone` because all reads/removes return cloned values. Custom hasher supported. Mutation takes `&mut self`; `get_or_insert` is only implemented for `&mut self`. No ordering guarantees.
- **`btreemap`** (`btreemap_benchmap.rs`): requires `K: Ord` (not `Hash`). **No custom hasher** (comparison-based). `&mut self` only. Ordered iteration.
- **`crossbeam-skiplist`** (`crossbeam_skiplist_benchmap.rs`): requires `K: Ord + Send + 'static`, `V: Send + 'static` for mutation (`V: Clone` where a value is returned). **No custom hasher**. Interior mutability for `insert`/`remove`/`get_or_insert`; `clear` needs `&mut self`.
- **`dashmap`** (`dashmap_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone` where values are returned. Custom hasher supported. Interior mutability. `clone_map` is a deep clone of all shards, not O(1).
- **`hashbrown`** (`hashbrown_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher + Default`; `V: Clone` where values are returned. Custom hasher supported. `&mut self` only.
- **`hashlink`** (`hashlink_benchmap.rs`): requires `K: Hash + Eq`; construction needs `H: Default`, but `BenchMapNewWithHasher` is implemented with **no bounds on `H` at all** (a wrapper quirk). Custom hasher supported. `&mut self` only. Iterates in insertion order.
- **`horde`** (`horde_benchmap.rs`): requires `K: Clone + Hash + Eq` for insert/remove and `V: Clone`. Custom hasher supported. Reads and iteration must run inside `horde::collect::pin(...)` (QSBR pin) — ergonomically unusual. Although the crate is concurrent, the wrapper exposes mutation only through `&mut self`, so `horde` is absent from concurrent benchmarks.
- **`imbl`** (`imbl_benchmap.rs`): requires `K: Hash + Eq + Clone`, `V: Clone`, `H: BuildHasher + Clone` for mutation. Custom hasher supported. Persistent HAMT, but mutation goes through `&mut self`.
- **`immutable-chunkmap`** (`immutable_chunkmap_benchmap.rs`): requires `K: Clone + Ord`, `V: Clone`. **No custom hasher**. Mutation uses copy-on-write methods (`insert_cow`, `get_or_insert_cow`, `remove_cow`) on `&mut self`. **No `clear`**, so it is absent from clear-and-reuse. Persistent; clone is cheap.
- **`indexmap`** (`indexmap_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher + Default`; `V: Clone` where returned. Custom hasher supported. `&mut self` only. **`remove` uses `swap_remove`**, which does not preserve insertion order (unlike `shift_remove`).
- **`intmap`** (`intmap_benchmap.rs`): requires `K: IntKey` (integer keys only, `Copy`). **No custom hasher and no non-integer keys** — absent from every string-key variant. `&mut self` only.
- **`leapfrog`** (`leapfrog_benchmap.rs`): requires `K: Eq + Hash + Copy` and `V: leapfrog::Value` (`Sized + Debug + Clone + Copy`), `H: BuildHasher + Default`. Custom hasher supported. Interior mutability. **The most restrictive key requirement**: `K: Copy` rules out `String` keys, so it is absent from all string variants.
- **`papaya`** (`papaya_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher + Default`; `V: Clone` where returned. Custom hasher supported. Interior mutability via `pin()` guards. `clear` needs `&mut self`.
- **`rpds-hash-trie-map`** (`rpds_benchmap.rs`): requires `K: Eq + Hash`, `H: BuildHasher + Clone + Default`; `V: Clone` for reads. Uses `archery::RcK`, so the map is **not `Send`/`Sync`** and cannot be shared across threads (excluded from concurrency). Custom hasher supported. `&mut self` only (`insert_mut`/`remove_mut`). **No `get_or_insert` and no `clear`**, so it is absent from those benchmarks. `remove` performs a lookup and then a second `remove_mut` to return the value. Clone is O(1).
- **`rustc-hash`** (`rustc_hash_benchmap.rs`): requires `K: Hash + Eq`. **No custom hasher** (fixed `FxBuildHasher`), so absent from all same-hasher variants. `&mut self` only. FxHash is fast but **not collision/DoS-resistant**, which matters for attacker-controlled string keys.
- **`scc`** (`scc_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher`; `V: Clone` (the wrapper clones values out of locks). Custom hasher supported. Interior mutability via the synchronous (`*_sync`) API. `.clone()` is a deep clone.
- **`starshard`** (`starshard_benchmap.rs`): requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync`. Custom hasher supported. Interior mutability. Values must be `Clone` even when not logically needed.
- **`std`** (`std_benchmap.rs`): requires `K: Hash + Eq`, `H: BuildHasher + Default`; `V: Clone` where returned. Custom hasher supported. `&mut self` only.
- **`txmap`** (`txmap_benchmap.rs`): requires `K: Hash + Eq` (plus `K: Clone` for get-or-insert, which passes `&key` and clones internally). Custom hasher supported. Interior mutability. Wrapper uses the `MutexPolicy` lock policy (a `RwLockPolicy` also exists). `clear` needs `&mut self`.

**Harness-level limitations.** The stored value type is always `u64`, and keys are limited to `u64` and `String` (lengths 16, 32 = 128). Maps requiring integer/Copy keys, exotic value types, or non-`Send` designs are therefore under-represented. Concurrent results only cover 2 and 3 threads.

## 6. Recommendations

1. **Separate hasher effects from map effects when making claims.** The `out-of-the-box` tables are dominated by `rustc-hash` (FxHash). The `same-hasher` tables show that `std`, `hashbrown`, and `ahash` are effectively tied and are the fair general-purpose winners. Any "fastest map" claim should cite the comparison mode.
2. **Use `indexmap` only where iteration dominates**, and be aware its `remove` semantics are `swap_remove`.
3. **For concurrent workloads, prefer `txmap`**, with `leapfrog` for `u64` keys; treat `dashmap`-vs-`txmap` gaps under 10% as noise given `dashmap`'s dispersion.
4. **Re-measure the noisy cases before acting on small gaps**: the 1M growth variants, `rpds` iteration, `dashmap` synchronization/write-heavy, and `leapfrog` contention/synchronization.
5. **Investigate measurement quality on near-zero benchmarks.** `create` (immutable-chunkmap at 3.12 µs / 10K), `clone` (~2.2 ns for `rpds`), and sub-300 ns lookups are near the timer's practical resolution; consider an amortized/unit-time variant to confirm.
6. **Re-run `same-hasher` with the full field** where possible. `btreemap`, `crossbeam-skiplist`, `immutable-chunkmap`, `intmap`, and `rustc-hash` cannot take the common hasher; a separate ordered-map comparison and a separate "fast hasher on every table" run would sharpen the conclusions.
7. **Document the excluded maps** (`concread`, `flurry`, `concurrent-map`) so results are not read as a complete survey.
8. **Treat persistent maps as a distinct category.** `rpds`, `imbl`, and `immutable-chunkmap` are excellent for clone/snapshot semantics and uncompetitive for mutation; they should not be ranked against mutable maps for write workloads.

*All timings are drawn exclusively from `target/criterion/**/new/estimates.json`; no numbers are estimated or invented. Figures use `median.point_estimate`.*
