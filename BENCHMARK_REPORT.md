### 3.3 Trade-offs (different implementations excel at different operations)

- **`rustc-hash`**: unbeatable serial performance with its fixed FxHash, but it is deterministic (collision-attackable), cannot take a custom hasher, and has no concurrent mode. It disappears from same-hasher comparisons.
- **`leapfrog`**: dominates contention but demands `Copy` keys **and** `Copy` values, has no `clear()` and no `Clone`, and is expensive to construct (1.23 ms/10K maps) and to grow (107 ms to 1M entries — 5× `rustc-hash`).
- **`indexmap`**: iteration is 3× faster than any hash map, and it wins same-hasher String growth, but it loses to plain hash maps on insert/lookup (index-array maintenance).
- **`intmap`**: integer lookups are ~1.4× faster than `rustc-hash` and ~1.9× faster than `ahash`, but keys must be integers (`IntKey`); no custom hasher.
- **Persistent maps (`rpds`/`imbl`/`immutable-chunkmap`)**: O(1) clone at any size, but clone-then-write is 10–17× slower than a deep-copying hash map, and `immutable-chunkmap` is the worst map at 1M growth (497 ms).
- **`horde`**: a copy-on-write table that is surprisingly fast at remove/insert when it holds the only reference (skips the copy) — but it is single-threaded despite the epoch-pinning machinery.
- **`txmap`**: the best 2-thread map, but its mutex policy shows at 3 threads under read-only single-key contention (1.3 ms — 8× slower than `leapfrog`).
- **Hash-function vs table design**: under `same-hasher`, `std`, `ahash`, `hashbrown`, and `hashlink` are within 1.5% on lookups — the hasher, not the probing table, is what separates them in these benchmarks.

### 4.2 Fast implementations with unusually noisy measurements

- **`create` / `rustc-hash`** has the largest std/median ratio in the entire dataset (x0.45). Its median is stable (MAD x0.005) but the distribution has heavy outliers. This matters because `rustc-hash` (2.85 µs) and the winner `immutable-chunkmap` (2.84 µs) are separated by less than `rustc-hash`'s own noise — **first place in `create` is a statistical tie**, not a meaningful difference.
- **`synchronization-3-threads_read-only` / `concurrent-map`** — MAD x0.13, std x0.25. Thread-synchronized timing with the wrapper's per-thread clone pattern.
- **`clone-then-write_map-size-1K` / `dashmap`** — MAD x0.16, the noisiest by MAD ratio.
- No **fastest** implementation in any group has std/median > 0.10, so headline winners are generally stable. Noise is concentrated in slow implementations (`concurrent-map`, `papaya`, `imbl`) and in very short benchmarks (`create`, `clone-then-write` 1K) where scheduler/timer jitter dominates.

## 5. Implementation Limitations

Findings from the wrapper code in `src/maps/` and the benchmark selection comments in `benches/`.

### `ahash` (ahash_benchmap.rs)
- Trait bounds: `K: Hash + Eq`, `V: Clone` for most ops; `K: Clone` additionally for clone.
- Custom hasher supported via `BenchMapNewWithHasher` (`H: BuildHasher`).
- Not concurrent — no `Send`/`Sync` wrapper, excluded from all concurrent benchmarks.
- Default hasher is randomized (a `RandomState` per map), hence the high `create` cost (~20 ns/map).

### `btreemap` (btreemap_benchmap.rs)
- Trait bounds: `K: Ord`, `V: Clone` (`K: Clone` for clone). No `Hash` requirement.
- **No custom hasher** — excluded from all same-hasher groups.
- Not concurrent. Ordered iteration, `O(log n)` operations; never fastest, never within 10%.

### `concread` (concread_benchmap.rs) — *not benchmarked*
- Trait bounds: `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static` — note the unusual `Debug` requirement.
- **Does not implement `Clone`** (excluded from clone benchmarks).
- **No custom hasher.**
- Every mutation goes through `write()` → `insert/remove/clear` → `commit()` (MVCC transaction), and every read through `read()` — heavy per-op overhead.
- Commented out of all benchmarks as "too slow".

### `concurrent-map` (concurrent_map_benchmap.rs)
- Trait bounds: `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`.
- **The crate's `ConcurrentMap` is `Send` but not `Sync`** (EBR state lives in a `RefCell`). The wrapper works around this with a `Mutex`-protected "master" map and a **thread-local clone per thread, refreshed once per iteration via a token and type-erased `Any` downcast**. This is a significant ergonomic and runtime cost that the benchmark measures — results may understate the raw crate for some patterns.
- **No `clear()`** (no `BenchMapMutClear`) — excluded from clear-and-reuse.
- **No custom hasher**, **no entry API** — get-or-insert is emulated as get-then-insert and is *not* atomic.
- Slowest map to construct (7.46 ms/10K maps = ~746 ns/map) and worst read-only single-key synchronization (472 µs).

### `crossbeam-skiplist` (crossbeam_skiplist_benchmap.rs)
- Trait bounds: `K: Ord` for reads/iteration; `K: Ord + Send + 'static`, `V: Send + 'static` for writes; `V: Clone` for get/remove.
- **Does not implement `Clone`** (excluded from clone benchmarks).
- **No custom hasher** (ordered structure).
- `O(log n)` skiplist; never fastest, never within 10% of fastest.

### `dashmap` (dashmap_benchmap.rs)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher + Clone + Default`; `K/V: Clone` for clone.
- Custom hasher supported. Concurrent (both `&self` and `&mut` paths).
- Participates in all 78 groups; **never fastest, never within 10%** — despite being the most popular concurrent map. Its sharded design (default shard count) consistently trails `txmap`, `leapfrog`, and `scc`.

### `flurry` (flurry_benchmap.rs) — *not benchmarked*
- Trait bounds: `K: Sync + Send + Clone + Hash + Ord`, `V: Sync + Send` (+ `Clone` for get/remove) — note the unusual `Ord` requirement on keys.
- Custom hasher supported. Every op requires `pin()`.
- Commented out of all benchmarks as "too slow (creates a `seize::Collector` per map)".

### `hashbrown` (hashbrown_benchmap.rs)
- Trait bounds: `K: Hash + Eq` for insert/get/remove; construction has **no** `K`/`V` bounds.
- Custom hasher supported. Not concurrent.
- `hashbrown` is the engine under `std::collections::HashMap`; with a common hasher the two are interchangeable.

### `hashlink` (hashlink_benchmap.rs)
- Trait bounds: `K: Hash + Eq`, `V: Clone` for get/get-or-insert.
- Custom hasher supported. Not concurrent (no `&self` mutation).
- Linked-list ordering bookkeeping makes it slower than plain hash maps on writes; only close to the fastest on lookups.

### `horde` (horde_benchmap.rs)
- Trait bounds: `K: Clone + Hash + Eq` (reads need `Hash + Eq`), `V: Clone`.
- Custom hasher supported. **Not concurrent** — `write()` returns a COW copy that must be stored back; mutations require `&mut`.
- Every op goes through `horde::collect::pin()` (epoch pin) even single-threaded.
- Fastest at same-hasher remove/insert — the COW `write()` on the only reference skips copying.

### `imbl` (imbl_benchmap.rs)
- Trait bounds: `K: Hash + Eq + Clone`, `V: Clone`; `H: BuildHasher + Clone`.
- Custom hasher supported. Not concurrent. Persistent (HAMT).
- O(1) structural-sharing clone (~12 ns at any size) but clone-then-write is ~10× slower than `ahash` at 100K.

### `immutable-chunkmap` (immutable_chunkmap_benchmap.rs)
- Trait bounds: `K: Clone + Ord`, `V: Clone`.
- **No custom hasher** (ordered persistent structure).
- **No `clear()`** (excluded from clear-and-reuse).
- COW mutation via `insert_cow`/`remove_cow`/`get_or_insert_cow`; requires `&mut`.
- Fastest to construct (lazy, ~0.28 ns/map) but the slowest map at 1M growth (497 ms).

### `indexmap` (indexmap_benchmap.rs)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`.
- Custom hasher supported. Not concurrent.
- Preserves insertion order; **`remove` uses `swap_remove`** — it does *not* preserve order on removal (an API-behavior caveat, not a bug).
- Unbeatable iteration; competitive same-hasher growth for String keys.

### `intmap` (intmap_benchmap.rs)
- Trait bounds: `K: IntKey` — **integer keys only** (`u8`–`u128`, `usize`, signed ints, etc.); no String keys. Excluded from all String-key benchmarks.
- **No custom hasher** (uses an internal hash).
- Not concurrent.
- Fastest u64 lookups/removal when it can be used.

### `leapfrog` (leapfrog_benchmap.rs)
- Trait bounds: `K: Eq + Hash + Copy`, `V: Value` where `Value: Sized + Debug + Clone + Copy` — **both keys and values must be `Copy`**. Excluded from all String-key benchmarks and any non-Copy value.
- Custom hasher supported (`H: BuildHasher + Default`).
- Concurrent (internally synchronized `&self` ops). Participates in all concurrent benchmarks.
- **No `clear()`**, **no `Clone`** — excluded from clear-and-reuse and clone benchmarks.
- Expensive construction (~123 ns/map) and growth (107 ms at 1M u64, 5× `rustc-hash`), but the dominant concurrent map under contention.

### `papaya` (papaya_benchmap.rs)
- Trait bounds: `K: Hash + Eq`, `H: BuildHasher`; `K/V: Clone` for clone.
- Custom hasher supported. Concurrent — **every operation requires a `pin()` guard** (hazard-pointer based).
- Participates in all 78 groups; never fastest, never within 10%. Worst write-heavy sync degradation (18× from read-only to write-only).

### `rpds-hash-trie-map` (rpds_benchmap.rs)
- Trait bounds: `K: Eq + Hash`, `H: BuildHasher + Clone`.
- Custom hasher supported. Not concurrent. Persistent (HAMT).
- **No entry API** — get-or-insert emulated as get-then-insert (non-atomic).
- **No `clear()`**.
- O(1) clone (1.1 ns at any size) but clone-then-write is 17× slower than `ahash` at 100K, and it is second-slowest at 1M growth (183 ms).

### `rustc-hash` (rustc_hash_benchmap.rs)
- Trait bounds: `K: Hash + Eq`; `K/V: Clone` for clone.
- **No custom hasher** (fixed `FxBuildHasher`) — excluded from all same-hasher groups.
- Not concurrent.
- FxHash is fast but **deterministic and not collision/DoS resistant**.
- The serial out-of-the-box champion across inserts, lookups, removes, growth, and single-threaded throughput.

### `scc` (scc_benchmap.rs)
- Trait bounds: `K: Hash + Eq`, `H: BuildHasher`.
- Custom hasher supported. Concurrent — every op uses the `*_sync` API (`read_sync`, `entry_sync`, `upsert_sync`, `remove_sync`, `iter_sync`, `clear_sync`).
- Never fastest, but comes within 10% in write-heavy 3-thread throughput and write-only synchronization.

### `starshard` (starshard_benchmap.rs)
- Trait bounds: `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync`.
- Custom hasher supported (default `FxBuildHasher`). Concurrent.
- **Fixed 8 shards** in the wrapper (`with_shards_and_hasher(8, …)`) — shard count is not tuned.
- Never fastest, never within 10%. Expensive construction (2.76 ms/10K maps).

### `std` (std_benchmap.rs)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`.
- Custom hasher supported. Not concurrent.
- Default `RandomState` (SipHash-1-3) costs ~2.4× on small-key lookups vs `ahash`/`rustc-hash`, but with a shared hasher `std` ties `ahash`/`hashbrown` to within 1.5%.

### `txmap` (txmap_benchmap.rs)
- Trait bounds: `K: Hash + Eq` (`K: Clone` for get-or-insert), `H: BuildHasher`.
- Custom hasher supported. Concurrent with `MutexPolicy`.
- Expensive construction (6.86 ms/10K maps = ~686 ns/map).
- Best 2-thread and write-heavy concurrent performer; weak at read-only single-key sync (1.3 ms vs `leapfrog` 162 µs).

## 6. Recommendations

### 6.1 Further investigation

1. **`dashmap`, `papaya`, `starshard`, `scc`, `concurrent-map` never win.** The most popular concurrent map (`dashmap`, 78/78 groups) is never fastest and never within 10%. Investigate shard counts (starshard is fixed at 8 in the wrapper; dashmap uses its default), per-op guard/pin costs (`papaya`), and whether the wrapper patterns (e.g. `concurrent-map`'s per-thread clone) handicap the raw crates.
2. **`leapfrog`'s Copy restriction.** Its contention results (1.6–4.5× over the field) are so strong that a `Clone`-based or string-key-capable variant would be high-value. Confirm whether the copy-only `Value` bound is fundamental to the leapfrog design.
3. **`horde` remove/insert wins.** COW-on-unique-reference removal being the fastest remove in the dataset deserves a closer look to confirm it is not a wrapper artifact (e.g. `write().remove()` on a map with no other references).
4. **`create` ranking.** `rustc-hash` (2nd) has std/median = 0.45; its 2.85 µs vs `immutable-chunkmap`'s 2.84 µs is within noise. Re-run `create` with more samples before treating `immutable-chunkmap` as the construction winner.
5. **`intmap`/`leapfrog` extreme lookup numbers** are measured on tiny maps (100 keys) that fit in L1; they will not generalize to large maps. Add a large-map lookup benchmark to validate scaling.
6. **`concurrent-map`'s get-or-insert is non-atomic** in the wrapper (get then insert). If atomic upsert matters, this implementation cannot currently provide it via the bench harness.

### 6.2 Measurement quality issues

- **No baseline/change data.** All conclusions are from single-run absolute medians; no Criterion comparison (change detection) data exists. Differences under ~2% should be treated as equivalent.
- **Near-identical medians in same-hasher lookup groups** (e.g. 235.6 vs 235.8 vs 236.3 ns for `hashbrown`/`ahash`/`std` u64 lookups) are below meaningful resolution — treat these implementations as tied.
- **Short benchmarks are noisy**: `create`, `clone-then-write` (1K), and sub-µs lookups show the highest relative variance (scheduler/timer jitter dominates); `create`/`rustc-hash` and `clone-then-write` 1K/`dashmap` are the worst cases.
- **Persistent-map clone timings (1–13 ns) are at the clock-resolution floor.** Report them qualitatively ("O(1), effectively free") rather than as precise measurements.
- The `concurrent-map` wrapper clones the master map per thread per iteration and downcasts through `Any`; its timings include this harness overhead and should not be read as raw crate performance.
