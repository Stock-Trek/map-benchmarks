**Scope of the data.** This report is derived exclusively from the Criterion.rs reports in `target/criterion/` for this repository. It covers **19 map implementations**, **112 benchmark groups**, and **1,323 individual measurements**. Only the current absolute measurements were available: there is no saved baseline, no historical run, and no comparison/change data in the reports, so every statement below compares implementations against each other *within this single run*, not against an earlier version of themselves.

**Conventions used throughout.**

* **Primary metric:** `median.point_estimate` from each `new/estimates.json`, in nanoseconds, converted to ns / µs / ms. `mean.point_estimate` was only used if a median were missing (it never was).
* **"Within 10%":** an implementation is a close contender when its median is at most **1.10×** the fastest median in the same group. Ratios are always *implementation time ÷ fastest time* (1.00× = tied, 2.00× = twice as slow).
* **Group = directory.** A "group" is one Criterion benchmark group directory, e.g. `iterate/map-size-100K/out-of-the-box`; the full path of a measurement is `target/criterion/<group>/<implementation>/new/estimates.json`. When a benchmark name alone is ambiguous, the group path is given.
* **Per-iteration time.** Each reported time is the median wall time of *one iteration* of that benchmark group, which is not always one operation: 100 lookups/removals for `lookup-*`, `remove`, and `key-sensitivity`; 10,000 insertions for `insert`, `growth`, and `clear-and-reuse`; 10,000 × thread-count operations for the concurrent groups. The Scope table states exactly what one iteration contains.
* **Dispersion:** `median_abs_dev` (MAD) and `std_dev` from the same estimates file, expressed as a percentage of the median.

* With the same hasher, `ahash` (256 µs u64), `std` (257 µs) and `hashbrown` (259 µs) tie, and `hashbrown` (1.005 ms), `ahash` (1.027 ms) and `std` (1.037 ms) tie on String<32>. `dashmap` (1.18×) and `indexmap` (1.19×) are the closest of the rest; `imbl`, `papaya` and `starshard` are 5.2–5.5× behind on u64, because their upsert path allocates/refcounts a node or copies a shard per miss.
* The maps without an upsert API (`horde`, `rpds-hash-trie-map`) were not measured here; `leapfrog`'s entry-based path is 2.6× behind on u64 despite being a lock-free table.

### 2.5 `lookup-hit` — 100 lookups of present keys

100 successful gets from a 10,000-entry map; the value (`u64`) is cloned.

| Variant | Fastest | Fastest median | Runner-up | Within 10% (time, ratio) |
|---|---|---|---|---|
| `out-of-the-box/String<32>` | rustc-hash | 971 ns | ahash 1.18 µs (1.22×) | none |
| `out-of-the-box/u64` | intmap | 172 ns | rustc-hash 208 ns (1.21×) | none |
| `same-hasher/String<32>` | hashbrown | 1.18 µs | ahash 1.18 µs (1.00×) | ahash 1.18 µs (1.00×), std 1.19 µs (1.01×) |
| `same-hasher/u64` | std | 276 ns | ahash 285 ns (1.03×) | ahash 285 ns (1.03×), hashbrown 285 ns (1.03×) |

**What stands out**

* **`intmap` is the fastest map on u64 keys by a wide margin** — 172 ns for 100 lookups = **1.72 ns per lookup**, 1.21× ahead of `rustc-hash` (2.08 ns) and 8× ahead of out-of-the-box `std` (13.8 ns). Direct integer indexing avoids hashing altogether.
* On String<32> keys `rustc-hash` wins at 971 ns = **9.7 ns per lookup**, 1.22× ahead of `ahash` (11.8 ns). Out-of-the-box `std` is 2.92 µs (29 ns) — the 3× penalty of SipHash-1-3 on a 32-byte key.
* With the same hasher, `std`, `ahash` and `hashbrown` are within 3% on both key types (2.76–2.85 ns u64, 12.0–12.4 ns String), confirming that hit-path differences between conventional hash tables are negligible compared with hashing and cache effects.
* The slowest structures are the ordered and persistent ones: `crossbeam-skiplist` 7.42 µs (74 ns/lookup, 43× intmap), `rpds-hash-trie-map` 4.74 µs (27.6×), `btreemap` 1.61 µs, `imbl` 1.91 µs, and `dashmap` 1.89 µs (shard lookup + `RwLock` read guard).

### 2.6 `lookup-miss` — 100 lookups of absent keys

| Variant | Fastest | Fastest median | Runner-up | Within 10% (time, ratio) |
|---|---|---|---|---|
| `out-of-the-box/String<32>` | rustc-hash | 507 ns | ahash 625 ns (1.23×) | none |
| `out-of-the-box/u64` | intmap | 131 ns | hashbrown 198 ns (1.51×) | none |

**What stands out**

* `intmap` again leads on u64 (131 ns = 1.31 ns/lookup, 1.51× ahead of `hashbrown`/`rustc-hash`); `rustc-hash` leads on String<32> (507 ns = 5.1 ns).

**What stands out**

### 2.12 `clone-then-write` — snapshot plus 10% new keys

This is the test that decides whether structural sharing actually pays.

| Variant | Fastest | Fastest median | Runner-up | Within 10% (time, ratio) |
|---|---|---|---|---|
| `map-size-100K/out-of-the-box` | rustc-hash | 200 µs | ahash 203 µs (1.01×) | ahash 203 µs (1.01×) |

**What stands out**

* **`rustc-hash` wins all three sizes** (1.31 µs / 14.2 µs / 200 µs), with `ahash` within 1.01–1.11×. A deep copy of 10K entries (~6 µs) plus 1,000 inserts is cheaper than path-copying 1,000 nodes.

* In the worst u64 case (3 threads, Zipfian 2.0) `dashmap` (2.2 ms), `scc` (2.2 ms) and `papaya` (2.6 ms) are 2.9–3.5× behind; `crossbeam-skiplist` (3.3–10.3×) and `starshard` (2.1–9.2×) trail in every contention group. String<32> contention costs 1.2–2.5× more than u64 for the hash-table designs (only `starshard`, which clones shard snapshots, is unaffected), again the hashing cost.

### 3.3 Trade-offs

* **Throughput versus snapshot cost.** The persistent maps (`rpds-hash-trie-map`, `immutable-chunkmap`, `imbl`) buy O(1) clones with 1.8–6× slower inserts and 12–26× slower clone-then-write. There is no implementation in this suite that is both a fast mutable table and a cheap snapshot.
* **Read path versus write path.** `leapfrog` has the best u64 read path under contention (320 µs read-only, 3 threads) but its `get-or-insert` and `insert` are 2.6–2.8× behind. `horde` is the best remover (629 ns u64) and one of the worst inserters (3.27× on String). `papaya` wins String read-only and is 3.6× behind on String write-only. Only `txmap` and `ahash`/`hashbrown` are consistently good at both.
* **Hasher versus table.** `rustc-hash`'s out-of-the-box wins are mostly `FxHash` wins: with a shared hasher it is still fast but `ahash`/`hashbrown`/`std` close to within 3%. Conversely `std` looks 3–10× slow out-of-the-box only because of SipHash-1-3. `FxHash` is not DoS-resistant; `std`'s SipHash is.
* **Sharding versus hot keys.** Sharded designs (`dashmap`, `scc`, `starshard`, `txmap`) are strong on disjoint-key throughput (`txmap` 286 µs, u64 read-heavy, 2 threads) and weak when all threads touch one key (`dashmap` 1.31 ms vs `txmap` 415 µs on 3-thread u64 read-only; `starshard` 4.19 ms). Lock-free designs (`leapfrog`, `papaya`) invert this: they are excellent on hot reads and poor on writes.
* **Layout versus flexibility.** `indexmap` is 2.6–3.4× faster to iterate than any hash table and 1.04–1.34× faster to grow with String keys, but 1.2–2.0× slower to insert into a populated map and 3.9× slower to clone than `std` at 100K.
* **Memory cost is invisible here.** No benchmark reports allocation counts or resident size; the implementation that is fastest (`rustc-hash`/`hashbrown` cluster) is also the one with the densest layout, while `indexmap` pays an extra index vector and persistent maps pay node overhead. Do not infer memory efficiency from these timings.

### 3.5 The hasher is the biggest single lever

Four observations support this:

1. Removing the hasher difference collapses the top of the serial table: `rustc-hash`'s out-of-the-box wins shrink from "clearly ahead" to "within 3%" when `ahash`, `hashbrown` and `std` use the same hasher (Section 3.4).
2. `std` moves from 1.38 µs (13.8 ns/lookup) to 2.76 ns/lookup on u64 `lookup-hit` — a **5×** swing — purely by swapping SipHash for the shared hasher.
3. `key-sensitivity` shows the same effect along the key-length axis: 2.75 ns (u64) → 24.1 ns (String<128>) for `ahash`, i.e. an 8.7× increase for 16× more key bytes.
4. On 1M-entry growth, where hashing is amortised over allocation and cache misses, the out-of-the-box ranking changes completely (`ahash` beats `rustc-hash` on u64) — hasher choice stops being decisive once memory becomes the bottleneck.

Practical consequence: choose the hasher first (DoS resistance, key type, hash quality), then the table. Ranking maps by out-of-the-box numbers measures hash functions as much as data structures.

## 4. Stability

### 4.1 How stable are these numbers?

Criterion recorded **exactly 100 samples for every one of the 1,323 measurements**. Across the whole suite the median relative MAD is **0.58%** and the median coefficient of variation (std. dev. ÷ median) is **1.47%**. Only 178 measurements (13.5%) exceed 2% MAD, 36 (2.7%) exceed 5%, 9 (0.7%) exceed 10%, and 3 exceed 20%.

That is a stable dataset, but the distribution has a long tail. The MAD is the more trustworthy dispersion measure here: several groups have a small MAD (the median is well determined) and a large standard deviation (a few samples were much slower, usually the first ones or ones hit by scheduling). Those groups are listed separately in Section 4.3.

**Measurement setup that affects stability:** 1 s warm-up; 2 s measurement (3 s for concurrent binaries); `Linear` sampling except `growth` and `clear-and-reuse`, which use `Flat`. All measurements are affected by the machine's cache/frequency behaviour, which is not recorded in the reports.

| `txmap` | `contention/threads-2/u64/Zipfian(1.0)` | 269 µs | 0.6% MAD, 19.6% CV | The winner of that group; its margin over `leapfrog` (1.42×) is much larger than the noise, but per-sample times are heavy-tailed. |
| `horde` | `remove` (both key types) | 1.89 µs (oob u64) | 1.0% MAD, 16.2% CV | Wins the same-hasher removal groups; the win (1.31×) survives the noise. |
| `papaya` | `throughput/threads-3/u64/read-heavy` | 587 µs | 0.3% MAD, 18.3% CV | Its third-place finish is stable, but individual samples vary by 18%. |

### 4.5 Recommendations for making this data decision-grade

1. **Save a baseline.** `target/criterion/*/base/` currently contains an exact copy of the `new/` run (medians agree to the last digit), so there is no historical comparison in these reports. Run `cargo bench -- --save-baseline main` and later compare with `--baseline main`.
2. **Increase the budget for the expensive groups.** 1M `growth` and 100K `iterate`/`clone` groups ran 100 samples regardless of the 2 s target (a single 1M growth iteration is 39–330 ms), so their wall-clock cost was tens of seconds each; raising `measurement_time`/`sample_size` and using `Flat` deliberately would stabilise them.
3. **Repeat and take the minimum of medians** for the noisy groups in Section 4.4, or accept only differences larger than 2× the MAD.
4. **Never compare absolute times across machines.** The reports do not record CPU model, core count, cache size or governor; only within-run ratios are portable.

## 5. Implementation Limitations

Two constraints apply to *every* implementation because they are imposed by the benchmark harness, not by the crates:

* **Values must be `Clone` and lookups clone.** Every read goes through `BenchMapGetCloned`, which returns `Option<V>` by cloning. Read benchmarks therefore measure lookup *plus* value clone, and no benchmark can use a non-`Clone` value type.
* **"Internal mutability" means the wrapper can mutate through `&self`.** Maps whose API requires `&mut self` can only be measured in serial groups, no matter how concurrent the crate is internally.

The per-implementation notes below record the bounds and gaps that actually shaped the results.

### 5.1 `ahash`

* Bounds: `K: Hash + Eq`, `V: Clone`, `H: BuildHasher + Default` for `new`, `H: BuildHasher` for `new_with_hasher`, `H: Clone` for cloning.
* No internal mutability: inserts/removes/clear need `&mut self`.
* Hasher is configurable, and `AHashMap<K, V>` is a `std::HashMap` with `RandomState = ahash::RandomState`, so the type aliases are drop-in.
* Ergonomic oddity: `ahash::RandomState::new()` seeds per map, which is why `create` costs 14.4 ns per map versus 0.6 ns for `FxHashMap`.
* Restriction: hash-flooding resistance depends on the keyed `RandomState`; the "same-hasher" groups replace it with a single shared `RandomState`, which is deliberately *not* per-map keyed.

### 5.2 `btreemap`

* Bounds: `K: Ord`, `V: Clone`; no `Hash` and therefore **no hasher support at all**, so it is absent from all `same-hasher` groups.
* No internal mutability.
* Provides ordered iteration and range queries (not exercised by these benchmarks); all point operations are O(log n), which is why it is 2.1–20.6× behind the hash tables on mixed workloads.

### 5.3 `crossbeam-skiplist`

* Bounds: `K: Ord` for reads; `K: Ord + Send + 'static`, `V: Send + 'static` for inserts/removes/clear; `V: Clone` for reads and `get_or_insert`.
* **No `Clone`** for `SkipMap`, so it is absent from `clone` and `clone-then-write`.
* **No custom hasher** (it is an ordered structure), so it is absent from every `same-hasher` group.
* The `Send + 'static` requirement rules out `Rc`-based keys/values; the `get_or_insert` API requires `Send` even for the `&self` path.
* Ergonomic oddity: `clear` needs `&mut`, while inserts/removes do not — the wrapper therefore implements both `BenchMapInsert` and `BenchMapMutInsert`.

### 5.4 `dashmap`

* Bounds: `K: Hash + Eq`, `H: BuildHasher + Clone + Default`, `V: Clone` for reads/clone.
* Fully internally mutable; custom hasher supported (`with_hasher`).
* Eagerly allocates a fixed shard array (a multiple of the CPU count), which is why `create` costs 216 ns per map and `clone` copies every shard (195 µs at 100K).
* Iteration must lock every shard; `remove` takes a shard write lock. Holding a `Ref`/`RefMut` across another map call can deadlock (not exercised by these benchmarks).
* Restriction: values must be `Clone` for the read path because `get_cloned` is used; `dashmap::mapref` guards are not measured.

### 5.5 `hashbrown`

* Bounds: `K: Hash + Eq`, `V: Clone` for reads, `H: BuildHasher + Default`; custom hasher supported.
* No internal mutability.
* The raw-table API (`RawTable`, `entry_ref`, `find`) is not used by the wrapper; `hashbrown` is measured only through its safe `HashMap` surface.

### 5.6 `hashlink`

* Bounds: `K: Hash + Eq` (+`Clone` for clone), `V: Clone`, `H: Default` for `new`, `H: BuildHasher` elsewhere; custom hasher supported.
* No internal mutability.
* `LinkedHashMap` maintains insertion order and supports move-to-front/LRU operations (not benchmarked); iteration follows the linked list, which makes it 3.7× slower to iterate than `indexmap`.
* Ergonomic oddity: the `new()` bound is `H: Default` rather than `BuildHasher`, so the hasher type must also be `Default` even when a hasher instance is supplied separately.

### 5.7 `horde`

* Bounds: `K: Clone + Hash + Eq`, `V: Clone`, `H: BuildHasher + Default`; custom hasher supported via `new_with(hasher, 0)`.
* **Asymmetric API:** reads take `&self` and pin a guard; writes take `&mut self` (`write()` → `insert/remove/replace`). It is therefore absent from every concurrent group despite being a concurrent table.
* **No get-or-insert/entry API**, so it is absent from `get-or-insert`.
* `clear` is implemented as `write().replace(empty, 0)`, i.e. it discards the table rather than retaining capacity — which is why its `clear-and-reuse` numbers are 2.2× behind the leaders.
* It is nevertheless the fastest remover in the suite (629 ns u64 with a shared hasher), because the write guard gives direct access to the bucket.

### 5.8 `imbl`

* Bounds: `K: Hash + Eq + Clone`, `V: Clone`, `H: Default` for `new`, `H: BuildHasher + Clone` elsewhere; custom hasher supported.
* No internal mutability: persistent mutation is `&mut self` (`insert`, `remove`, `clear`), each path-copying.
* Persistent HAMT: O(1)-ish clones (4.6 ns) but 1.8–2.5× slower inserts and 12× slower clone-then-write than deep-copy maps; iteration is 32.7× slower than `indexmap` at 100K.
* Restriction: the `Clone` bound on keys is required for mutation, not just for cloning.

### 5.9 `immutable-chunkmap`

* Bounds: `K: Clone + Ord`, `V: Clone` — **no hashing**, so no custom-hasher support and absence from `same-hasher` groups.
* No internal mutability; COW operations (`insert_cow`, `remove_cow`, `get_or_insert_cow`) take `&mut self`.
* **No `clear`** in the crate's public surface (or at least none used by the wrapper), so it is absent from `clear-and-reuse`.
* `MapM::new()` is a no-op (empty tree, no allocation): 0.31 ns per map, the fastest `create` in the suite. That is a lazy-constructor artifact, not a claim that it is cheap to *use*.
* Constant-time clone (~3.9 ns) and 15–26× slower clone-then-write.

### 5.10 `indexmap`

* Bounds: `K: Hash + Eq`, `V: Clone` for reads, `H: BuildHasher + Default`; custom hasher supported.
* No internal mutability.
* **Semantic difference:** the wrapper removes with `swap_remove`, so removal does not preserve insertion order (the last element is moved into the hole). `shift_remove` would be O(n) and much slower. Its `remove` and `clear-and-reuse` numbers are therefore not directly comparable to an order-preserving map's.
* Strengths/limits from the layout: 2.6–3.4× faster iteration and 1.04–1.34× faster String growth, but 1.2–2.0× slower insert-into-populated and 3.9× slower clone than `std` at 100K.

### 5.11 `intmap`

* Bounds: `K: IntKey` only — no `Hash`/`Eq`, **no hasher**, no `String` keys. It is therefore absent from every `same-hasher` group and from all String<32> variants.
* No internal mutability.
* Integer radix tree: 1.31–1.72 ns per lookup and 6.2 ns per removal on u64 (best in the suite), but 4.66 ms to clone 100K entries (77× `std`) and 705 µs to iterate 100K.
* Restriction: `clone` is a deep copy of the whole trie; there is no structural sharing.

### 5.12 `leapfrog`

* Bounds: `K: Eq + Hash + Copy`, `V: Value` (leapfrog's `Value: Sized + Debug + Clone + Copy`), `H: BuildHasher + Default`. **Keys and values must be `Copy`**, so no `String` keys and no `String` values; it is absent from every String<32> group.
* **No `Clone`** implementation in the wrapper (the `LeapMap` is not `Clone`), so it is absent from `clone` and `clone-then-write`. **No `clear`**, so it is absent from `clear-and-reuse`.
* Internally mutable with `&self` (`try_insert`, `get`, `remove`); `get` returns an `Entry` whose `value()` is a second step (the wrapper's `get_cloned` does `get(key).and_then(|mut e| e.value())`).
* Constructor is `with_capacity_and_hasher(0, hasher)`: capacity 0, so `create` costs 97.7 ns per map and growth starts from an empty table.
* Its lock-free read path is the best u64 read performance under contention, but `insert`/`get-or-insert` are 2.6–2.8× behind, so it is a read-mostly specialist.

### 5.13 `papaya`

* Bounds: `K: Hash + Eq`, `V: Clone`, `H: BuildHasher + Default`; custom hasher supported.
* Fully internally mutable. Every operation goes through `map.pin()`, so guard acquisition/retirement is included in every timing; this is the main reason it is 3.4× behind `ahash` on serial lookups and 5.5× behind on serial upserts.
* `clone` is a deep copy of all shards (8.24 ms at 100K, 136× `std`), not a snapshot.
* Restriction: memory reclamation is epoch-based; pinning must not be held across blocking operations (not exercised).

### 5.14 `rpds-hash-trie-map`

* Bounds: `K: Eq + Hash`, `V: Clone`, `H: BuildHasher + Clone + Default`; custom hasher supported. Pointer kind is `archery::RcK`, i.e. **non-atomic** reference counting — the map is not `Send`/`Sync`, which is why it appears only in serial groups.
* No internal mutability (`insert_mut`/`remove_mut` take `&mut self`).
* **No get-or-insert** and **no `clear`**, so it is absent from those two families.
* Persistent HAMT: 1.74 ns clone (the cheapest in the suite) but the *slowest* iterator (4.18 ms at 100K, 103× `indexmap`), 3.74–6.15× behind `hashbrown` on insert, and 12.6–22× behind the deep-copy maps on clone-then-write.

### 5.15 `rustc-hash`

* Bounds: `K: Hash + Eq`, `V: Clone`; the hasher is fixed by the type (`FxHashMap` = `HashMap<K, V, FxBuildHasher>`), and the wrapper has **no `new_with_hasher`**, so it is absent from all `same-hasher` groups.
* No internal mutability.
* `FxHasher` is a fast, non-cryptographic, trivially collidable hash: it is the main reason `rustc-hash` wins most out-of-the-box serial groups, and it is unsuitable for adversarial/untrusted keys.
* Its 1M u64 `growth` loss to `ahash` shows the advantage is not unconditional.

### 5.16 `scc`

* Bounds: `K: Hash + Eq`, `V: Clone`, `H: BuildHasher + Default`; custom hasher supported.
* Fully internally mutable. The wrapper uses the synchronous `_sync` API (`insert_sync`, `read_sync`, `remove_sync`, `update_sync`); scc's async API is not benchmarked, and async runtimes would change the numbers.
* Per-bucket locking: strong on disjoint write-heavy throughput, weak on single-key contention (1.09 ms write-only at 2 threads; 1.94 ms read-only at 3 threads for String).
* Iteration locks buckets as it goes (224 µs at 100K, 5.5× `indexmap`).

### 5.17 `starshard`

* Bounds: `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync` — the heaviest bounds in the suite; values must be `Send + Sync` and `Clone`.
* Fully internally mutable; snapshots (`clone`) are size-independent (51.6 ns) but mutation after a snapshot costs more than a deep copy (482 µs at 100K, 2.4× the fastest).
* Constructor always uses `starshard::DEFAULT_SHARDS` (fixed shard count) and eagerly allocates: 246 ns per empty map.
* Its default hasher is `FxBuildHasher`, so out-of-the-box and same-hasher results are nearly identical for it — unlike the SipHash-defaulted crates.
* It is the slowest or second-slowest implementation in every concurrent group (1.4–13.1× behind), including 13.1× on 3-thread u64 read-only.

### 5.18 `std`

* Bounds: `K: Hash + Eq`, `V: Clone`, `H: BuildHasher + Default`; custom hasher supported.
* No internal mutability.
* Default hasher is SipHash-1-3 (DoS-resistant, ~3–5× slower than `FxHash`/`ahash` on these key sizes); `HashMap::new()` does not allocate (1.56 ns per map), so `create` is cheap but the first insert pays for allocation.
* Values must be `Clone` only because of the harness's read path; `std::collections::HashMap` itself does not require it.

### 5.19 `txmap`

* Bounds: `K: Hash + Eq` (`K: Clone` for `get_or_insert`), `V: Clone`, `H: BuildHasher + Default`; custom hasher supported through `TxMapBuilder`.
* Fully internally mutable. The wrapper fixes the policy to `txmap::MutexPolicy`; the crate's other execution policies (if used) are not benchmarked, so these results describe the mutex-policy configuration only.
* `TxMapBuilder::default().build()` eagerly allocates the shard/bucket structure (864 ns per empty map, 2,765× the lazy maps), and `clone` deep-copies every shard (168 µs at 100K).
* Its transactional API (multi-key transactions) is not exercised; only single-key operations are measured.
* Ergonomic oddity: `get_with_or_insert(&key, || value, ...)` takes the key by reference and a constructor closure, so the wrapper must clone keys for the upsert path.
* It is the best concurrent map in 37/48 groups but 1.2–3.8× slower than a single-threaded `rustc-hash` at one thread.

### 6.2 Measurement-quality issues that could affect conclusions

1. **Single run, single machine.** Every number comes from one Criterion run. The reports record no CPU model, core count, cache sizes, governor or memory configuration, so absolute timings are not portable and cannot be compared against numbers from another machine or another report.
2. **No historical data.** `new/` and `base/` are copies of the same run (medians identical to the last digit); there is no `change/` data. This report can rank implementations but cannot say whether anything regressed or improved.
3. **Coverage is asymmetric.** Concurrent groups have 6–7 implementations; serial groups have 11–19; `same-hasher` groups omit five implementations; `clone`, `clear-and-reuse` and `get-or-insert` each omit two or three. A ranking is only valid within the set of implementations that appear in that group (Appendix A).
4. **Hasher confound.** Out-of-the-box comparisons mix table design with hasher choice. Section 3.5 quantifies the effect: `std`'s point-lookup cost changes 5× when the hasher is swapped, and the top three conventional tables become indistinguishable. Use the `same-hasher` groups for table-vs-table conclusions and the out-of-the-box groups for "what you get if you just use the crate's default".
5. **Semantic differences.** `indexmap`'s removal is `swap_remove` and does not preserve order; `horde`'s `clear` replaces the table instead of retaining capacity; `create` measures *empty* construction. These are real API differences, but they mean the same operation is not always the same work.
6. **Timer resolution at the fast end.** Several `clone` results are 1.7–5 ns (persistent maps) and `create` results are 0.3–1.6 ns per map. At that scale, a 10–20% difference is at the edge of Criterion's resolution and of per-iteration overhead. Treat rankings below ~10 ns as ties unless repeated.
7. **Concurrency model.** Concurrent benchmarks use 2 and 3 pinned threads and 10,000 operations per thread, with thread start/join outside the timed region. Results are not guaranteed to extrapolate to 8–64 threads, to NUMA machines, or to async runtimes (`scc`'s async API is not exercised). Also, concurrent `throughput` inserts draw from a shared pool of missing keys with replacement, so two threads can insert the same key — some "inserts" in concurrent mixed workloads are overwrites.
8. **No memory or allocation metrics.** Nothing here measures resident memory, allocation counts or reclamation latency, all of which matter for the persistent and epoch-based implementations.
9. **Conflict of interest disclosure.** `txmap` is authored by the organisation that maintains this benchmark suite (crate metadata: stock-trek). It is benchmarked with default settings and its `MutexPolicy` only, and it wins most concurrent groups. Its results should be reproduced independently before being treated as a vendor-neutral comparison.
10. **Excluded implementations.** `concread`, `concurrent-map` and `flurry` are absent (Section 5.20). "Fastest" in this report always means "fastest of the 19 implementations that were measured", not of the Rust ecosystem.

### 6.3 How to use these numbers

* For an implementation decision: pick the use case in Section 3.2, then read that operation's subsection in Section 2 for the variant closest to your key type and size, and check Section 4 before relying on a margin under ~10%.
* For a performance investigation: use the `same-hasher` groups to isolate table design from hashing (Section 3.5 lists the largest effects), and start with the group-level winners in Appendix C.
* For a regression check: record a baseline (`--save-baseline`), then compare like-for-like; the current `base/` directories cannot serve that purpose.

## Appendix B — Settings, Data Layout and Reproduction

**Criterion settings**

| Setting | Value |
|---|---|
| Criterion version | 0.8.2 |
| Warm-up | 1 s |
| Measurement | 2 s serial, 3 s concurrent (`contention`, `synchronization`, `throughput` with ≥2 threads) |
| Sampling mode | `Linear`, except `growth` and `clear-and-reuse` (`Flat`) |
| Samples per measurement | 100 (all 1,323 measurements) |
| Map size for point operations | 10,000 entries |
| Lookups/removals per iteration | 100 |
| Inserts per iteration (`insert`, `growth`, `clear-and-reuse`) | map size (1K–1M depending on the group) |
| Mixed operations per iteration | 10,000 per thread |
| Thread counts | 2 and 3 (`THREAD_COUNTS`); 1 for serial throughput |
| Get-or-insert hit ratio | 90% hits, 10% missing keys (20,000 ops per iteration) |

**Data layout**

```
target/criterion/<group>/<implementation>/new/estimates.json   # mean, median, median_abs_dev, std_dev, slope
target/criterion/<group>/<implementation>/new/sample.json      # 100 samples (iters, times)
target/criterion/<group>/<implementation>/new/benchmark.json   # group_id, function_id, throughput, full_id
```

Directory names replace the `/` separators of the logical group path with `_` (e.g. `growth_map-size-1M_same-hasher_u64`); in this report the logical path (`growth/map-size-1M/same-hasher/u64`) is used.

**Derived figures.** Per-map and per-operation costs (e.g. "1.72 ns per lookup", "0.31 ns per empty map") are computed by dividing the reported median by the number of operations in one iteration (100, 10,000, or 10,000 × threads). They are arithmetic derivations, not separate measurements.

**Reproduction**

```bash
cargo bench --bench <benchmark>            # one family, e.g. lookup_hit
cargo bench                                # everything (long: 1M growth and 100K iterate dominate)
cargo bench -- --save-baseline main        # record a baseline for future comparisons
```
