### 3.3 Trade-offs

- **Fastest single-threaded maps are not concurrent.** `rustc-hash`, `ahash`, `hashbrown`, `std` and `indexmap` support only `&mut self` mutation, so they cannot be shared across threads through this harness. The concurrent maps pay for their concurrency with a large fixed cost: at *Create*, `papaya` is ~2,000× and `txmap` ~2,400× the fastest empty-map construction.
- **Concurrency changes the winner, not just the constant.** `txmap` rules 2-thread throughput; `leapfrog` takes over the u64 synchronization and 3-thread contention cases; `scc` takes the 3-thread write-heavy cases. There is no single best concurrent map across all workloads.
- **Ordered maps are a category of their own.** `btreemap` and `crossbeam-skiplist` never reach within 10% of the fastest on any measured operation. They exist for ordering, not raw speed.
- **Persistence trades all-round speed for O(1) clone.** `rpds-hash-trie-map`, `imbl` and `immutable-chunkmap` win *Clone* by orders of magnitude, and they lose badly everywhere else (e.g. `imbl` is 27× the fastest at 100K *Iterate*).
- **Key type narrows the field.** `intmap` (integer keys) and `leapfrog` (`Copy` keys) cannot hold `String<32>` keys at all, which is why they are absent from every String variant.
- **The default hasher can swamp the data structure.** In `out-of-the-box` *Lookup hit* (u64), `std` (SipHash) is 7.3× slower than `intmap`; with a shared hasher `std` is within 1% of the leader. Always compare `same-hasher` rows when judging a data structure, and `out-of-the-box` rows when judging a complete map-plus-default-hasher package.

## 5. Implementation Limitations

The notes below come from the wrapper code in `src/maps/` and the benchmark configuration; they describe what each implementation can and cannot do in this harness.

- **`std` (`std::collections::HashMap`)** — `K: Hash + Eq`; a hasher can be supplied (`BenchMapNewWithHasher`). No `&self` insert/remove, so single-threaded only. Default `SipHash` is slow and is what the out-of-the-box numbers show.
- **`hashbrown::HashMap`** — Same shape as `std` but a different default hasher. `K: Hash + Eq`, configurable hasher, single-threaded only.
- **`ahash::AHashMap`** — `K: Hash + Eq`, configurable hasher, single-threaded only. `new()` is comparatively expensive because it builds a fresh random state.
- **`rustc_hash::FxHashMap`** — Fixed `FxHasher` — **no configurable hasher**. Single-threaded only. Fastest overall medians, but FxHasher is not collision-resistant.
- **`indexmap::IndexMap`** — `K: Hash + Eq`, configurable hasher, single-threaded only. Insertion-ordered; the dense vector makes iteration fast and offsets hash-table lookups.
- **`hashlink::LinkedHashMap`** — `K: Hash + Eq`, configurable hasher, single-threaded only. Maintains insertion order via a linked list, which costs on removal and iteration.
- **`std::collections::BTreeMap`** — `K: Ord` — **no hasher support** (it is not hash-based). No `&self` insert. Ordered, but never competitive on speed.
- **`intmap::IntMap`** — Requires `K: IntKey` — **integer keys only, no String keys, no custom hasher**. No `&self` mutation and no `get_or_insert` (`&self`) — only `&mut` operations. Fastest u64 lookup/remove out of the box.
- **`imbl::HashMap`** — Persistent HAMT. `K: Hash + Eq + Clone` for writes, configurable hasher. No `&self` insert; mutations return a new map and require `&mut`. Cheap clone, expensive read/write/iterate.
- **`rpds::HashTrieMap`** — Persistent HAMT using `RcK` (`Rc`), so it is not `Send`/`Sync`. Configurable hasher, no `&self` insert, no `get_or_insert`, no `clear`. All mutations are `&mut`. Cheapest clone measured.
- **`immutable_chunkmap::map::MapM`** — Requires `K: Clone + Ord` — it is an ordered copy-on-write map, so it has **no hasher support**; equality/order is by `Ord`. No `&self` insert; no `clear`. Only its empty construction is fast.
- **`dashmap::DashMap`** — `K: Hash + Eq`, `H: BuildHasher + Clone`. Interior mutability via `&self`, configurable hasher. Sharded `RwLock`; good write-heavy concurrency, mediocre single-threaded speed and expensive construction.
- **`papaya::HashMap`** — `K: Hash + Eq`, configurable hasher, `&self` mutation. Best read-only concurrency; expensive to construct and mid-pack on reads/writes.
- **`scc::HashMap`** — `K: Hash + Eq`, configurable hasher, `&self` mutation. Strong at 3-thread write-heavy throughput; some of the highest variance in the String synchronization groups.
- **`starshard::ShardedHashMap`** — Requires `K: Clone + Hash + Eq + Send + Sync` and `V: Clone + Send + Sync` — the strictest bounds of any map here. Configurable hasher, `&self` mutation. No benchmark win; consistently the slowest concurrent option.
- **`leapfrog::LeapMap`** — Requires `K: Eq + Hash + Copy` (so **no `String` keys**) and `V: Value`. Configurable hasher, `&self` mutation, but no `Clone`. Wins concurrent u64 synchronization and contention; loses badly on single-threaded lookup and construction.
- **`crossbeam_skiplist::SkipMap`** — Requires `K: Ord + Send + 'static` and `Send` values; **no hasher support and no `Clone`**. **The only ordered map with `&self` mutation**, so the only ordered map usable in concurrent groups. Consistently slow.
- **`horde::SyncTable`** — Configurable hasher. The wrapper exposes only `&mut` insert/remove and uses `horde::collect::pin` for reads, so it cannot participate in concurrent groups even though the underlying map is concurrent. No `BenchMapInsert`/`BenchMapRemove` (`&self`).
- **`txmap::TxMap`** — `K: Hash + Eq`, configurable hasher, `&self` mutation. Best concurrent throughput and mixed contention; expensive construction and slow when used single-threaded.

**Cross-cutting limitations.**

- Only maps implementing `BenchMapNewWithHasher` can be measured in `same-hasher` groups: `btreemap`, `crossbeam-skiplist`, `immutable-chunkmap`, `intmap` and `rustc-hash` are excluded, so they cannot be compared on equal-hasher footing.
- Only maps with `&self` mutation participate in the concurrent groups (`throughput` threads ≥ 2, `contention`, `synchronization`): `crossbeam-skiplist`, `dashmap`, `leapfrog`, `papaya`, `scc`, `starshard` and `txmap`. `horde` is excluded despite being concurrent.
- `intmap` and `leapfrog` cannot be benchmarked with `String` keys at all; all other 17 implementations were.
- No benchmark measures memory consumption, allocator behaviour, iteration order guarantees, or correctness under concurrent modification — only wall-clock timing.

## 6. Recommendations and Follow-up

### 6.1 Implementations and benchmarks that need more investigation

- **`horde` is the biggest coverage gap.** It is a concurrent map, but the wrapper implements only the `&mut self` mutation traits, so it is missing from every concurrent group. Adding `BenchMapInsert` / `BenchMapRemove` via `horde::collect::pin` would make the concurrent comparison complete.
- **Concurrent groups have no `same-hasher` variant.** All concurrent results (`throughput` threads ≥ 2, `contention`, `synchronization`) compare each map's *default-hasher package*, and those defaults differ (`starshard` ships `FxBuildHasher`, others ship their own). A shared-hasher concurrent variant is needed before attributing those differences to the map design rather than the hasher.
- **The three excluded concurrent maps should be re-confirmed.** `concread`, `flurry` and `concurrent_map` were dropped as "too slow" (or not `Sync`). `flurry` in particular is a widely used Java-style concurrent map; measuring it, even if slow, would complete the picture. A quick sanity run with a reduced `OP_COUNT` would confirm the exclusion.
- **The ordered maps are only measured on hash-map workloads.** `btreemap` and `crossbeam-skiplist` exist to provide ordering, yet there is no range-scan or in-order-iteration benchmark. Their current numbers say "slower than hash maps", which is expected and not actionable.
- **The persistent maps are only exercised through `Clone`.** `imbl`, `immutable-chunkmap` and `rpds-hash-trie-map` are judged almost entirely on structural-sharing clone; there is no snapshot-plus-concurrent-write workload. `rpds` is `Rc`-based and therefore neither `Send` nor `Sync`, which should be called out wherever it is proposed.
- **Integer-keyed maps deserve their own comparison set.** `intmap` and `leapfrog` cannot hold `String` keys, so their strong integer-key results are diluted across the full table. A u64-only leaderboard would present them fairly.
- **No memory or allocation measurements exist.** All conclusions are wall-clock only. If footprint matters (embedded, many maps, memory-bound services), an allocation-count or peak-RSS benchmark is needed.

### 6.2 Measurement-quality issues that could affect conclusions

- **Concurrent String synchronization at 3 threads is the noisiest area** (`scc` and `dashmap` reach ~10% MAD). Re-run these groups with a longer measurement time and pinned CPUs before treating the 2nd/3rd-place ordering as final.
- **`Create` is dominated by hasher and shard setup, not data-structure work.** Because an empty map allocates no entries, the numbers mainly expose `RandomState` construction (`ahash`) and shard/lock setup (concurrent maps). It should not be read as a measure of general construction speed for populated maps.
- **Tiny batches are close to harness overhead.** `Create`, 1K `Clone` and 1K `Clone then write` times are in the single-digit-microsecond or even sub-microsecond range; Criterion's own overhead is a non-trivial fraction there. Higher iteration counts or larger batches would tighten them.
- **A few fast maps show occasional slow samples.** `rustc-hash` on `Create` (std_dev/median ≈ 36%) and `hashbrown`/`ahash` on 100K `Clone` (~18–19%) have high `std_dev` but low MAD, i.e. outliers rather than skew. Conclusions should rely on the median/MAD, which this report does.
- **Everything is one run on one machine.** There is no baseline and no repetition across hosts. Before selecting a map for production, re-measure on the target hardware with CPU frequency scaling and turbo disabled, and pin worker threads.

## 7. How to Read This Report

- Every figure is a Criterion `median.point_estimate` taken directly from `target/criterion/`. No values were interpolated, estimated or invented.
- "Fastest" always means the smallest median within the specific variant; "within 10%" is a strict `≤ 1.10×` test. A dash means no other implementation was that close.
- `same-hasher` groups isolate the map; `out-of-the-box` groups measure the map plus its shipped default hasher. Conclusions about the *data structure* should come from `same-hasher`; conclusions about a *ready-to-use map* should come from `out-of-the-box`.
- Concurrent results are sensitive to machine core count, scheduling and shared-key contention; treat them as directional and re-measure on the target hardware before committing.
