### 3.3 Trade-offs

- **leapfrog ↔ txmap:** the two dominant concurrent maps split the workload space cleanly. leapfrog wins reads and contention (its advantage grows with Zipfian skew: 1.39× → 2.42× over txmap); txmap wins writes and 2-thread throughput. In every concurrent group the winner is one of these two.
- **rustc-hash ↔ ahash/std/hashbrown:** rustc-hash wins when its cheap-but-weak Fx hasher is allowed; when the hasher is equalised, ahash/std/hashbrown win. rustc-hash also cannot take a custom hasher and is not DoS-hardened.
- **indexmap:** a different data layout (Vec-backed entries) makes iteration 2.4×–3.7× faster than every other map, at the cost of being mid-pack (1.2×–3.5× slower) for inserts, lookups and removes.
- **intmap:** integer-only keys buy the fastest u64 lookups/removes anywhere, but the type restriction and lack of concurrency limit its applicability.
- **Persistent maps (rpds, imbl, immutable-chunkmap):** O(1) clone (1.4–4 ns) but ~4×–30× slower writes, and copy-on-write (clone-then-write) is 10×–30× slower than rustc-hash. immutable-chunkmap additionally has the cheapest empty construction (2.7 µs vs 5.5 µs for the next best).
- **std is never fastest for single-key ops** but is consistently within a few percent of the winner (within 10% in 14 of 60 groups) — a safe default.

### 3.4 Consistently close contenders

**std** (within 10% in 14 groups) and **hashbrown** (12 groups) and **ahash** (20 groups) are the "always in the hunt" implementations. Notably, **ahash** is within 10% of the fastest in a third of all benchmark groups. Among concurrent maps, **txmap and leapfrog** are within 10% of each other in 5 of the 17 concurrent groups and are the top-2 in nearly all of them.

- **dashmap, papaya, crossbeam-skiplist** show 15–30% rel. std_dev in some concurrent groups (get-or-insert threads-2/3, contention Zipfian(2.0)).
- rpds-hash-trie-map shows high *relative* MAD on `clone` (~7–11%) but on an absolute 1.4 ns measurement with ~0.1–0.2 ns MAD — this is timer-resolution noise on an effectively constant O(1) operation, not a real instability.

The multithreaded groups account for most of the flagged variance, which is expected (CPU scheduling, pinning, cache interference). Median-based ranking is robust to this, but the margins in several concurrent wins are within the noise band, so the ordering at the top should be treated as indicative rather than exact.

## 5. Implementation Limitations (from `src/maps/` wrappers)

Per-wrapper findings; trait bounds and missing traits are exactly as implemented in the harness.

- **ahash** (`ahash_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `V: Clone` for reads/clone/get-or-insert; `H: BuildHasher` (+ `Default`/`Clone` where needed).
  - Custom hasher: yes. Full trait coverage: clone, iter, get-or-insert, remove, clear.
  - Default hasher is `ahash::RandomState` (randomised; DoS-resistant).

- **btreemap** (`btreemap_benchmap.rs`)
  - Bounds: `K: Ord` (no hashing); `V: Clone` for reads.
  - Custom hasher: **no** (not applicable). No clone-then-write/clear restriction — all traits present (incl. clear).
  - Ordered map; only implementation in the suite with sorted iteration.

- **concread** (`concread_benchmap.rs`)
  - **Not benchmarked** (excluded as "too slow" in bench sources).
  - Bounds: `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static` — heavy bounds.
  - No `Clone` impl (so not eligible for clone benchmarks); does implement get-or-insert, insert, remove, iter, clear via read/write transaction handles.

- **concurrent-map** (`concurrent_map_benchmap.rs`)
  - Bounds: `K: 'static + Clone + Minimum + Send + Sync` (crate-specific `Minimum` trait, not `Ord`), `V: 'static + Clone + Send + Sync`.
  - Custom hasher: **no**. `BenchMapMutClear`: **not implemented** (excluded from clear-and-reuse).
  - **Ergonomically unusual:** the crate's `ConcurrentMap` is `Send` but not `Sync` (EBR state in a `RefCell`), so the wrapper works around it with a `Mutex`-guarded master map and thread-local clones keyed by a per-instance token; each thread re-clones the master once per iteration. `get_or_insert` is emulated as get-then-insert (no entry API).
  - Highest per-instance overhead of the concurrent maps (6 ms create).

- **crossbeam-skiplist** (`crossbeam_skiplist_benchmap.rs`)
  - Bounds: `K: Ord` for reads/iter; `K: Ord + Send + 'static`, `V: Clone/Send + 'static` for writes/removes.
  - Custom hasher: **no** (ordered structure). `BenchMapClone`: **not implemented** (excluded from clone benchmarks). Has clear.
  - Skiplist: ordered keys, lock-free reads; slowest large-map growth (505 ms @ 1M).

- **dashmap** (`dashmap_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `H: BuildHasher + Clone`; `V: Clone` only for get_cloned/get_or_insert/clone.
  - Custom hasher: yes. Full traits (clone, clear, iter, remove, entry).
  - Sharded design; `clone_map` is a deep copy. No per-map configuration of shard count in wrapper.

- **flurry** (`flurry_benchmap.rs`)
  - **Not benchmarked** (excluded as "too slow" — creates a `seize::Collector` per map).
  - Bounds: `K: Sync + Send + Clone + Hash + Ord` (note the extra `Ord`), `V: Sync + Send + Clone` — notably **requires `Ord` keys** and `Sync + Send` on both K and V.
  - Custom hasher: yes; `pin()`-based API (pin guard required for every op).

- **hashbrown** (`hashbrown_benchmap.rs`)
  - Bounds: `K: Hash + Eq` for lookups/inserts; `H: BuildHasher`; `V: Clone` only where values are returned by value.
  - Custom hasher: yes. Full trait coverage.
  - Same SwissTable algorithm as `std::HashMap` (which wraps hashbrown) with a cheaper default `DefaultHashBuilder` than `RandomState`.

- **hashlink** (`hashlink_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for reads.
  - Custom hasher: yes. Full trait coverage.
  - `LinkedHashMap`: insertion order preserved via a linked list; iteration is ~2.4× slower than indexmap at scale.

- **horde** (`horde_benchmap.rs`)
  - Bounds: `K: Clone + Hash + Eq` for writes, `K: Hash + Eq` for reads; `V: Clone`; `H: BuildHasher`.
  - Custom hasher: yes. Full traits incl. clone and clear (clear implemented via `replace` with an empty iterator).
  - `pin()`-based reads; `get_or_insert` is emulated as read-then-write (not atomic entry API).

- **imbl** (`imbl_benchmap.rs`)
  - Bounds: `K: Hash + Eq` for reads, `+ Clone` for writes; `V: Clone`; `H: BuildHasher + Clone`.
  - Custom hasher: yes. Full traits incl. clear.
  - Persistent (immutable) hash map: `clone` is O(1) structural sharing (~4 ns) but writes are copy-on-write and ~4×–30× slower than mutable maps.

- **immutable-chunkmap** (`immutable_chunkmap_benchmap.rs`)
  - Bounds: `K: Clone + Ord` (ordered — no hashing), `V: Clone`.
  - Custom hasher: **no** (ordered). `BenchMapMutClear`: **not implemented** (excluded from clear-and-reuse).
  - Persistent ordered chunked map; cheapest empty construction (2.7 µs); clone O(1) (~3.6 ns); writes slow (~13× slower than rustc-hash at 1M growth).

- **indexmap** (`indexmap_benchmap.rs`)
  - Bounds: `K: Hash + Eq` for lookups; `H: BuildHasher`; `V: Clone` where returned.
  - Custom hasher: yes. Full trait coverage.
  - Vec-backed entries give the fastest iteration in the suite; `remove` uses `swap_remove` (order changes, but O(1) removal).

- **intmap** (`intmap_benchmap.rs`)
  - Bounds: `K: IntKey` (integer keys only — **no general `Hash`/`Eq` key support**).
  - Custom hasher: **no** (not applicable — keys hash to themselves).
  - Full traits (clone, iter, remove, clear) but **no concurrent variants**; `V` is unconstrained for most ops.
  - Fastest u64 lookups/removes; cannot hold string or arbitrary keys.

- **leapfrog** (`leapfrog_benchmap.rs`)
  - Bounds: **`K: Eq + Hash + Copy`** (keys must be `Copy`!) and **`V: leapfrog::Value`** (a crate trait with its own requirements) — the most restrictive bounds in the suite.
  - Custom hasher: yes. `BenchMapClone`: **not implemented** (excluded from clone benchmarks). `BenchMapMutClear`: **not implemented** (excluded from clear-and-reuse).
  - Default hasher is `DefaultHasher`-based (`BuildHasherDefault<DefaultHasher>`), used for out-of-the-box concurrent groups.
  - `get_or_insert` uses `try_insert` (returns existing or inserts default).

- **papaya** (`papaya_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for reads.
  - Custom hasher: yes. Full traits incl. clone and clear.
  - `pin()`-based API — every operation requires a pin guard (epoch protection); 10.3 ms create (per-map reclamation infrastructure).

- **rpds-hash-trie-map** (`rpds_benchmap.rs`)
  - Bounds: `K: Eq + Hash`; `H: BuildHasher + Clone`; `V: Clone` where returned.
  - Custom hasher: yes. `BenchMapMutClear`: **not implemented** (excluded from clear-and-reuse).
  - Persistent hash trie: clone is O(1) (~1.4 ns) via `Rc`-based structural sharing; `get_or_insert` emulated as get-then-insert; writes 7×–25× slower than mutable maps.
  - **Caution:** uses `archery::RcK` (single-threaded reference counting), so `Send + Sync` sharing of clones is not provided by this wrapper.

- **rustc-hash** (`rustc_hash_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; no `V: Clone` requirement for most ops.
  - Custom hasher: **no** — Fx hasher is fixed (`BenchMapNewWithHasher` not implemented; excluded from all same-hasher groups).
  - Full traits incl. clear. Fx is a **fast but non-cryptographic, collision-prone hasher** (DoS risk on untrusted keys).

- **scc** (`scc_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for reads.
  - Custom hasher: yes. Full traits incl. clone and clear.
  - Concurrent hash map with `*_sync` API in the wrapper.

- **starshard** (`starshard_benchmap.rs`)
  - Bounds: `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync` — requires `Send + Sync` on keys and values.
  - Custom hasher: yes. Full traits incl. clone and clear.
  - Hard-coded to **8 shards** in the wrapper (`with_shards_and_hasher(8, …)`); shard count not configurable per benchmark.
  - Default hasher `rustc_hash::FxBuildHasher` (fast, not DoS-hardened).

- **std** (`std_benchmap.rs`)
  - Bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` where returned.
  - Custom hasher: yes. Full trait coverage.
  - Default `RandomState` (SipHash; DoS-resistant but slower than Fx/ahash on small keys).

- **txmap** (`txmap_benchmap.rs`)
  - Bounds: `K: Hash + Eq` (+ `Clone` for get_or_insert); `H: BuildHasher`.
  - Custom hasher: yes. Full traits incl. clone and clear.
  - `MutexPolicy` locking; `get_or_insert` uses `get_with_or_insert`. 7.2 ms create (per-map infrastructure).

### Benchmark-coverage gaps (not a limitation of the maps themselves)

- `concread` and `flurry` were excluded as "too slow" — no measurements exist.
- `crossbeam-skiplist` and `leapfrog` have no `Clone`; `concurrent-map`, `immutable-chunkmap`, `leapfrog`, `rpds-hash-trie-map` have no `clear`; `btreemap`, `concurrent-map`, `crossbeam-skiplist`, `immutable-chunkmap`, `intmap`, `rustc-hash` have no custom-hasher support. These are absent from the respective benchmark groups, so cross-group comparisons for those operations must account for the differing participant sets.

## 6. Recommendations

### Further investigation

1. **Re-verify the leapfrog `get-or-insert threads-3` win** (rel. std_dev ≈ 38%): it beats txmap by 1.19×, but the noise band is comparable to the margin. Rerun with longer measurement time or more samples before treating it as a real advantage.
2. **Re-verify rustc-hash's `throughput-1-thread balanced` win** (rel. std_dev ≈ 15%, rel. MAD ≈ 12%) — the headline serial result sits on noisy data. Its clear-and-reuse/growth wins (6–7% MAD) are more trustworthy.
3. **Boundary-tie groups** (ratio 1.09–1.10×) should be treated as ties, not wins: `insert out-of-the-box` ahash (1.09×), `key-sensitivity u64` hashlink (1.10×), `key-sensitivity String_128` indexmap (1.10×), `throughput-1 balanced` ahash (1.10×).
4. **Persistent-map clone results** (`rpds` ~1.4 ns, `immutable-chunkmap` ~3.6 ns, `imbl` ~4 ns) sit at the timer-resolution floor; use the `clone-then-write` results for the true copy cost, and consider a memory/allocations profile for these maps (structural sharing trades time for memory).
5. **Add `same-hasher` variants for the serial throughput family** (`throughput-1-thread`) — currently the only serial family without a controlled-hasher run, which makes it impossible to separate Fx-hash advantage from data-structure advantage there.

### Measurement-quality caveats

- **No baseline data**: only current absolute measurements exist; nothing can be said about regressions or improvements over time.
- **Short measurement window** (2 s, 1 s warm-up) for multithreaded groups, which dominate the high-variance flags; medians are robust, but top-of-table orderings in concurrent groups have margins comparable to the noise.
- **Participant sets differ per group** (hasher-capable, clone-capable, clear-capable, concurrent-only); "fastest" claims are only meaningful within the participants of that group.
- `lookup-hit`/`key-sensitivity` probe only 100 keys in a 10,000-entry map, so those numbers reflect a cache-resident hot-set rather than cold random access.
- Values reported are per-iteration wall time for the whole workload (e.g. 10,000 ops); throughput scaling is not shown per-op here but the rankings are unaffected.

### Bottom line

For serial workloads, **rustc-hash** (defaults) and **ahash** (controlled hasher) lead, with **hashbrown** and **std** as safe close seconds. For concurrent workloads, choose **leapfrog** for read/contention-heavy and **txmap** for write-heavy; they are the clear top-2. **indexmap** (iteration), **intmap** (integer lookups) and the **persistent maps** (O(1) copy) are the specialist choices. The headline serial and some concurrent wins carry meaningful measurement noise — confirm with longer runs before making final library decisions.
