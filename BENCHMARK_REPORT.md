| Map pool clear-and-reuse | **rustc-hash** oob; **ahash/std/hashbrown** with common hasher |
| Build-from-empty (growth) | **rustc-hash** oob; **indexmap** for String with common hasher |
| Remove-heavy workloads | **horde** (same-hasher) / rustc-hash, intmap (u64 oob) |

### 3.3 Trade-offs

- **The concurrency/seriality split is stark.** txmap, the dominant concurrent implementation, is ~1.3× slower than rustc-hash in serial String throughput but 1.9–3.9× on u64 (and 3.4× slower than intmap on u64 lookup-hit) yet 1.1–1.6× *ahead* of its nearest concurrent rival under contention (dashmap/scc/leapfrog). Concurrent maps as a class are 3–40× slower than serial maps on single-threaded u64 lookups (dashmap ~10×, scc ~15×, crossbeam-skiplist/concurrent-map ~37–39×).
- **Hashing cost dominates serial results.** std loses out-of-the-box (SipHash) but ties with ahash/hashbrown once a common hasher is used. rustc-hash and ahash win because their hashers are fast, not because the map structure is superior — in every same-hasher serial benchmark the open-addressing hash maps are within a few percent of each other.
- **`indexmap` trades lookups for iteration.** It is 2.8–3.4× faster at iteration and often best at String insert/growth, but 1.2–1.8× slower than hashbrown at random lookups (its extra indirection for order maintenance).
- **Persistent maps are incomparable on clone**: rpds/imbl/immutable-chunkmap are 4–5 orders of magnitude faster at *cloning* (refcount bump) but their COW writes make them slowest on clone-then-write and growth.
- **intmap wins u64 lookups** by skipping hashing entirely (integer keys used directly), but cannot be used with String keys or custom hashers.
- **leapfrog is the only implementation that beats txmap** — and only on u64 hot spots (Zipfian, write-heavy). It requires `K: Copy`, so it cannot handle String keys.

### 3.4 Consistently close implementations

- **ahash, hashbrown and std** are the most consistently close *serial* implementations: with a common hasher they are within ~3% of each other in nearly every read/write benchmark (hashbrown is within 10% of the fastest in 20/64 configs, ahash 24/64).
- **hashlink** is never fastest but lands within 10% in 5 configs (u64 same-hasher lookups).
- **dashmap and scc** are the most consistently close *concurrent* alternatives to txmap (dashmap within 10% in 4 configs, scc in 3), typically 1.5–2× behind txmap.
- **leapfrog** is within 10% of the fastest in 11 configs — all u64 concurrent ones.

### 4.2 Noisy fast implementations

Several *winners* have unusually noisy measurements, so their margins should be read with caution:

- **ahash** — clone 100K has 27% std_dev/median (63.5 µs ± 17 µs); its clone-then-write results are also noisy.
- **horde** — wins remove (same-hasher u64, 730 ns) with 14.3% std_dev/median; the remove win is real but the margin is uncertain.
- **leapfrog** — remove same-hasher u64 (842 ns) has 17.9% std_dev; iterate 10K same-hasher 33% std_dev; synchronization results carry 8–12% std_dev.
- **rpds-hash-trie-map** — iterate 100K (both hasher modes) shows 12–14% MAD and 12% std_dev; the sub-2 ns clone numbers carry 13.5% std_dev (absolute noise is tiny).
- **txmap** — despite being the headline winner, its own measurements are generally *stable* (mean MAD ratio 1.4%, worst 10.7% at clone-then-write 1K, 11.5% std_dev at sync 3t u64 write-majority).
- **concurrent-map** — the most consistently noisy implementation (20.6% MAD at clone-then-write 1K, ~19–30% std_dev on several lookups). Its thread-local clone wrapper (§5) plausibly contributes.

## 5. Implementation Limitations (from `src/maps/` wrapper code)

- **ahash** — requires `K: Hash + Eq`; `V: Clone` for get/get-or-insert; mutation needs `&mut` (no interior mutability); hasher configurable. No restrictions beyond the trait set.
- **btreemap** — requires `K: Ord` (no hashing at all, hence no custom hasher and absent from all same-hasher variants); mutation via `&mut`; iteration is in sorted order.
- **concread** — `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`; interior-mutable via write-transaction/commit; no custom hasher. **Excluded from every benchmark** in the harness (“too slow”).
- **concurrent-map** — heaviest bounds: `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`. The crate's `ConcurrentMap` is `Send` but **not `Sync`**; the wrapper keeps a master map behind a `Mutex` and lazily clones it into a thread-local once per iteration (type-erased `Box<dyn Any>`). This per-iteration clone + type-erasure overhead is structural and penalizes it in every concurrent benchmark (it is consistently the slowest or near-slowest). No custom hasher. No `clear`, no entry/get-or-insert API.
- **crossbeam-skiplist** — requires `K: Ord` (ordered); no custom hasher; interior-mutable; **no `Clone`** (absent from clone/clone-then-write). Requires `Send + 'static` for insert/remove/get-or-insert.
- **dashmap** — requires `K: Hash + Eq`, `H: BuildHasher + Clone`; interior-mutable; hasher configurable. Full coverage in all benchmark categories.
- **flurry** — requires `K: Sync + Send + Clone + Hash + **Ord**`, `V: Sync + Send + Clone` (the `Ord` bound is unusual for a hash map); interior-mutable; hasher configurable. **Excluded from every benchmark** (“too slow”; per-map `seize::Collector` in create).
- **hashbrown** — requires `K: Hash + Eq` for operations; hasher configurable; mutation via `&mut`. No restrictions beyond the trait set.
- **hashlink** — requires `K: Hash + Eq`; hasher configurable; mutation via `&mut`; maintains insertion order (slight per-entry overhead vs. hashbrown).
- **horde** — requires `K: Hash + Eq`, `V: Clone` for get/remove; writes go through `write()` and require `&mut` (not interior-mutable); **no entry/get-or-insert API** (absent from get-or-insert). Hasher configurable.
- **imbl** — persistent; requires `K: Hash + Eq + Clone`, `V: Clone`, `H: BuildHasher + Clone`; mutation via `&mut` (COW). Insert/get-or-insert/remove all pay the persistent-merge cost.
- **immutable-chunkmap** — persistent; requires `K: Clone + Ord` (ordered), `V: Clone`; no custom hasher (absent from same-hasher); **no `clear`** (absent from clear-and-reuse); no entry API. `create` result reflects a shared empty structure (O(1) `new`).
- **indexmap** — requires `K: Hash + Eq`; hasher configurable; mutation via `&mut`; `remove` uses `swap_remove` (changes iteration order — semantically different from other maps). Iteration is contiguous and cache-friendly.
- **intmap** — **integer keys only** (`K: IntKey`; absent from all String variants); no custom hasher; no get-or-insert at `&self`; mutation via `&mut`. Keys are used directly as hashes, so there is no hashing cost.
- **leapfrog** — requires `K: Eq + Hash + **Copy**` (absent from all String variants) and `V: leapfrog::Value`; hasher configurable; interior-mutable (`&self` insert/remove); **no `Clone`** (absent from clone) and **no `clear`** (absent from clear-and-reuse).
- **papaya** — requires `K: Hash + Eq`, `V: Clone` for get/remove; interior-mutable via `pin()`; hasher configurable. Full coverage.
- **rpds-hash-trie-map** — persistent (`HashTrieMap` with `archery::RcK`); requires `K: Eq + Hash`, `H: BuildHasher + Clone`; mutation via `&mut` (COW; `insert_mut`/`remove_mut`); **no `clear`** and **no entry/get-or-insert API**. `clone` is O(1).
- **rustc-hash** — requires `K: Hash + Eq`; **fixed FxHasher, no custom hasher** (absent from all same-hasher variants); mutation via `&mut`. FxHash is fast but not DoS-resistant.
- **scc** — requires `K: Hash + Eq`; hasher configurable; interior-mutable (`read_sync`/`entry_sync`/`upsert_sync`/`remove_sync`). Full coverage.
- **starshard** — requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, hasher `Clone + Send + Sync`; interior-mutable; wrapper hard-codes **8 shards**. Full coverage.
- **std** — requires `K: Hash + Eq`; default hasher `RandomState` (SipHash-1-3) — the main reason it loses out-of-the-box; hasher configurable; mutation via `&mut`.
- **txmap** — requires `K: Hash + Eq` (+ `Clone` for get-or-insert), `V: Clone` for get; hasher configurable; interior-mutable; uses `txmap::MutexPolicy` (a configurable choice, fixed in the wrapper). Full coverage.

## 6. Recommendations

### 6.1 Further investigation

1. **txmap's concurrent dominance should be validated before adoption.** It wins 38/112 configs — every multi-threaded benchmark except a handful — with stable measurements (MAD ≈ 1.4%). Its transactional design (per-thread transaction cache, deferred writes) is the likely cause, but: (a) only 2–3 threads were tested; scaling to 4–16 threads and larger maps (1M+) is untested; (b) its serial cost (1.25–3.9× rustc-hash on 1-thread throughput, worst for u64 keys) and String get-or-insert cost (2.2–2.7×) should be weighed for mixed workloads. A dedicated scaling study (thread sweep × size sweep) is warranted.
2. **leapfrog vs. txmap on u64 hot spots.** leapfrog beat txmap on Zipfian-contended u64 keys and several single-key write mixes (up to 1.98×). This suggests fine-grained locking wins when contention concentrates on few cache lines. Worth a focused study on key distribution shape, plus confirming its `K: Copy` limitation is acceptable.
3. **horde's remove win (same-hasher)** — 1.48× faster than the next best with a common hasher, but the measurement is noisy (14.3% std_dev). Re-run with longer measurement time to confirm.
4. **indexmap's String growth/insert edge** at 1M entries (1.37× faster than hashbrown) plus its 3× iteration advantage suggests insertion-ordered contiguous maps deserve a look for String-heavy workloads with iteration.
5. **intmap** — skipping hashing entirely is a big win for u64 lookups (fastest on both hit and miss). If the harness can be extended to `usize`/`u32` key workloads, intmap should be evaluated there.
6. **concread and flurry are absent from all results.** If they are candidates, they need their own benchmarks rather than the blanket “too slow” exclusion.

### 6.2 Measurement quality issues

- **No baseline/change data.** All comparisons are absolute; regression/change analysis is not possible from this data.
- **Single run set.** Each benchmark ran once (Criterion default sampling). High-variance items in §4 should be re-measured before drawing conclusions (esp. clone-then-write for concurrent-map/dashmap/intmap, imbl growth, ahash clone 100K, leapfrog iterate/remove).
- **The `clone` benchmark mixes incomparable operations**: persistent maps do an O(1) refcount bump while mutable maps deep-copy. The 4–5 order-of-magnitude gaps are structural, not “speed”.
- **`create` for persistent maps** measures a shared-empty-structure clone (~0.3 ns per construction), not eager allocation cost; cross-implementation create comparisons are only meaningful among eagerly-allocating maps.
- **The concurrent-map wrapper adds per-iteration setup** (thread-local clone + type erasure), so its numbers understate the raw crate's steady-state performance; conversely its `Sync`-ness is obtained through serialized master cloning.
- **`indexmap`'s `swap_remove`** means its remove results are not semantically identical to other maps (order-destroying removal).
- Concurrent benchmarks were run with a 3 s measurement time vs. 2 s for serial; fine, but noise remains higher for synchronization workloads (all-threads-single-key is inherently bursty).
- The out-of-the-box vs. same-hasher split means implementations with fixed hashers (btreemap, rustc-hash, intmap, …) simply cannot be compared under the hasher-neutralized condition — their absence from those 32 configs should not be read as poor performance.
