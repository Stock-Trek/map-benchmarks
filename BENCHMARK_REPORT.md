### 1.3 Measurement methodology notes

- All timings are **median point estimates** (`median.point_estimate`) from each benchmark's `new/estimates.json`, in nanoseconds. `new/` and `base/` contain identical values (same run), so no change data exists; all comparisons are between implementations within the same benchmark group.
- A benchmark iteration performs the whole workload described above (e.g., inserting all N keys). Throughput is reported by Criterion as elements per iteration, but the values in this report are total wall-clock time per iteration.
- Criterion config: 1 s warm-up, 2 s measurement per benchmark. All map values are `u64`, keys are `u64` except `key-sensitivity`. `black_box` is used to defeat optimization; mutating benchmarks use `iter_batched` with per-iteration setup so each iteration starts from a fresh map. Concurrent worker threads are spawned once and pinned to CPUs outside the timed region.
- A "close contender" is any implementation whose median time is **within 10%** of the group's fastest median. A "—" entry means the fastest is clearly ahead (no implementation within 10%).

| indexmap | 6 (5%) | 9 (7%) | All 6 iterate benchmarks, by a large margin |
| std | 5 (4%) | 17 (14%) | Same-hasher lookups/inserts (competitive once SipHash is replaced with ahash) |
| horde | 4 (3%) | 6 (5%) | All 3 same-hasher remove benchmarks + insert(100K same-hasher) |
| rpds-hash-trie-map | 3 (2%) | 3 (2%) | All 3 clone benchmarks — O(1) structural-sharing clone |
| hashlink | 3 (2%) | 9 (7%) | Lookup-miss (same-hasher); consistently within 10% on misses |
| scc | 1 (1%) | 2 (2%) | get-or-insert 100K · 4 threads (a very noisy group) |
| immutable-chunkmap | 0 | 1 (1%) | Within 10% only on create |
| dashmap | 0 | 1 (1%) | Within 10% only on zipfian read-heavy 10K · 4 threads |
| crossbeam-skiplist | 0 | 0 | Never close to fastest |
| concurrent-map | 0 | 0 | Never close to fastest |
| imbl | 0 | 0 | Never close to fastest |
| papaya | 0 | 0 | Never close to fastest |
| starshard | 0 | 0 | Never close to fastest |
| btreemap | 0 | 0 | Never close to fastest |

### 3.2 Recommendations by use case

| Use case | Recommended implementation(s) |
|---|---|
| Single-threaded lookups / get-or-insert (serial) | rustc-hash (default hasher); ahash / hashbrown / std (when a robust hasher is needed) |
| Single-threaded bulk insert / build | rustc-hash; ahash / hashbrown / std / horde (same-hasher) |
| Single-threaded mixed workload (serial) | rustc-hash |
| Map pooling (clear-and-reuse) | ahash (or rustc-hash / std) |
| Iteration-heavy code | indexmap (fastest by far); hashlink (insertion order); btreemap (sorted order) |
| Removal-heavy code | horde (same-hasher); rustc-hash / hashbrown (out-of-the-box) |
| Snapshot / clone-heavy code | rpds-hash-trie-map (O(1) clone) |
| Concurrent, 2 threads, read-heavy / cache-entry | txmap |
| Concurrent, 3–4 threads, mixed / write-heavy, larger maps | leapfrog |
| Concurrent hot-key (zipfian) | txmap (2 threads) / leapfrog (3–4 threads) |
| Concurrent, robustness over peak speed | dashmap, scc, papaya, starshard (all slower in these tests but within 1–4× of txmap/leapfrog) |

### 3.3 Trade-offs between implementations

- **Serial vs concurrent is the biggest split.** `rustc-hash` wins every single-threaded group; `txmap`/`leapfrog` win every multi-threaded group. Neither family is competitive in the other's regime.
- **txmap vs leapfrog** is the main concurrent trade-off: txmap wins 2-thread workloads; leapfrog wins 3–4-thread and large-map workloads. They are within 10% of each other in many groups (see §4 — several of these comparisons sit inside high-variance groups, so the ordering at 4 threads should be treated cautiously).
- **indexmap's** contiguous storage gives a decisive iteration advantage at the cost of slower mutation (insert at 1,000 keys: 28 µs vs 23 µs for std) and O(1)-but-order-changing swap_remove semantics on removal (indexmap remove ≈ 5.1 µs at 100K vs 0.94 µs for hashbrown — 5.5× slower).
- **Persistent maps** (rpds, imbl, immutable-chunkmap) trade O(1) clone / cheap snapshots for much slower mutation and iteration; they never approach the fastest on write paths (rpds insert ≈ 95 µs at 1,000 keys vs 23 µs for rustc-hash, both out-of-the-box).
- **horde** is specialized: fastest remove and large same-hasher insert, but requires `&mut` for writes so it cannot participate in the shared-`&self` concurrent benchmarks, and its iterate (93 µs @100K) trails indexmap by 2.6×.
- **dashmap/scc/papaya/starshard** never win a group; papaya and starshard also show high variance. They are 1.5–4× slower than txmap/leapfrog in these concurrent workloads.

### 3.4 Consistently close implementations

- **leapfrog** — within 10% of the fastest in 38/124 groups (31%), the most of any implementation; it is either winning or very close in nearly every concurrent group.
- **txmap** — within 10% in 37/124 groups.
- **rustc-hash** — within 10% in 28/124 groups (all serial).
- **ahash / hashbrown** — within 10% in 21 groups each; hashbrown is within 10% of the fastest on all six lookup-miss groups and all six lookup-hit groups.
- **std** — within 10% in 17 groups, always in same-hasher serial groups (showing its default SipHash hasher, not its structure, is the bottleneck).

## 4. Stability

Method: a measurement is flagged as high-variance when `median_abs_dev / median > 0.10` or `std_dev / median > 0.25` (relative dispersion of the sample set around the median).

### 4.1 Summary

- **92 of 1,448 measurements (6.3%) are flagged.** Flags are heavily concentrated in the multi-threaded concurrent groups: leapfrog 17, scc 16, txmap 15, dashmap 13, papaya 10, starshard 6. The serial single-threaded groups are stable (rustc-hash 1 flag, hashbrown 1, std 1, ahash 2, indexmap 1).
- **Worst individual cases** (all 100,000-entry, 4-thread concurrent groups, or 100,000-entry persistent-map serial groups):
  - `zipfian read-heavy 100K · 4t` leapfrog: std/median = 2.35
  - `workload read-heavy 100K · 4t` leapfrog: std/median = 1.29
  - `workload balanced 100K · 4t` leapfrog: std/median = 1.12
  - `get-or-insert 100K · 4t` leapfrog: mad/median = 0.89
  - `workload read-heavy 100K · 1t` rpds: mad/median = 0.55 (persistent-map allocation noise)
  - `get-or-insert 100K · 4t` txmap: mad/median = 0.37

### 4.2 Noisy fast implementations (winners with unstable measurements)

These groups' **winning** implementation has suspiciously high dispersion, so the winner's margin should not be over-interpreted:

| Benchmark group | Winner | Median | mad/median | std/median |
|---|---|---|---|---|
| get-or-insert 10K · 4 threads | txmap | 950.7 µs | 0.182 | 0.176 |
| workload read-heavy 100K · 4 threads | leapfrog | 519.9 µs | 0.175 | **1.293** |
| clear-and-reuse same-hasher 10K | ahash | 125.4 µs | 0.174 | 0.141 |
| workload balanced 10K · 4 threads | txmap | 986.8 µs | 0.161 | 0.162 |
| workload read-heavy 10K · 4 threads | txmap | 882.6 µs | 0.161 | 0.186 |
| zipfian read-heavy 10K · 4 threads | txmap | 920.6 µs | 0.156 | 0.151 |
| workload balanced 10K · 1 thread | rustc-hash | 46.1 µs | 0.134 | 0.091 |
| zipfian write-heavy 10K · 4 threads | leapfrog | 1112.4 µs | 0.127 | 0.152 |
| workload read-heavy 1K · 4 threads | leapfrog | 493.4 µs | 0.119 | 0.668 |
| workload balanced 100K · 4 threads | leapfrog | 552.6 µs | 0.105 | 1.120 |

### 4.3 Interpretation

- The 4-thread concurrent benchmarks are the noisiest by far; pinning reduces but does not eliminate OS-scheduling / cache-contention jitter on the (shared CI) host. This is a measurement-environment artifact more than a map-behavior artifact, but it weakens every 4-thread ranking, especially the txmap↔leapfrog head-to-heads.
- The 100,000-entry workloads amplify both real (allocation, cache misses, GC/EBR reclamation) and environmental variance. Persistent maps (rpds) at 100K serial show MAD/median ≈ 0.5, consistent with structural-sharing allocation bursts.
- Stable winners (low variance AND fast) include: rustc-hash in all serial groups (except one borderline), indexmap in iterate, horde in same-hasher remove, and txmap/leapfrog in the 2–3-thread groups (mad/median mostly < 0.1).

## 5. Implementation Limitations (from `src/maps/` wrappers)

### ahash (`AhashBenchMap`)
- Trait bounds: `K: Hash + Eq`; `V: Clone` required for `get_cloned`, `get_or_insert`, `clone`; hasher `H: BuildHasher` (+ `Default` for `new`).
- Custom hasher supported → participates in both `out-of-the-box` and `same-hasher` groups.
- Default hasher is ahash's own `RandomState`; in `same-hasher` mode it uses the shared ahash hasher (home-field advantage).

### btreemap (`BTreeMapBenchMap`)
- Trait bounds: `K: Ord` (no hashing); `V: Clone`.
- No custom-hasher support → `out-of-the-box` groups only.
- Ordered iteration; O(log n) operations; never competitive with hash maps for hash-map workloads (never within 10%).

### concurrent-map (`ConcurrentMapBenchMap`)
- Trait bounds: `K: 'static + Clone + Minimum + Send + Sync`; `V: 'static + Clone + Send + Sync` (`Minimum` is concurrent-map's own marker trait).
- No custom hasher; no `clear()` → excluded from `clear-and-reuse`.
- `Send` but **not `Sync`** → cannot share `&ConcurrentMap` across threads → excluded from all concurrent multi-thread benchmarks.
- `get_or_insert` has no entry API and is emulated as get-then-insert (non-atomic; a race could insert twice).

### crossbeam-skiplist (`CrossbeamSkiplistBenchMap`)
- Trait bounds: `K: Ord + Send + 'static` (writes), `V: Clone + Send + 'static` (get/remove) or `V: Send + 'static` (insert).
- No custom hasher; not `Clone` → excluded from `clone`/`clone-then-write`.
- Lock-free ordered skiplist; consistently among the slowest in every family it participates in (iterate 100K ≈ 2.6 ms).

### dashmap (`DashMapBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher + Clone`; `V: Clone` for `get_cloned`/`get_or_insert`.
- Custom hasher supported → both groups.
- Concurrent; never won a group; within 10% once (zipfian read-heavy 10K · 4 threads).

### hashbrown (`HashbrownBenchMap`)
- Trait bounds: `K: Hash + Eq` for get/insert/remove; **no `V: Clone` bound** on insert/remove/iterate (only `get_cloned` needs it); `H: BuildHasher`.
- Custom hasher supported → both groups.
- Consistently near the top on lookups (within 10% in all 12 lookup groups).

### hashlink (`HashlinkBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for `get_cloned`.
- Custom hasher supported → both groups.
- LinkedHashMap: iteration preserves insertion order (slower iterate than indexmap but faster than most hashed maps).

### horde (`HordeBenchMap`)
- Trait bounds: `K: Clone + Hash + Eq` for insert; `V: Clone` for get/remove; `H: BuildHasher`.
- Custom hasher supported → both groups.
- Writes require `&mut self` (`write().insert(...)`); no shared-`&self` insert → excluded from concurrent shared-reference benchmarks.
- All access goes through EBR pinning (`horde::collect::pin`).
- `clear()` implemented as a table replace (`write().replace(empty)`), which is why `clear-and-reuse` does not benefit from capacity retention.
- Best-in-class for same-hasher removal.

### imbl (`ImblBenchMap`)
- Trait bounds: `K: Hash + Eq + Clone` for insert/get_or_insert; `V: Clone`; `H: BuildHasher + Clone`.
- Custom hasher supported → both groups.
- Persistent map with structural sharing; mutation requires `&mut`; default shared-pointer type is not `Send`/`Sync` → excluded from concurrent benchmarks.
- Never close to fastest on any benchmark.

### immutable-chunkmap (`ImmutableChunkMapBenchMap`)
- Trait bounds: `K: Clone + Ord`; `V: Clone`.
- No custom hasher → `out-of-the-box` only; no `clear()` → excluded from `clear-and-reuse`.
- Persistent `MapM` with COW (`insert_cow`, `remove_cow`, `get_or_insert_cow`); writes via `&mut`.
- Only competitive on `create` (empty-map creation is allocation-free and effectively ties rustc-hash).

### indexmap (`IndexMapBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for `get_cloned`.
- Custom hasher supported → both groups.
- Insertion-order iteration; contiguous entry storage → decisive iterate wins.
- `remove` uses `swap_remove` (O(1) but changes iteration order); slower inserts than plain hash maps.

### leapfrog (`LeapfrogBenchMap`)
- Trait bounds: `K: Eq + Hash + **Copy**`; `V: leapfrog::Value` (a restricted value trait — values must fit the open-addressing slot model); `H: BuildHasher + Default`.
- Custom hasher supported → both groups.
- No `Clone` → excluded from `clone`/`clone-then-write`; no `clear()` → excluded from `clear-and-reuse`.
- `K: Copy` excludes String keys → absent from `key-sensitivity` String groups.
- Concurrent get-or-insert via `try_insert`.

### papaya (`PapayaBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for `get_cloned`.
- Custom hasher supported → both groups.
- All operations go through `map.pin()` (hazard/epoch-based pinning per operation).
- Concurrent; never won a group; high variance in several 4-thread groups.

### rpds-hash-trie-map (`RpdsHashTrieMapBenchMap`)
- Trait bounds: `K: Eq + Hash`; `V: Clone`; `H: BuildHasher + Clone`; uses `archery::RcK` (reference-counted) pointer kind.
- Custom hasher supported → both groups.
- Persistent; `clone_map()` is O(1) (Rc bump, ~1.4 ns) — the source of its clone wins.
- Mutation via `insert_mut`/`remove_mut` (in-place COW); `get_or_insert` emulated as get-then-`insert_mut` (non-atomic).
- Default `RcK` pointer is not `Send`/`Sync` → excluded from concurrent benchmarks.
- No `clear()` → excluded from `clear-and-reuse`.

### rustc-hash (`RustCHashBenchMap`)
- Trait bounds: `K: Hash + Eq` for get/insert/remove; no bounds for `new`/iterate; `V: Clone` for `get_cloned`.
- **No custom-hasher support** (fixed `FxBuildHasher`) → `out-of-the-box` only.
- FxHash is very fast on small keys but is **not collision/DoS-resistant**; iteration is over raw buckets (arbitrary order).
- Fastest implementation in most out-of-the-box single-threaded groups (26 of 37; the exceptions are iteration, clone, and a few insert/lookup-miss/remove/clear-and-reuse groups where hashbrown/ahash/hashlink edge it out).

### scc (`SccBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher`; `V: Clone` for `get_cloned`.
- Custom hasher supported → both groups.
- All operations use `*_sync` APIs (`read_sync`, `entry_sync`, `upsert_sync`, `iter_sync`, `remove_sync`, `clear_sync`).
- Concurrent; one win (get-or-insert 100K · 4 threads) in a very noisy group; otherwise 1.5–2× behind txmap/leapfrog.

### starshard (`StarshardBenchMap`)
- Trait bounds: `K: Clone + Hash + Eq + Send + Sync`; `V: Clone + Send + Sync`; `H: BuildHasher + Clone + Send + Sync`.
- Custom hasher supported → both groups.
- Fixed 8 shards (`with_shards_and_hasher(8, …)`).
- Concurrent; never won; typically 2–6× slower than txmap/leapfrog in concurrent groups.

### std (`StdBenchMap`)
- Trait bounds: `K: Hash + Eq`; `H: BuildHasher` (+ `Default`); `V: Clone` for `get_cloned`.
- Custom hasher supported → both groups.
- Default `RandomState` (SipHash-1-3) is the main bottleneck out-of-the-box; with the shared ahash hasher std is competitive with ahash/hashbrown.
- Stable and predictable; within 10% in 17 groups.

### txmap (`TxMapBenchMap`)
- Trait bounds: `K: Hash + Eq`; `K: Clone + Hash + Eq` for `get_or_insert`; `V: Clone` for `get_cloned`; `H: BuildHasher`.
- Custom hasher supported → both groups.
- `TxMap` with `MutexPolicy` locking; built via `TxMapBuilder`.
- Concurrent; most-frequent overall winner (32 groups), dominant at 2 threads; shares the 3–4-thread wins with leapfrog.

### Excluded implementations
- **concread** — excluded everywhere ("too slow"); wrapper exists (`concread_benchmap.rs`) but is not used.
- **flurry** — excluded everywhere ("too slow"; also creates a `seize::Collector` per map, per `create.rs` comment); wrapper exists (`flurry_benchmap.rs`) but is not used.

## 6. Recommendations

### 6.1 Further investigation

1. **txmap vs leapfrog at 4 threads / 100K entries.** These are the two headline concurrent implementations, but their head-to-head at 4 threads sits inside the noisiest measurements (std/median up to 1.3–2.4). Re-run those specific groups with longer measurement time / more samples before treating the 4-thread ordering as fact.
2. **leapfrog's `V: Value` / `K: Copy` restrictions.** It wins many concurrent groups but only for Copy keys and word-sized values. Verify the win generalizes to reference types and heap values.
3. **horde's remove/insert strength.** Horde wins all same-hasher remove groups and large same-hasher insert, but requires `&mut` writes. Investigate whether a `&self` write API (or different pinning strategy) would extend its reach into concurrent workloads.
4. **scc's single win** (get-or-insert 100K · 4 threads) is in a group where the median itself is questionable (MAD/median ≈ 0.7–0.9 for several impls). Confirm before citing.
5. **rpds clone semantics.** The ~1.4 ns clone is O(1) structural sharing, not a deep copy. If a deep-copy semantic is what's wanted, rpds is not the answer; if snapshot semantics are wanted, it is ideal. This should be called out wherever these numbers are reused.
6. **Persistent-map variance at 100K** (rpds MAD/median ≈ 0.5 in workload 100K · 1 thread) suggests allocator/COW bursts; longer measurement time would firm these numbers.

### 6.2 Measurement quality issues that could affect conclusions

- **No baseline/change data**: `new/` and `base/` are identical (a single run), so all "wins" are absolute, same-run comparisons only. There is no signal about run-to-run stability across days or machines.
- **Shared-host noise in 4-thread groups**: threads are pinned, but the environment is clearly noisy at 4 threads. Treat all 4-thread rankings (especially margins < 10%) as provisional.
- **Short measurement window**: 1 s warm-up / 2 s measurement per benchmark on a busy host leaves few samples for the slowest 100K-entry concurrent groups, inflating MAD/std.
- **Hasher asymmetry**: `same-hasher` uses `ahash::RandomState` for every map — ahash benefits disproportionately, and maps with hasher-independent costs (e.g. horde, scc, leapfrog) are measured fairly, but `out-of-the-box` comparisons blend hasher quality with structure quality. Both views are provided and should be read together.
- **Iteration-order effects**: indexmap/hashlink/btreemap iterate in a deterministic order (and indexmap contiguously), while hashed maps iterate in arbitrary bucket order. The iterate benchmark therefore measures cache behavior as much as algorithmic iteration cost.
- **`get_or_insert` emulation**: concurrent-map and rpds lack a native entry API; their get-or-insert numbers include a non-atomic get-then-insert, which is both slower and semantically weaker (race could insert twice). Their get-or-insert results are not directly comparable to native-entry implementations.

### 6.3 Bottom line

- **Single-threaded code: use `rustc-hash`** when FxHash's collision weakness is acceptable; otherwise **`ahash` or `hashbrown`** (std is fine with a better hasher).
- **Concurrent code: use `txmap` for 2-thread/read-heavy workloads and `leapfrog` for 3–4-thread/larger workloads**; both are far ahead of dashmap/scc/papaya/starshard in these tests.
- **Specialized picks**: `indexmap` for iteration, `rpds` for O(1) snapshots, `horde` for removal-heavy same-hasher workloads, `btreemap` for sorted order.
