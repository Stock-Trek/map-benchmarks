### 3.3 Trade-offs (different implementations excel in different operations)

- **rustc-hash** is unbeatable serially but is absent from same-hasher and concurrent comparisons (no custom hasher, not concurrent). Its FxHasher is fast but not randomized/DoS-hardened.
- **txmap vs leapfrog** is the clearest trade-off: txmap wins nearly every 2-thread and large-map concurrent case; leapfrog wins write-heavy and small-map cases at 3–4 threads. **scc** is the consistent runner-up in both regimes.
- **indexmap** wins iteration by a wide margin but is mid-pack (1.7–4.4×) in mutation/lookup — an order-preserving index costs on writes.
- **horde** is the clear removal specialist (1.2–1.3× faster than any rival in same-hasher removal) and is also within 10% of the fastest on same-hasher inserts; elsewhere it is mid-pack, and its `SyncTable` requires `&mut`-style write access (excluded from concurrent benches).
- **Persistent maps (rpds, imbl, immutable-chunkmap)** have O(1) clone/create but are 5–60× slower at mutation and lookup — appropriate only when structural sharing/immutability is the actual requirement.

### 3.4 Consistently close across many operations

- **hashbrown** (within 10% in 20/94 groups) and **ahash** (20) and **std** (18) form a tight cluster in every serial same-hasher test; they are interchangeable there.
- **txmap** (26) and **leapfrog** (18) are the reliable concurrent contenders; **scc** is close behind (5 groups within 10%, never fastest but usually 2nd–4th).

## 5. Implementation Limitations (from `src/maps/` wrapper code)

Key trait bounds and ergonomic restrictions per implementation:

- **ahash** (`AhashBenchMap<K, V, H = RandomState>`): requires `K: Hash + Eq`, `V: Clone` (for `get_cloned`/`get_or_insert`), `H: BuildHasher`. Supports custom hasher. Not concurrent; no shared-reference mutation API.
- **btreemap** (`BTreeMapBenchMap<K, V>`): requires `K: Ord`. **No custom hasher** (excluded from all same-hasher groups). Not concurrent. No shared-reference mutation.
- **concread** (`ConcreadBenchMap`): requires `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`. **Never benchmarked** — commented out of every bench as "too slow". Also **no `Clone` impl** (excluded from clone).
- **concurrent-map** (`ConcurrentMapBenchMap`): requires `K: Clone + Minimum + Send + Sync`, `V: Clone + Send + Sync`. **`Send` but not `Sync`** — cannot share `&ConcurrentMap` across threads, so excluded from all concurrent benches. **No `clear()`** (excluded from clear-and-reuse). **No custom hasher** (excluded from same-hasher). `get_or_insert` is emulated as get-then-insert (no entry API).
- **crossbeam-skiplist** (`CrossbeamSkiplistBenchMap`): requires `K: Ord` (+ `Send + 'static` for writes). **No `Clone`** (excluded from clone). **No custom hasher**. Concurrent (SkipMap). Values must be `Clone` for `get_cloned`/`remove`.
- **dashmap** (`DashMapBenchMap<K, V, H = RandomState>`): `K: Hash + Eq`, `V: Clone` for `get_cloned`; `H: BuildHasher + Clone`. Supports custom hasher. Concurrent. `get_cloned`/`remove` clone values out of the map (required for the benchmark API).
- **flurry** (`FlurryBenchMap`): heavy bounds — `K: Sync + Send + Clone + Hash + Ord`, `V: Sync + Send (+ Clone)`. **Never benchmarked** — commented out everywhere as "too slow". Also creates a `seize::Collector` per map, which makes `create` expensive.
- **hashbrown** (`HashbrownBenchMap<K, V, H>`): `K: Hash + Eq` (plus `Clone` for `clone_map`). Supports custom hasher. Not concurrent. No shared-reference mutation.
- **hashlink** (`HashlinkBenchMap<K, V, H>`, `LinkedHashMap`): `K: Hash + Eq`; `H: BuildHasher`. Supports custom hasher. **Insertion-order iteration** — iteration is ~2–6× slower than indexmap because of the linked-list traversal. Not concurrent; mutation requires `&mut`.
- **horde** (`HordeBenchMap`, `SyncTable`): `K: Clone + Hash + Eq` for insert/get-or-insert, `V: Clone`. Supports custom hasher. `get_cloned`/`iter` must run inside `horde::collect::pin(...)`; `clear()` is implemented via `write().replace(empty)`. **Mutation requires `&mut`** (excluded from concurrent benches). Writes need `K: Clone`, reads only `Hash + Eq`.
- **imbl** (`ImblBenchMap<K, V, H = RandomState>`, persistent `GenericHashMap`): inserts require `K: Hash + Eq + Clone`, `V: Clone`. Supports custom hasher. **Persistent**; `Clone` is O(1) refcount. Mutation via `&mut` only (not usable in concurrent benches).
- **immutable-chunkmap** (`ImmutableChunkMapBenchMap`, `MapM`): requires `K: Clone + Ord`, `V: Clone`. **No custom hasher** (excluded from same-hasher). **No `clear()`** (excluded from clear-and-reuse). Persistent COW; all mutation goes through `_cow` methods.
- **indexmap** (`IndexMapBenchMap<K, V, H>`): `K: Hash + Eq`; `H: BuildHasher`. Supports custom hasher. **`remove` uses `swap_remove`** (order-changing, and different from `shift_remove` semantics). Not concurrent.
- **leapfrog** (`LeapfrogBenchMap<K, V, H>`): **requires `K: Eq + Hash + Copy` and `V: leapfrog::Value`** — the most restrictive key bound in the set (no `String` keys, no non-`Copy` keys). **No `Clone`** (excluded from clone). **No `clear()`** (excluded from clear-and-reuse). Supports custom hasher. Concurrent (used in concurrent benches).
- **papaya** (`PapayaBenchMap<K, V, H = RandomState>`): `K: Hash + Eq`, `V: Clone` (for `get_cloned`/`get_or_insert`/`remove`). Supports custom hasher. Concurrent; every op goes through `pin()` (epoch-style guard).
- **rpds** (`RpdsHashTrieMapBenchMap<K, V, H = RandomState>`, `HashTrieMap` with `archery::RcK`): `K: Eq + Hash`. Supports custom hasher. **Persistent**; mutation returns a new map, so the wrapper uses `insert_mut`/`remove_mut` and `get_or_insert`/`remove` are **emulated as get-then-mutate** (no entry API). Default `RcK` pointer kind is **not `Send`/`Sync`** (excluded from concurrent benches). **No `clear()`** (excluded from clear-and-reuse).
- **rustc-hash** (`RustCHashBenchMap`, `FxHashMap`): `K: Hash + Eq`. **No custom hasher** (excluded from same-hasher groups). FxHasher is not randomized — vulnerable to hash-flooding attacks. Not concurrent.
- **scc** (`SccBenchMap<K, V, H = RandomState>`): `K: Hash + Eq`, `V: Clone`. Supports custom hasher. Concurrent; all operations use the `*_sync` variants (`read_sync`, `upsert_sync`, `entry_sync`, `remove_sync`, `iter_sync`, `clear_sync`).
- **starshard** (`StarshardBenchMap<K, V, H = FxBuildHasher>`): requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync`. Supports custom hasher. Concurrent. **Fixed 8 shards** (`with_shards_and_hasher(8, …)`) regardless of map size — a tuning parameter, not a design choice of the benchmark.
- **std** (`StdBenchMap<K, V, H = RandomState>`): `K: Hash + Eq`. Supports custom hasher. Not concurrent. Baseline `HashMap`.
- **txmap** (`TxMapBenchMap<K, V, H = txmap::DefaultBuildHasher>`): requires `K: Clone + Hash + Eq`; `H: BuildHasher`. Supports custom hasher. Concurrent; built through `TxMapBuilder::default()` with **`txmap::MutexPolicy`** (the wrapper hardcodes this policy — other txmap policies such as `RwLockPolicy` were not benchmarked).

General observations:

- `V: Clone` is required by the benchmark harness (`get_cloned`, `get_or_insert` return owned values), so results do not speak to zero-copy value handling.
- Four implementations were **excluded from specific benches for API reasons** (not performance): concurrent-map (no `clear`, not `Sync`), crossbeam-skiplist (no `Clone`), leapfrog (no `Clone`, no `clear`, `Copy` keys), immutable-chunkmap (no `clear`, no custom hasher), rpds (no `clear`, not `Send`/`Sync`).
- **horde, hashlink, imbl, immutable-chunkmap** could not participate in concurrent benches because their mutation APIs require `&mut` (horde is genuinely concurrent but the wrapper could not express `&Self` mutation).
- concread and flurry produced **no measurements at all**.

## 6. Recommendations

### 6.1 Implementations / benchmarks needing further investigation

1. **txmap vs leapfrog vs scc (concurrent)**: The winner depends on thread count, map size and workload mix. The current data suggests txmap for ≤2 threads/large maps and leapfrog for write-heavy at 3–4 threads, but margins are frequently < 10% and noisy at 4 threads. A dedicated scaling study (2/4/8/16 threads, more sizes) is warranted before making a single "concurrent winner" claim.
2. **dashmap read-heavy 100k @ 4 threads**: dashmap's only win, with rel-SD ≈ 82%. Needs a rerun (more samples/measurement time) to confirm it beats scc/txmap.
3. **rpds-hash-trie-map serial workloads**: 36–63% rel-MAD. If rpds is a candidate for persistent use, its 100k-entry mutation workloads should be re-measured with a longer measurement time.
4. **horde** was excluded from concurrent benches despite being a concurrent structure (its wrapper requires `&mut`). If horde is of interest for concurrent use, adding a shared-reference mutation path would let it be compared fairly.
5. **starshard shard count**: fixed at 8 shards. On a 4-core machine with 100k-entry maps this is a plausible but arbitrary configuration; re-tune and re-measure before drawing conclusions about starshard.
6. **leapfrog `Copy` keys / `Value` values**: results only cover `u64` keys and values; non-`Copy` keys cannot be used, which limits generalizability for that implementation.
7. **txmap policy**: only `MutexPolicy` was exercised; `RwLockPolicy` may behave differently under read-heavy load.

### 6.2 Measurement quality issues

1. **CPU oversubscription at threads-4**: the host has 4 CPUs and worker threads are pinned to CPUs 0–3; the coordinating benchmark thread is *not* pinned and shares a core with a worker at threads-4. This explains the large rel-MAD/rel-SD at 4 threads (e.g. dashmap rel-SD up to 184%). Conclusions at threads-4 should be treated as provisional.
2. **All numbers are absolute, single-run Criterion samples** (warm-up 1 s, measurement 2 s per bench per the harness config). No baseline/change data exists, so "faster than" claims rest solely on medians within this one run.
3. **Throughput-aware values**: because `Throughput::Elements(N)` is set, per-element rates differ from the batch medians reported here; the relative ordering within a group is unaffected, but cross-group comparisons of absolute numbers (e.g. `create` vs `insert`) are not meaningful.
4. **Hot-key benchmarks** (`lookup-hit`, `lookup-miss`, `key-sensitivity`) probe only 100 keys, so they measure best-case cache-resident lookup and are insensitive to map size (confirmed: hit/miss times are flat across 1k/10k/100k).
5. **Clone results for persistent maps** (rpds/imbl/immutable-chunkmap) are O(1) refcount bumps; they should not be compared directly with the O(N) clones of mutable maps as if they were the same operation.
6. **No concread/flurry data**: two of the 21 wrappers contributed zero measurements; the "21 implementations" claim in the README is not reflected in the data (19 measured, 7 concurrent).
