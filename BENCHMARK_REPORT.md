### 3.2 Recommendations by use case

| Use case | Recommended implementation(s) |
|---|---|
| Single-threaded, out-of-the-box, u64 keys (write-heavy/insert/growth) | `rustc-hash` (clear winner) |
| Single-threaded, out-of-the-box, String keys | `rustc-hash`; `ahash`/`hashbrown` close behind |
| Single-threaded with a chosen hasher (fair comparison) | `ahash` / `hashbrown` / `std` (all within ~1% of each other) |
| Fast u64 lookups (hit and miss), out-of-the-box | `intmap` |
| Fast String lookups | `rustc-hash` (oob); `std`/`hashbrown` (common hasher) |
| Full-map iteration (cache-friendly walk) | `indexmap` (2–3× faster than the next best) |
| Insertion-order-preserving map | `indexmap` (iterate) / `hashlink` (also fast lookups) |
| Cheap copies / persistent semantics | `rpds-hash-trie-map`, `imbl`, `immutable-chunkmap` (O(1)-ish clone); caveat: writes to clones are not competitive |
| Clone-then-write / copy-on-write workloads | `rustc-hash`, `ahash` |
| Pooling / clear-and-reuse | `rustc-hash`, `ahash`, `std`, `hashbrown` (retain capacity) |
| Removals (String keys) | `horde`; (`intmap` for u64) |
| Multi-threaded read+write (any mix, 2–3 threads) | `txmap` (overall leader); `leapfrog` for heavily skewed u64 contention; `scc` for write-heavy String; `papaya` for read-only |
| Minimum map-construction overhead | `immutable-chunkmap` (persistent, lazy) |
| Ordered / sorted keys | `btreemap`, `crossbeam-skiplist`, `immutable-chunkmap` (none are fastest, but they offer order) |

### 3.3 Trade-offs

- **Concurrency vs raw speed:** `txmap` wins all concurrent families but is not competitive in serial benchmarks (e.g. 607.7 ns per 100 u64 lookup-hits vs 193 ns for `intmap`; growth 1M u64 60.5 ms vs 34.5 ms for `rustc-hash`). Conversely, `rustc-hash` (fastest serial) is **not concurrent** at all.
- **Persistence vs writes:** `rpds-hash-trie-map`/`imbl`/`immutable-chunkmap` clone in nanoseconds (structural sharing) but are among the slowest for insert/remove/growth. `imbl`'s 100K-clone at 5.3 ns contrasts with its 100K-iterate at 1.376 ms (pointer-chasing).
- **Hasher choice matters hugely for `std`:** with SipHash (out-of-the-box) `std` u64 lookup-hit costs 1.79 µs; with a common hasher 295 ns (~6×). The underlying table (hashbrown/SwissTable) is top-tier when the hasher is cheap.
- **`intmap` specialization:** fastest u64 lookups/removals out-of-the-box but cannot handle String keys at all.
- **`indexmap`:** sacrifices some insert/lookup speed for unbeatable iteration and good large-String growth; also benefits from `swap_remove` in the remove benchmark.
- **`horde`:** strong removal and iteration, but its wrapper only exposes `&mut` writes, so it can't join concurrent benchmarks (its design is concurrent, but this harness cannot share it).

### 3.4 Consistently close implementations

`ahash` (30 groups within 10%), `hashbrown` (22), `std` (19), `rustc-hash` (25), `txmap` (45), `leapfrog` (11) are the most consistently competitive. Notably `ahash`, `hashbrown` and `std` are practically interchangeable under a common hasher across insert/lookup/growth/key-sensitivity — differences of 1% or less are within measurement noise.

## 5. Implementation Limitations

Based on the wrapper code in `src/maps/`. Where a benchmark group omits an implementation, the exclusion reason is stated in the bench source (e.g. `benches/insert.rs`).

- **`ahash`** (`ahash_benchmap.rs`) — bounds `K: Hash + Eq`; mutable operations require `&mut` (not usable in concurrent benches). Configurable hasher via `H: BuildHasher`. Full functionality.
- **`btreemap`** (`btreemap_benchmap.rs`) — ordered map, bounds `K: Ord`; no custom hasher (excluded from all `same-hasher` groups). Not concurrent. Cloning is a full deep copy.
- **`concurrent-map`** (`concurrent_map_benchmap.rs`) — **ergonomically unusual**: the underlying `ConcurrentMap` is `Send` but not `Sync` (EBR state in `RefCell`). The wrapper works around this by keeping a "master" map in a `Mutex` and lazily cloning it into a thread-local per thread (detected via a token). This means each thread mutates its **own private clone** — writes by different threads are not actually shared until the next iteration. Bounds: `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`. No custom hasher. Cannot do `get_or_insert` (no entry API).
- **`crossbeam-skiplist`** (`crossbeam_skiplist_benchmap.rs`) — ordered skip list, `K: Ord + Send + 'static`; no custom hasher; no `get_or_insert` via entry API (has `get_or_insert` op though). Deep-copies are not applicable (no `BenchMapClone` impl).
- **`dashmap`** (`dashmap_benchmap.rs`) — bounds `K: Hash + Eq`, hasher `H: BuildHasher + Clone`. Full concurrent API (get_or_insert/insert/remove via `&self`). Clone is a deep copy. Present in all groups.
- **`flurry`** (excluded, `flurry_benchmap.rs`) — **not benchmarked** (too slow in earlier runs). Interesting bounds: `K: Hash + Ord` for reads, `K: Sync + Send + Clone + Hash + Ord` for writes. Uses `pin()` guards.
- **`hashbrown`** (`hashbrown_benchmap.rs`) — bounds `K: Hash + Eq`; `&mut` mutation; configurable hasher. Present in serial groups only.
- **`hashlink`** (`hashlink_benchmap.rs`) — insertion-ordered `LinkedHashMap`, bounds `K: Hash + Eq`; `&mut` mutation; configurable hasher. Present in serial groups only.
- **`horde`** (`horde_benchmap.rs`) — `horde::SyncTable`; **mutation only through `&mut` in this wrapper** (bench comments: "mutation requires &mut, cannot mutate through a shared reference"), so it is excluded from all concurrent benchmarks even though the underlying crate is concurrent. Reads require `horde::collect::pin` guards. `K: Hash + Eq` (reads) / `Clone + Hash + Eq` (writes). Has no `BenchMapGetOrInsert` (no entry API) — excluded from get-or-insert. No `BenchMapClone`.
- **`imbl`** (`imbl_benchmap.rs`) — persistent `GenericHashMap`; `&mut` mutation; `K: Hash + Eq + Clone` for mutation; configurable hasher. Clone is O(1)-ish (structural sharing). Excluded from concurrent benches.
- **`immutable-chunkmap`** (`immutable_chunkmap_benchmap.rs`) — persistent ordered chunk map, `K: Clone + Ord`, `V: Clone`; COW mutations (`insert_cow`/`remove_cow`) requiring `&mut`; no custom hasher (excluded from same-hasher groups). No `BenchMapMutClear` (no clear impl). Wins `create` and near-free clone.
- **`indexmap`** (`indexmap_benchmap.rs`) — `IndexMap`, `&mut` mutation, configurable hasher; **removal uses `swap_remove`** (unordered removal — cheap but changes iteration order). Excluded from concurrent benches.
- **`intmap`** (`intmap_benchmap.rs`) — integer-key specialization, `K: IntKey` only; **no String keys**; no custom hasher. `&mut` mutation. Excluded from concurrent benches.
- **`leapfrog`** (`leapfrog_benchmap.rs`) — `K: Eq + Hash + Copy`, `V: leapfrog::Value`; **no String keys** (`Copy` required) — excluded from all String groups. Concurrent (insert/remove via `&self`). Has no `BenchMapMutClear`/`BenchMapMutGetOrInsert`... actually it implements both `BenchMapGetOrInsert` and `BenchMapMutGetOrInsert` via `try_insert`. No `BenchMapClone`.
- **`papaya`** (`papaya_benchmap.rs`) — concurrent, uses `pin()` guards per operation; `K: Hash + Eq`; configurable hasher; full API. Present in all groups.
- **`rpds-hash-trie-map`** (`rpds_benchmap.rs`) — persistent `HashTrieMap` with `archery::RcK`; `&mut` mutation (mutating methods); configurable hasher. No `BenchMapGetOrInsert` (excluded from get-or-insert). `remove` is implemented as get-then-remove (two lookups). Excluded from concurrent benches.
- **`rustc-hash`** (`rustc_hash_benchmap.rs`) — `FxHashMap` with fixed FxBuildHasher; **no custom hasher** (excluded from all same-hasher groups); `&mut` mutation. No `BenchMapGetOrInsert`/`BenchMapInsert`/`BenchMapRemove` (shared-ref) — excluded from get-or-insert oob? No — it IS in get-or-insert oob (has `BenchMapMutGetOrInsert`). Excluded from concurrent benches.
- **`scc`** (`scc_benchmap.rs`) — concurrent, `*_sync` API (blocking variants); `K: Hash + Eq`; configurable hasher; full API including get_or_insert. Present in all applicable groups.
- **`starshard`** (`starshard_benchmap.rs`) — `ShardedHashMap` fixed at **8 shards** in the wrapper (`with_shards_and_hasher(8, ...)`); bounds `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`; configurable hasher (defaults to FxBuildHasher); full concurrent API. Present in all applicable groups.
- **`std`** (`std_benchmap.rs`) — `std::collections::HashMap` (hashbrown engine + SipHash); `&mut` mutation; configurable hasher. Default SipHash-1-3 is slow for lookups (see §3.3). Present in all serial groups.
- **`txmap`** (`txmap_benchmap.rs`) — `txmap::TxMap` with `txmap::MutexPolicy`; concurrent via `&self`; configurable hasher; full API including `get_or_insert`. Present in all groups.

## 6. Recommendations

### Further investigation

1. **`txmap`'s serial/concurrent split** — `txmap` wins nearly every concurrent benchmark (often clearly) but is mid-pack or slow in serial ones. Its design (transactional, mutex-based) warrants a closer look: is the serial overhead inherent, or is it the `MutexPolicy` choice? (The wrapper hard-codes `MutexPolicy`; a different policy might change serial results.)
2. **`leapfrog` under heavy skew** — it beat `txmap` in 3-thread u64 Zipfian(1.0)/Zipfian(2.0) contention and 3-thread u64 read-heavy sync. The boundary where leapfrog overtakes txmap (thread count, key distribution, key type) is worth mapping.
3. **`std`/`hashbrown`/`ahash` parity** — under a common hasher these three are within 1% on most serial ops. Verify whether the differences are real or noise (confidence intervals overlap in most same-hasher groups).
4. **`indexmap` at 1M String growth** — it won both out-of-the-box and same-hasher 1M String growth and all iterate groups. Understanding why its resize behavior wins at large String-key sizes (and whether the `swap_remove` iteration-order change matters) would clarify the recommendation.
5. **`horde` removal** — `horde` wins remove with `&mut`-only access. A wrapper change exposing `&self` mutation (if the crate supports it) could make it a concurrent contender worth benchmarking.
6. **The missing concurrent get-or-insert benchmark** — the README documents a concurrent get-or-insert workload (90% hits, 2–3 threads) but no such Criterion group exists in the data. Re-run to complete the picture.
7. **`concurrent-map` wrapper correctness** — each worker thread operates on a private clone of the master map (thread-local), so cross-thread writes are not actually synchronized in the measured region. Results for this crate should be interpreted as "per-thread private map throughput", not shared-map contention.

### Measurement quality issues

1. **Noisy short benchmarks** — several sub-200 µs benchmarks (clear-and-reuse 1K/10K, clone-then-write 1K, throughput-1 u64) show 10–34% relative MAD, including for top performers (`rustc-hash`, `ahash`, `hashbrown`, `std`). Consider longer measurement times or more samples for these.
2. **`create` micro-benchmark** — `immutable-chunkmap` at 0.35 ns per map construction (3.52 µs / 10K) is below a single CPU cycle and suspiciously close to what loop-invariant code motion would produce; the `black_box` may not fully prevent the compiler from hoisting construction of identical empty maps. Treat absolute `create` ratios with caution.
3. **Concurrent benchmark variance** — `dashmap` and `concurrent-map` show 13–30% relative std on several concurrent groups; rankings there (e.g. dashmap within 1% of txmap in contention 3-thread String Zipfian(2.0)) may not be stable across runs.
4. **All conclusions are based on medians** — using means instead would change several close rankings (e.g. `clear-and-reuse` groups with 18–34% rel. MAD). This report consistently uses `median.point_estimate`, per the project convention.
5. **No baseline data** — without change measurements, differences below ~5% between close contenders (e.g. `ahash` vs `std` vs `hashbrown` same-hasher u64 groups) should be treated as noise-level unless reproduced.
