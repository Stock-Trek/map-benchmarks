- **`leapfrog`** is the concurrency king (10 wins: contention, synchronization, 3-thread read-heavy) but is mediocre-to-poor serially: `insert` 853µs vs rustc-hash 149µs (×5.7), `iterate` 90µs vs indexmap 3µs (×30). Its `create` cost is also high (1.22ms).
- **`txmap`** scales best with threads on balanced/write-heavy workloads (all 2-thread groups, 2 of 3 3-thread groups) but is ~6.4× slower than rustc-hash on single-threaded throughput and 1.3–4.8× slower than leapfrog under hot-key contention.
- **`indexmap`** is unmatched at iteration but only mid-pack at inserts/lookups (e.g. insert 276µs vs 149µs; lookup-hit 1.02µs vs 182ns).

- **`horde`** is fast with an ahash hasher (insert 139.86µs, growth 10k 147µs, remove 530ns — all fastest) yet falls behind with its default hasher (insert 326µs). Hasher choice matters as much as map structure.
- **`std`** with its default SipHash is 5–8× slower than rustc-hash on lookups (937ns vs 182ns) but identical once given ahash (253ns vs 243ns).

### Single-threaded hash maps
- **`ahash` (`ahash_benchmap.rs`)** — Requires `K: Hash + Eq` (get/insert/remove), `V: Clone` for get/get-or-insert; clone needs `K: Clone, H: Clone`. Supports custom hashers (`BenchMapNewWithHasher`). No concurrency (`&self` insert not provided). No limitations within the benchmark scope.
- **`std` (`std_benchmap.rs`)** — Requires `K: Hash + Eq` for lookups (not needed for `new()`). Supports custom hashers. Not concurrent. Default hasher (SipHash) is a major performance handicap out-of-the-box.
- **`hashbrown` (`hashbrown_benchmap.rs`)** — Same shape as `std`; supports custom hashers; not concurrent. No `BenchMapRemove` (`&self`) or `BenchMapGetOrInsert` (`&self`) — mutation is `&mut`-only, so it cannot be shared across threads.
- **`rustc-hash` (`rustc_hash_benchmap.rs`)** — Requires `K: Hash + Eq`. **No custom-hasher support** (no `BenchMapNewWithHasher`), so it only competes in `out-of-the-box` groups; FxHash is fast on small keys but not DoS-resistant (well-known property of FxHash). Not concurrent. No `BenchMapRemove`/`GetOrInsert` on `&self`.
- **`hashlink` (`hashlink_benchmap.rs`)** — LinkedHashMap: maintains insertion order; requires `K: Hash + Eq`; supports custom hashers; `&mut`-only mutation (not concurrent). Slightly slower inserts/removes than plain hash maps due to the linked-list bookkeeping.
- **`indexmap` (`indexmap_benchmap.rs`)** — IndexMap: preserves insertion order with dense entry storage; supports custom hashers; `&mut`-only mutation. `swap_remove` (used for remove) does **not** preserve order of the removed element — an ergonomic/behavioural caveat if order stability matters during deletion. Not concurrent.
- **`btreemap` (`btreemap_benchmap.rs`)** — Requires `K: Ord` (not `Hash`); ordered iteration; **no custom-hasher support**; not concurrent. No inherent limitation otherwise, but never competitive on the u64 workloads measured.

### Concurrent maps
- **`dashmap` (`dashmap_benchmap.rs`)** — Requires `K: Hash + Eq`, `H: Clone` (hasher must be clonable for `get`). Supports custom hashers; `Send + Sync`; supports `&self` insert/remove/get-or-insert (sharded RW-locking). No trait-bound surprises.
- **`scc` (`scc_benchmap.rs`)** — Requires `H: BuildHasher` at the struct level; `K: Hash + Eq` for ops; supports custom hashers; `Send + Sync`. Uses `_sync` variants (`read_sync`, `upsert_sync`, `iter_sync`, `clear_sync`) in the wrapper. No notable ergonomic issues in scope.
- **`papaya` (`papaya_benchmap.rs`)** — Requires `K: Hash + Eq`, `V: Clone` for get/remove; supports custom hashers; `Send + Sync`; hazard-pointer based. Every operation goes through `map.pin()`, which is automatic in the wrapper. No trait-bound surprises.
- **`leapfrog` (`leapfrog_benchmap.rs`)** — **Requires `K: Eq + Hash + Copy`** and **`V: leapfrog::Value`** (a sealed-ish trait; in practice supports `Copy`/`Clone` value types) — cannot store arbitrary non-`Copy` keys or `String` keys (excluded from `key-sensitivity` String groups for this reason). Requires `H: BuildHasher + Default` even for custom hashers. **No `clear()`** (absent from `clear-and-reuse`). `get_or_insert` is emulated via `try_insert`. Supports `&self` mutation; `Send + Sync`.
- **`txmap` (`txmap_benchmap.rs`)** — Requires `K: Hash + Eq`, `K: Clone` for get-or-insert; `H: BuildHasher`. Uses `TxMapBuilder` (MutexPolicy default). Supports `&self` mutation; `Send + Sync`. No `clear`-related limitation; wrapper provides `clear`.
- **`horde` (`horde_benchmap.rs`)** — Requires `K: Clone + Hash + Eq` for inserts (keys are cloned into the table); `V: Clone` for get/remove. Supports custom hashers. Mutation is `&mut`-only (write transactions via `map.write()`), so it **cannot be used in the multi-threaded shared-reference groups** despite being internally concurrent. Default hasher (`horde::sync_table::DefaultHashBuilder`) is slow; needs ahash to shine.
- **`crossbeam-skiplist` (`crossbeam_skiplist_benchmap.rs`)** — Requires `K: Ord` (not `Hash`), and `K/V: Send + 'static` for insertion; `V: Clone` for get/remove. **No custom-hasher support**, no `Clone` (absent from `clone`/`clone-then-write`). Never competitive on the measured workloads.
- **`starshard` (`starshard_benchmap.rs`)** — Requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync`. **Hard-coded to 8 shards** in the wrapper (`with_shards_and_hasher(8, …)`). Default hasher is `rustc_hash::FxBuildHasher`. Consistently slowest of the concurrent maps in most groups.
- **`concurrent-map` (`concurrent_map_benchmap.rs`)** — Requires `K: Clone + Minimum + Send + Sync + 'static` (the `Minimum` bound comes from the crate). The raw `ConcurrentMap` is **`Send` but not `Sync`**: its `ebr` dependency keeps epoch-reclamation state in a `RefCell`, so a single `&ConcurrentMap` cannot be shared across threads (forcing it would panic on `RefCell` borrow conflicts). The wrapper is `Send + Sync` and shares the map across threads the way the crate intends — it clones the map per thread (clones share the tree via an internal `Arc` but give each thread its own EBR), so it now participates in the multi-threaded groups. **No custom-hasher support**, no `clear`. get-or-insert is emulated as get-then-insert (not atomic).

### Persistent / structural-sharing maps
- **`imbl` (`imbl_benchmap.rs`)** — Requires `K: Hash + Eq + Clone` for mutation, `V: Clone`, `H: BuildHasher + Clone`. Supports custom hashers. Mutation is `&mut`-only (not usable in shared-reference multi-threaded groups). Uses `DefaultSharedPtr` (Rc-based).
- **`rpds-hash-trie-map` (`rpds_benchmap.rs`)** — Requires `K: Eq + Hash`, `H: BuildHasher + Clone`; uses **`archery::RcK` pointer kind** (not `Send`/`Sync`), so it is excluded from multi-threaded groups. **No entry API** — get-or-insert is emulated as get-then-insert (non-atomic), and `remove` is emulated as get + `remove_mut`. No `clear`. Clone is O(1) structural sharing.
- **`immutable-chunkmap` (`immutable_chunkmap_benchmap.rs`)** — Requires **`K: Clone + Ord`** (ordered tree, not hash-based) and `V: Clone`; **no custom-hasher support**. Mutation via `_cow` variants (copy-on-write); `&mut`-only. No `clear` (absent from `clear-and-reuse`).

### Excluded implementations
- **`concread` (`concread_benchmap.rs`)** — Requires `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`. Supports `&self` mutation via write transactions. **Excluded from all benchmarks as "too slow"** — no measurements exist.
- **`flurry` (`flurry_benchmap.rs`)** — Requires `K: Sync + Send + Clone + Hash + Ord` for insert (note the extra `Ord` bound), `V: Sync + Send`. **Excluded from all benchmarks as "too slow"** (creates a `seize::Collector` per map). No measurements exist.

## 6. Recommendations

### Implementations/benchmarks needing further investigation
1. **`leapfrog` concurrency variance** — Its wins are decisive, but elevated rel std (8–12%) in `contention-3-threads_Uniform`, `synchronization-3-threads_read-only`, `throughput-3-threads_read-heavy` and `throughput-2-threads_balanced` warrants longer measurement runs or more repetitions to pin down the true margin.
2. **`horde` default hasher** — `horde` is fastest in several `same-hasher` groups but much slower with its own default hasher (insert: 139.86µs vs 326.56µs). Investigate whether the default hasher should be replaced upstream.
3. **`create` noise for `rustc-hash`/`indexmap`** — rel std up to 34.6% suggests allocator interference; re-measure with more samples or larger batch sizes before trusting the `create` ranking.
4. **`concurrent-map` and `dashmap` in small `clone-then-write`** — 26.8% / 15.9% relative MAD; verify with longer runs before drawing conclusions.
5. **`concread` and `flurry`** — Wrappers exist but no data. If they are of interest to consumers, benchmark them (or document the exclusion rationale).
6. **`starshard` shard count** — the wrapper hard-codes 8 shards; results may not represent the crate's tunable configurations.
7. **Thread-count scaling** — concurrency was only exercised at 2–3 threads (`DEFAULT_THREAD_COUNTS = [2, 3]`); rankings may change at higher core counts (e.g., dashmap/starshard are sharded and typically scale further).

### Measurement-quality caveats
- **Sub-nanosecond clone timings** — `rpds-hash-trie-map` at ~1.2ns and `imbl`/`immutable-chunkmap` at ~13–15ns are near or at Criterion's timing floor for the harness; the relative ordering is clear but absolute values have limited precision.
- **Small per-iteration workloads** — `lookup-hit`/`lookup-miss`/`remove`/`key-sensitivity` iterate only 100 keys per sample; the `slope` estimate is available in the JSON and could be used for cross-checks.
- **Short measurement windows** — warm-up 1s / measurement 2s per group; noisy tails (especially 1M-entry `growth` and `create`) could benefit from longer windows.
- **No baseline data** — all conclusions are absolute; relative changes between versions cannot be assessed from this data.
- **Hasher asymmetry** — `rustc-hash` (the serial leader) competes only in `out-of-the-box` mode. Its dominance partly reflects FxHash's speed on u64 keys; it should not be assumed for string keys or adversarial inputs (FxHash is not DoS-hardened).
