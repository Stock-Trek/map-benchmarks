### 1.3 How to read the comparisons

- **Out-of-the-box** uses each map’s default hasher. Differences therefore include both map design and hasher choice. This is the realistic “drop-in” comparison.
- **Same-hasher** builds every participating map with `CommonHasher = ahash::RandomState`, isolating the map’s own data structure and serial overhead. It is not available for `btreemap`, `crossbeam-skiplist`, `immutable-chunkmap`, `intmap`, or `rustc-hash`, none of which exposes a configurable hasher in the wrapper.
- **Concurrent groups are out-of-the-box only.** No same-hasher concurrent groups exist in this data. `txmap`’s default is `rapidhash`; `dashmap`, `scc`, and `papaya` default to `RandomState`; `starshard` defaults to `FxBuildHasher`; `crossbeam-skiplist` has no hasher; and `leapfrog` defaults to `BuildHasherDefault<DefaultHasher>`. This is a material confound for concurrent rankings.
- Times are Criterion medians for one whole batch. For example, a `lookup-hit` time covers 100 lookups, while an `insert` time covers 10,000 inserts. Do not compare absolute times across rows with different batch sizes.
- The harness returns cloned values (`get_cloned`), so read/remove paths include value cloning. Memory usage, allocation counts, tail latency, and long-running throughput are not measured.

### 3.3 What the counts mean

- **Two different “fastest” stories.** `rustc-hash` dominates out-of-the-box serial groups because FxHash is much cheaper than `RandomState` for u64 and String keys. When the hasher is held constant, the map differences shrink sharply: `std`, `hashbrown`, and `ahash` are usually within a few percent for insert, lookup, get-or-insert, and u64 growth; same-hasher String growth at 1M is the main exception, where `hashbrown` is about 35% slower than `indexmap`. Do not attribute the entire `rustc-hash` advantage to its table design.
- **Operation shape matters more than “best map” claims.** `indexmap` is the clear iteration winner and also strong for String inserts/growth. `intmap` wins u64 lookups/removals but is weak on insert, growth, and iteration. `horde` wins same-hasher removals but cannot mutate through `&self`. `rpds-hash-trie-map` wins clone by an enormous margin but loses clone-then-write, growth, and iteration.
- **Concurrent rankings are not hasher-controlled.** `txmap`’s default `rapidhash` is faster than the `RandomState` defaults used by `dashmap`, `scc`, and `papaya`; `starshard` uses `FxBuildHasher`. The concurrent wins should therefore be read as “best out-of-the-box configuration in this harness,” not as pure data-structure rankings. The same caveat applies to `leapfrog`’s default hasher.
- **Single-threaded concurrent maps are usually a poor trade.** `txmap` has only one close serial result; `dashmap`, `papaya`, `scc`, `starshard`, `leapfrog`, and `crossbeam-skiplist` have none. Use a concurrent map when shared mutation is required, not as a general-purpose single-threaded map.
- **Ordered maps are not speed leaders.** `btreemap` and `crossbeam-skiplist` win no groups. `indexmap` preserves insertion order and is fast for iteration/insertion, but its wrapper uses `swap_remove`, so order is not preserved after removal.

### 3.5 Trade-offs to keep in mind

1. **HashDoS resistance versus raw speed.** `rustc-hash`/FxHash is the fastest out-of-the-box option in many rows, but FxHash is not designed to resist adversarial collisions. `std`/`ahash`/`rapidhash` use keyed/randomized hashing and are safer defaults for untrusted input. `ahash` is fast but is not a cryptographic hash.
2. **Same-hasher fairness versus realistic deployment.** Same-hasher groups isolate map design, but many real applications use each crate’s default. The out-of-the-box groups answer “what happens if I drop this in?”, while same-hasher groups answer “which table/synchronization design is better?”. The two answers differ materially, especially for `rustc-hash`.
3. **Clone cost versus write cost.** Persistent maps make clone nearly free but make mutation expensive through path copying. `clone-then-write` is the relevant benchmark for copy-on-write use cases, and there `rustc-hash`/`ahash` beat the persistent maps by 19–29× at 100K.
4. **Iteration layout versus point-operation layout.** `indexmap`’s contiguous entry array is excellent for scans and insertion-order work, but its point lookups are slower than the best hash tables, and its wrapper’s `swap_remove` changes order.
5. **Concurrency design versus contention pattern.** `txmap` wins most mixes, but `leapfrog` wins u64 Zipfian/read-heavy cases, `scc` wins some String write-only/write-heavy cases, and `papaya` wins pure String read-only. There is no single concurrent winner across all contention shapes.
6. **No memory or tail-latency data.** A map that is slightly slower in median time may still be preferable for lower memory use or more predictable latency; those dimensions are not measured here.
7. **Absolute times are machine- and run-specific.** The dataset has no baseline or repeated independent runs. The stability section quantifies within-run dispersion, not run-to-run reproducibility.

### 3.6 Consistently close implementations

- **Serial:** `hashbrown` is the most consistent runner-up (25/64 within 10%, 39.1%), followed by `ahash` (24/64, 37.5%), `std` (17/64, 26.6%), and `indexmap` (13/64, 20.3%). `hashbrown` has only two outright wins, but it is rarely far off the pace in same-hasher groups.
- **Concurrent:** `txmap` is close in 42/48 groups (87.5%), which is consistent with its broad win count. `leapfrog` is close in 16/24 u64 groups (66.7%) but is absent from String groups. `scc` is close in 5/48 (10.4%), `dashmap` in 3/48 (6.2%), and the rest essentially never.
- **“Close” is not “equivalent.”** Several close results are within measurement noise (e.g. 1.00–1.02×), while others are genuine 5–9% gaps. The 10% band is a reporting convenience, not a significance threshold.

### 4.3 Interpretation and noisy fast implementations

- **Median-based rankings are mostly protected from the worst SD outliers.** `leapfrog`’s 2-thread u64 Zipfian 2.0 contention result has 0.2% MAD but 69.9% SD; a handful of very slow samples inflate the standard deviation while the median remains stable. `txmap`’s 3-thread u64 write-majority synchronization result is similar (2.1% MAD, 47.8% SD). Both are still fastest, but their means/slopes would be less trustworthy than their medians.
- **`rpds-hash-trie-map` clone entries look noisy in relative terms but are irrelevant in absolute terms.** At 1K/10K/100K the median is 2.18 ns and SD is 0.23–0.33 ns (10.7–15.2% relative). This is sub-nanosecond jitter on an O(1) pointer clone, not a practical concern.
- **Genuinely noisy slow cases can be ignored for winner selection.** `rpds-hash-trie-map` iteration at 100K (24.9% MAD), `imbl` u64 growth at 100K (24.1% MAD), and `imbl` 1M String growth (11.4% MAD) are far from the leaders; their variance does not change any recommendation.
- **Close calls that deserve caution.** `dashmap`’s 2-thread String write-only synchronization result (18.9% MAD) is within 10% of the winner, and `scc`’s 3-thread String write-only result (5.1% MAD) is also within 10%. The exact ordering of these near-ties should not be treated as robust.
- **`dashmap` and `starshard` are the most consistently noisy concurrent implementations.** They appear repeatedly in the high-variance list for write-heavy/write-only synchronization and clear-and-reuse. `crossbeam-skiplist` is noisy in String read-only synchronization but is not near the lead.
- **The fastest implementations are not uniformly noisy.** `rustc-hash`, `std`, `hashbrown`, `ahash`, and `indexmap` mostly fall below the flagging thresholds. The notable fast-but-noisy cases are `leapfrog` under contention, `txmap` under one u64 write-majority synchronization case, `horde` under same-hasher u64 removal, and `scc` in one String write-only case. For `horde`, MAD is only 1.2% and the win is large, so the median result is credible despite the SD flag.

## 5. Implementation Limitations

### 5.1 Constraints that apply to the whole comparison

- **The measured API clones values.** `get`, `remove`, and `get_or_insert` return owned `V` values, so read/removal times include `V::clone`. This is necessary for a uniform harness but penalizes maps that return references and hides maps that can avoid cloning.
- **No memory, allocation, capacity, or tail-latency metrics.** The harness records time only. A map with a slightly worse median may be preferable for memory footprint, allocation behavior, or predictable p99 latency; those questions cannot be answered from this dataset.
- **Concurrent measurements are out-of-the-box only.** There is no same-hasher concurrent run. `txmap` uses `rapidhash` by default, `starshard` uses `FxBuildHasher`, and most others use `RandomState`; the concurrent ranking therefore mixes map design and hasher choice. This is the single largest comparability limitation in the report.
- **Thread counts are limited to 2 and 3.** The dataset cannot show scaling beyond three workers, nor behavior on NUMA systems or under oversubscription.
- **The harness is synchronous.** `scc` is exercised through its `*_sync` methods; async runtimes and async map APIs are not measured. `horde`/`papaya` pinning and reclamation costs are included per operation, but long-lived pins, guard lifetimes, and reclamation pauses are not modeled.
- **The benchmark covers point operations, full scans, and synthetic contention.** It does not cover range queries (except implicitly for ordered maps in iteration), concurrent iteration, resizing under memory pressure, persistence/serialization, or crash recovery.
- **No baseline or independent repetitions.** A single Criterion run per benchmark is available. Stability is assessed from Criterion’s within-run dispersion, not from repeated independent process runs.
- **`iter_batched` setup is outside the timed region in several benchmarks.** Clone/growth/insert/remove benchmarks prepare the initial map outside the timed region, and concurrent benchmarks spawn/pin workers once per sample outside the timed region. The numbers measure the operation batch, not worker startup or map population.
- **Batch sizes differ by operation.** `lookup-hit`, `lookup-miss`, and `remove` time 100 operations; `insert` times 10,000 inserts; `get-or-insert` times 20,000 calls (10,000 existing keys plus 10,000 missing keys); `iterate` is a full scan. Cross-operation absolute-time comparisons are invalid without normalizing by the batch.

Per-wrapper notes:

- **`ahash`:** `K: Hash + Eq`, `V: Clone`, `H: BuildHasher`; defaults to `ahash::RandomState`; hasher is configurable; all benchmarked operations are exposed; no mutation through `&self`.
- **`btreemap`:** `K: Ord` (no `Hash` requirement), `V: Clone`; no hasher parameter, so it cannot enter same-hasher groups; ordered point operations are O(log n); all benchmarked operations including `clear` are exposed.
- **`crossbeam-skiplist`:** `K: Ord + Send + 'static`, `V: Clone + Send + 'static` for `get_or_insert`; no hasher; no `BenchMapClone`, so clone is absent; ordered skip list; exposes concurrent `&self` insertion/removal.
- **`dashmap`:** `K: Hash + Eq`, `H: BuildHasher + Clone + Default`, `V: Clone`; default `RandomState`; deep-copy clone; `clear` is exposed through `&mut self`; holding a `Ref` while touching another entry can deadlock.
- **`hashbrown`:** `K: Hash + Eq`, `H: BuildHasher + Default`, `V: Clone`; default `DefaultHashBuilder` (foldhash), configurable per wrapper; no `&self` mutation; all benchmarked operations are exposed.
- **`hashlink`:** `K: Hash + Eq`, `H: BuildHasher`, `V: Clone`; default `hashbrown::DefaultHashBuilder`; insertion-ordered linked map; all benchmarked operations including `clear` are exposed.
- **`horde`:** `K: Clone + Hash + Eq`, `V: Clone`, `H: BuildHasher + Clone`; no get-or-insert; reads/iteration require `horde::collect::pin`; writes require `&mut self`; `clear` uses `replace(empty)`; reclamation can delay memory reuse.
- **`immutable-chunkmap`:** `K: Clone + Ord`, `V: Clone`; no hasher and no same-hasher groups; copy-on-write `*_cow` methods require `&mut self`; no `clear` wrapper; cheap structural clone, expensive mutation.
- **`imbl`:** `K: Clone + Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone`; persistent HAMT; all benchmarked operations including `clear` are exposed, but updates take `&mut self`; cheap clone, expensive writes.
- **`indexmap`:** `K: Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone`; all benchmarked operations are exposed; the wrapper uses `swap_remove`, which does not preserve order after removal; `shift_remove` would be the stable-order alternative in application code.
- **`intmap`:** `K: IntKey` only, `V: Clone`; no hasher, no String keys, no same-hasher groups; all benchmarked operations including `clear` are exposed; weak on insert, growth, and iteration relative to its lookup/removal niche.
- **`leapfrog`:** `K: Eq + Hash + Copy`, `V: Value` (`Clone + Copy + Debug`), `H: BuildHasher + Default`; no String/non-`Copy` keys; no `BenchMapClone` or `BenchMapMutClear`; concurrent mutation through `&self`; no get-or-insert wrapper.
- **`papaya`:** `K: Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone`; pinning is required; all benchmarked operations including `get_or_insert` and `clear` are exposed, with `clear` behind `&mut self`; reclamation/guard lifetimes matter in real code.
- **`rpds-hash-trie-map`:** `K: Eq + Hash`, `H: BuildHasher + Clone`; map is parameterized with `archery::RcK`; no get-or-insert or clear wrapper; not `Send`/`Sync`; persistent updates via `&mut`; wrapper `remove` is lookup plus `remove_mut` (two traversals).
- **`rustc-hash`:** `K: Hash + Eq`; fixed `FxBuildHasher`, so no custom-hasher or same-hasher groups; all benchmarked operations are exposed; FxHash is fast but deterministic and not HashDoS-resistant; no `&self` mutation.
- **`scc`:** `K: Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone`; exercised through `*_sync` APIs; all benchmarked operations including `get_or_insert`/`clear` are exposed, with `clear` behind `&mut self`; clone is a deep copy.
- **`starshard`:** `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync`; default `FxBuildHasher`; all benchmarked operations are exposed, with `clear` behind `&mut self`; heavy bounds and sharded locking add overhead.
- **`std`:** `K: Hash + Eq`, `H: BuildHasher + Default`, `V: Clone`; default `RandomState` is keyed/DoS-resistant but slower than FxHash/rapidhash; all benchmarked operations are exposed; no `&self` mutation.
- **`txmap`:** `K: Clone + Hash + Eq`, `H: BuildHasher + Clone`, `V: Clone`; default `rapidhash` (not cryptographic); all benchmarked operations including `get_or_insert`/`clear` are exposed, with `clear` behind `&mut self`; high single-thread overhead; clone is a deep copy.

### 5.3 What these limitations mean for interpretation

1. **The “best” map depends on the operation and on the hasher.** There is no implementation that wins across all 15 operation families. `rustc-hash` wins many serial groups only because FxHash is inexpensive; `indexmap` wins iteration; `intmap` wins u64 point lookups/removals; `horde` wins same-hasher removals; `rpds` wins clone; `txmap` and `leapfrog` win different concurrent patterns.
2. **Same-hasher results are the fairest structural comparison; out-of-the-box results are the fairest deployment comparison.** Neither is universally “correct.” Use same-hasher to choose a data structure, then re-test the final candidate with the hasher you will actually deploy.
3. **The concurrent ranking is provisional with respect to hashers.** Before standardizing on `txmap` for concurrent workloads, rerun the relevant concurrent benchmarks with a common hasher (or with the production hasher) to separate its map design from its default `rapidhash`. The same applies to `starshard`’s `FxBuildHasher` and `leapfrog`’s defaults.
4. **Persistent maps need workload-specific validation.** Their clone numbers are spectacular, but clone-then-write and growth show the cost of path copying. If the workload clones and then mutates, benchmark that pattern, not clone alone.
5. **Feature gaps are not performance results.** Missing wrapper operations (clone for `crossbeam-skiplist`, clear for `immutable-chunkmap`/`leapfrog`/`rpds`, get-or-insert for `horde`/`rpds`) mean those cells are absent, not that the crate is incapable of the operation. Check the crate API before ruling out an implementation.
6. **Operational costs not captured here can dominate.** Lock contention under long critical sections, memory reclamation pauses, `Rc` versus `Arc` thread-safety, async integration, and allocation pressure are all outside the measured surface.

## 6. Recommendations

### 6.1 Implementations and benchmarks that need further investigation

- **Concurrent maps with a controlled hasher.** `txmap` is the broad concurrent winner, but its default `rapidhash` is not the same as the `RandomState` used by `std`, `dashmap`, `scc`, and `papaya`, or the `FxBuildHasher` used by `starshard`. Re-run `txmap`, `leapfrog`, `scc`, `papaya`, `dashmap`, and `starshard` with `CommonHasher` (and with the production hasher) before treating the concurrent ranking as a data-structure ranking.
- **Persistent maps under clone-then-write.** `rpds-hash-trie-map`, `imbl`, and `immutable-chunkmap` look excellent for clone-only workloads and poor for clone-then-write. Test the actual snapshot/mutation pattern, including the fraction of the clone that is subsequently modified.
- **`intmap` for insert/growth-heavy integer workloads.** It wins u64 lookup/removal but is weak on insert, growth, and iteration. If integer-keyed workloads are write-heavy, compare it against `std`/`hashbrown` rather than assuming the lookup win carries over.
- **`horde` ergonomics.** Its same-hasher removal wins are the largest non-hasher advantages in the serial data, but writes require `&mut self`, reads/iteration require pinning, and there is no get-or-insert wrapper. Measure the pinned read path and the real write pattern before adopting it.
- **`scc`, `papaya`, and `dashmap` niches.** Their wins/close calls are narrow and sometimes noisy. Re-run String write-only/write-heavy (`scc`, `dashmap`) and String read-only (`papaya`) with longer measurement windows and more thread counts.
- **Ordered maps for range workloads.** `btreemap` and `crossbeam-skiplist` are not competitive on point operations, but this benchmark does not measure range queries. If range scans matter, add a range-query benchmark before ruling them out.
- **`starshard` variance.** It never places within 10% of the fastest concurrent result and appears repeatedly in the high-variance list. Profile it under the intended shard count and write mix before considering it.

### 6.2 Measurement quality issues that could affect conclusions

- **Single run, no baseline.** All conclusions are from one Criterion dataset. Re-run any decision-critical benchmark, ideally in a quiet environment with multiple independent process runs.
- **Hasher confound.** Out-of-the-box results mix map design with hasher choice; same-hasher results cover serial operations only. This is the biggest threat to the concurrent conclusions.
- **Value cloning.** The harness returns cloned `u64` values. For large or expensive `V`, clone cost can dominate lookups/removals and change the ranking.
- **Batch-size differences.** `lookup`/`remove` batches are 100 operations; `insert` is 10,000; `get-or-insert` is 20,000; iteration is a full scan. Never compare absolute times across operation families.
- **High-variance cells.** 45/1,323 measurements meet the MAD ≥ 5% or SD ≥ 10% screen. Close concurrent orderings should be treated as provisional.
- **Limited concurrency and no memory metrics.** Only 2 and 3 threads are measured; memory, allocation rate, p99 latency, and reclamation pauses are not.

### 6.3 Priority next steps

1. Re-run the final concurrent candidate set with a common hasher and the production hasher.
2. Re-run clone-then-write for any persistent-map candidate.
3. Re-run the 10–15 closest or highest-variance concurrent cells before standardizing.
4. Add memory and tail-latency measurements for latency- or memory-sensitive services.

## 7. Bottom Line

- **Single-threaded, trusted keys, raw speed:** `rustc-hash` is the most frequent winner (26/64 serial groups), but the advantage is largely the FxHash hasher. For a safer default, `std`/`hashbrown`/`ahash` are usually within a few percent when the hasher is held constant.
- **Iteration or insertion order:** `indexmap` is the clear choice, winning every iteration group by a wide margin.
- **Integer keys with lookup/removal-heavy access:** `intmap` wins the relevant u64 out-of-the-box groups, but it is a poor choice for insert/growth/iteration and does not support String keys.
- **Cheap snapshots:** `rpds-hash-trie-map` is the clone winner (2.18 ns at all sizes), with `imbl` and `immutable-chunkmap` also in the 4 ns range. Do not use them for mutation-heavy workloads without measuring clone-then-write.
- **Concurrent mixed workloads:** `txmap` is the broad winner (34/48 groups, 42/48 within 10%), but that result is out-of-the-box and benefits from `rapidhash`. `leapfrog` is the specialist for concurrent u64/hot-spot workloads; `scc` and `papaya` have narrow String write/read niches.
- **Stability:** most medians are stable (median relative MAD 0.53%). The noisy cases are concentrated in concurrent write/synchronization workloads and persistent-map iteration/growth. Re-run any close concurrent call before making a production decision.
