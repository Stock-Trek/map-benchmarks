### 3.2 Recommended implementation(s) by use case

| Use case | Recommended implementation(s) |
|---|---|
| General-purpose single-threaded map | `rustc-hash` (fastest overall); `ahash`, `hashbrown` or `std` when a configurable/secure hasher is needed |
| Ordered iteration / cache-friendly traversal | `indexmap` (clear winner); `immutable-chunkmap` for immutable snapshots |
| Cheap snapshotting / persistent data structures | `rpds-hash-trie-map`, `imbl`, `immutable-chunkmap` (O(1) clone) |
| Integer (`u64`) key lookups | `intmap` out of the box; `ahash`/`hashbrown`/`std` under a shared hasher |
| Heavy concurrent read/write mix | `txmap` (MutexPolicy); `leapfrog` as the lock-free alternative |
| Concurrent single hot key (skewed contention) | `txmap` for mixed loads; `leapfrog` for write-heavy `u64` loads |
| Write-once / read-only after build | `std`/`hashbrown`/`ahash`; avoid `txmap`, `papaya`, `dashmap` unless concurrency is required |
| Short-lived maps created in bulk | `rustc-hash` or `immutable-chunkmap` (near-zero construction cost) |
| Removal-heavy workloads | `horde` (shared hasher); `rustc-hash`/`intmap` out of the box |

### 3.3 Trade-offs

- **Clone vs. mutation.** Persistent maps (`rpds`, `imbl`, `immutable-chunkmap`) clone in nanoseconds but pay far more for every mutation; mutable maps clone in tens of microseconds to milliseconds but insert fastest. Pick based on whether snapshots or writes dominate.

- **Construction vs. steady state.** `rustc-hash`/`immutable-chunkmap` build empty maps for free, while `dashmap`, `starshard`, `papaya`, `txmap` and `concurrent-map` spend ~0.2–0.9 µs per map. A concurrent map is a bad choice for a short-lived map.

- **Iteration vs. hashing.** `indexmap` is ~2–10× faster to iterate than the general hash maps but is slower for random insert/lookup because it maintains a second index vector.

- **Contention granularity.** `txmap` and `leapfrog` win under contention; `starshard`'s fixed 8 shards and `concurrent-map`'s per-thread clones fare poorly. Skew (Zipfian) hurts `txmap` more than `leapfrog`, which is fastest for the most skewed `u64` threads-3 cases.

- **Hash function matters.** In out-of-the-box runs `rustc-hash`'s FxHasher often decides the winner; once a shared hasher is used the ranking collapses to the same few SwissTable maps (`ahash`, `hashbrown`, `std`).

## 5. Implementation Limitations

Derived from the wrapper code in `src/maps/`. "Interior mutability" means the map implements the shared-reference insert (`BenchMapInsert`) required by the concurrent benchmarks.

- **`ahash`** (`ahash_benchmap.rs`): `K: Hash + Eq`, `V: Clone`; clone additionally needs `K: Clone` and a `Clone` hasher. Only `&mut` mutation, so it is excluded from all concurrent write benchmarks. Supports a custom hasher; `clear` available.
- **`btreemap`** (`btreemap_benchmap.rs`): requires `K: Ord` (comparison, not hashing), `V: Clone`. No custom hasher API and only `&mut` mutation; therefore present only in serial out-of-the-box runs. In-order iteration is free.
- **`concurrent-map`** (`concurrent_map_benchmap.rs`): `K: Minimum + Clone + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`. **Ergonomically unusual:** `ConcurrentMap` is `Send` but *not* `Sync` (its EBR state lives in a `RefCell`), so the wrapper keeps a master map behind a `Mutex` and lazily clones it into a thread-local per iteration, type-erasing it through `Any`. Shared-reference operations therefore act on a per-thread clone rather than a single shared map — a fidelity caveat for the concurrency numbers. No custom-hasher constructor in the wrapper and no `clear`.
- **`crossbeam-skiplist`** (`crossbeam_skiplist_benchmap.rs`): `K: Ord + Send + 'static`, `V: Send (+ Clone)`; no `Clone`, so it is absent from clone/clone-then-write. No custom hasher. `clear` available. Values must be `Send`.
- **`dashmap`** (`dashmap_benchmap.rs`): `K: Hash + Eq`; hasher must be `BuildHasher + Clone (+ Default)`. Supports custom hasher, shared-reference mutation, clone and `clear`.
- **`hashbrown`** (`hashbrown_benchmap.rs`): `K: Hash + Eq`; custom hasher; only `&mut` mutation; clone and `clear`.
- **`hashlink`** (`hashlink_benchmap.rs`): `K: Hash + Eq`; custom hasher (needs `Default` for `new`); only `&mut` mutation; clone and `clear`.
- **`horde`** (`horde_benchmap.rs`): `K: Hash (+ Eq)`, `V: Clone`; custom hasher. All mutation (`insert`, `remove`, `clear`) requires `&mut self`, so it is excluded from concurrent *write* benchmarks; it also has no get-or-insert API (absent from that benchmark). Reads use an epoch `pin`.
- **`imbl`** (`imbl_benchmap.rs`): persistent HAMT; `K: Hash + Eq + Clone` for mutation, hasher `Clone`. Custom hasher constructor exists in the wrapper but the type is not entered in the same-hasher runs. Only `&mut` mutation (copy-on-write); O(1) clone.
- **`immutable-chunkmap`** (`immutable_chunkmap_benchmap.rs`): `K: Clone + Ord` (ordered, *not* hashed), `V: Clone`. Mutation is via `insert_cow`/`remove_cow`/`get_or_insert_cow`, i.e. copy-on-write returning new nodes; no custom hasher and no `clear`. O(1) clone.
- **`indexmap`** (`indexmap_benchmap.rs`): `K: Hash + Eq`; custom hasher; only `&mut` mutation; clone and `clear`. Removal uses `swap_remove`, so ordering is not preserved across removals.
- **`intmap`** (`intmap_benchmap.rs`): keys must implement `IntKey` (integer types only). **No `String` keys**, no custom hasher, only `&mut` mutation. clone and `clear` available.
- **`leapfrog`** (`leapfrog_benchmap.rs`): **`K: Eq + Hash + Copy`** (keys must be `Copy`, so no `String`) and `V: Value` (POD-like). Custom hasher requires `BuildHasher + Default`. No `Clone` and no `clear`, so it is absent from clone, clone-then-write and clear-and-reuse. Supports both shared-reference and `&mut` mutation.
- **`papaya`** (`papaya_benchmap.rs`): `K: Hash + Eq` (`V: Clone` for get/remove); custom hasher; shared-reference and `&mut` mutation; clone and `clear`. Per-map setup is comparatively expensive (reclamation infrastructure).
- **`rpds-hash-trie-map`** (`rpds_benchmap.rs`): persistent hash trie using the `archery::RcK` pointer kind — **`Rc`-based and therefore not `Send`/`Sync`**, so it cannot be used in concurrent benchmarks. `K: Eq + Hash`; custom hasher; mutation via `insert_mut`/`remove_mut` requires `&mut`; no `clear`; no get-or-insert API. O(1) clone.
- **`rustc-hash`** (`rustc_hash_benchmap.rs`): hard-wires `FxHasher` — **no configurable hasher**, hence absent from all same-hasher benchmarks. `K: Hash + Eq`; only `&mut` mutation; clone and `clear`.
- **`scc`** (`scc_benchmap.rs`): `K: Hash + Eq`; custom hasher; shared-reference and `&mut` mutation; clone and `clear`. Uses `_sync` variants for the lock-free path.
- **`starshard`** (`starshard_benchmap.rs`): shard count is **hard-coded to 8** in the wrapper; requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync` and a `Send + Sync` hasher. Supports custom hasher but is not entered in same-hasher runs. Shared-reference and `&mut` mutation; clone and `clear`.
- **`std`** (`std_benchmap.rs`): `K: Hash + Eq`; custom hasher; only `&mut` mutation; clone and `clear`.
- **`txmap`** (`txmap_benchmap.rs`): `MutexPolicy` is hard-coded; `K: Hash + Eq` (`K: Clone` for get-or-insert). Custom hasher; shared-reference and `&mut` mutation; clone and `clear`.

**Wrapped but not present in the report data:** `concread` and `flurry`. Their wrappers exist (`concread_benchmap.rs`, `flurry_benchmap.rs`) but they are commented out of every benchmark (documented as "too slow"). `concread` additionally offers no `Clone`, no custom hasher and no get-or-insert API; `flurry` requires `K: Hash + Ord + Send + Sync` and `V: Send + Sync`.

## 6. Recommendations

**Benchmarks / implementations that need further investigation**

1. **Re-verify `txmap`'s concurrent dominance.** `txmap` wins 38 of 48 concurrent groups and is often 1.3–2× the next map. Before treating this as a general result, confirm the `MutexPolicy` configuration used by the wrapper, that updates from all threads are actually applied to one shared map, and that `get_cloned`/`insert`/`remove` exercise the intended transactional path. This is the single most consequential result in the report.
2. **Audit the `concurrent-map` wrapper.** Its thread-local clone design means shared-reference operations do not all touch the same map instance. Its numbers (often the slowest) should be treated as a property of the wrapper, not necessarily of `concurrent_map::ConcurrentMap` used the recommended way.
3. **Split `clone` into its own category.** Comparing O(1) persistent clones with O(n) deep copies produces 4–6 order-of-magnitude ratios that swamp every aggregate. Report persistent and mutable maps separately, or normalise per element.
4. **Add baselines / repeated runs.** Only `new` measurements are available and there is no `base` change data. Re-running the noisiest groups (1M growth, 100K iteration, 100K clear-and-reuse, `String` insert/get-or-insert) would confirm the rankings where relative MAD exceeds ~10%.
5. **Improve the same-hasher coverage.** Several maps (`imbl`, `starshard`, `immutable-chunkmap`, `concurrent-map`, `crossbeam-skiplist`, `btreemap`, `intmap`, `leapfrog` on `String`, `rustc-hash`) cannot take the common hasher or the common key type. The cross-map comparison is therefore only complete for the SwissTable-style maps; document this when quoting "fair" comparisons.
6. **Close the concurrency feature gap.** `horde`, `imbl`, `immutable-chunkmap`, `rpds` and the plain maps expose only `&mut` mutation and so never enter the concurrent benchmarks. If they are candidates for concurrent use, confirm this is a genuine API limitation rather than a wrapper-choice gap.

**Measurement-quality issues that could affect conclusions**

- All numbers are single-run point estimates with no confidence-interval analysis beyond Criterion's defaults; treat sub-5% differences as ties unless confirmed by a re-run.
- The concurrency benchmarks share one map via `Arc` and amortise thread spawn/pinning outside the timed region, which is good, but the workload generation, allocator state and CPU frequency can still vary between sample sets.
- Out-of-the-box results mix two effects — data-structure design and the default hash function. When the question is "which map is faster", prefer the same-hasher results; when the question is "which map should I drop in", prefer the out-of-the-box results.
- `remove` timings for several maps have high relative MAD; the `horde` removal win in particular should be reproduced before acting on it.
