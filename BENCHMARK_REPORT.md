**Most often fastest overall:** `rustc-hash` (28 wins, all of them in the serial out-of-the-box domain). **Best concurrent map:** `txmap` (16 wins) and `leapfrog` (18 wins, u64-only). **Most consistently competitive:** `hashbrown` (31/64 within 10%) and `ahash` (30/64).

### 3.2 Recommendations by use case

| Use case | Recommended implementation(s) |
|---|---|
| Single-threaded, default hasher, u64 or String keys (general purpose) | `rustc-hash` (fastest nearly everywhere; caveat: FxHasher is not DoS-hardened and no custom hasher) |
| Single-threaded with a shared/custom hasher (structure vs hasher) | `ahash` / `hashbrown` / `std` — statistically tied (within 1–9%) |
| Get-or-insert / cache-fill pattern | `rustc-hash` (default hasher); `ahash` / `hashbrown` / `std` (custom hasher) |
| Iteration-heavy workloads | `indexmap` (2.5–3× faster than any hash map) |
| Snapshot/clone-heavy workloads, versioned data | `rpds` (clone is O(1)); also `imbl`, `immutable-chunkmap` (accepting 10–20× write cost) |
| Concurrent mixed workloads (2–3 threads) | `txmap` (String, most mixes); `leapfrog` (u64 keys) |
| Concurrent hot-key / single-key sync | u64: `leapfrog`; String read-only: `papaya`; String writes 2 threads: `dashmap`; String writes 3 threads: `scc` |
| Concurrent read-mostly, skewed access | `txmap`, `leapfrog` (u64), `dashmap`/`papaya` under extreme skew |
| u64-only maps (lookup/remove-heavy) | `intmap` (fastest u64 hit/miss/remove) |

### 3.3 Trade-offs

There are clear cases where **different implementations excel at different operations**:

- **`rustc-hash`** is unbeatable for serial out-of-the-box use but contributes nothing to `same-hasher` or concurrent runs (no custom hasher; not concurrent).
- **`leapfrog`** owns concurrent u64 workloads (contention, synchronization, throughput) but is ~356× slower at `create` (per-map setup), is limited to `Copy` keys/values (no String), and is 1.5–30× slower in serial u64 operations than the SwissTable family.
- **`txmap`** owns concurrent String throughput and contention, but pays ~887× on `create` and is ~6× slower than rustc-hash on serial throughput.
- **`indexmap`** wins iteration by a wide margin and does well on same-hasher String growth, but its clone is expensive and its `remove` uses `swap_remove`, which does not preserve insertion order (an ergonomic caveat).
- **`rpds`** is a spectacular cloner (O(1)) yet 2–40× slower at nearly everything else.
- **`papaya`** is the best read-only single-key concurrent map but among the worst write-heavy performers.
- **`intmap`** is fastest for u64 hit/miss/remove yet inapplicable to String keys and mediocre at iteration and growth.

### 3.4 Consistently close implementations

- **`hashbrown`** and **`ahash`**: within 10% of the fastest in ~half of all serial groups they enter; they are effectively interchangeable with each other and with `std` when the hasher is equalised.
- **`std`**: only competitive with a fast hasher (SipHash drags it to x1.8–x7.5 in out-of-the-box runs).
- **`hashlink`**: never fastest but within 10% in 8 groups (lookups, key sensitivity).

## 4. Stability

Criterion reports `median_abs_dev` (MAD) and `std_dev` per benchmark. The table below lists measurements with **MAD/median > 5%** — the noisy outliers. (For context, the vast majority of measurements have MAD < 2%.)

| Group | Implementation | Time | MAD/median | std/median | Position |
|---|---|---|---|---|---|

| synchronization 3t String write-mostly | `txmap` | 3.23 ms | 6.8% | 7.2% | **2nd (fast)** |
| throughput 1t String write-heavy | `papaya` | 2.26 ms | 6.8% | 6.4% | mid-pack |
| throughput 1t u64 write-heavy | `papaya` | 1.33 ms | 6.6% | 5.8% | mid-pack |
| synchronization 3t String read-mostly | `txmap` | 2.08 ms | 5.6% | 4.4% | **2nd (fast)** |

| lookup-hit same-hasher String | `rpds-hash-trie-map` | 2.87 µs | 6.1% | 5.8% | mid-pack |
| lookup-hit oob String | `crossbeam-skiplist` | 13.2 µs | 5.7% | 4.9% | mid-pack |
| lookup-miss oob String | `hashbrown` | 655.8 ns | 5.4% | 5.1% | **3rd (fast)** |

**Key findings:**

1. **Every outright fastest measurement is stable.** In no group does the winning implementation have MAD/median above ~3%; most winners are under 1%. Conclusions about the leaders are not noise-driven.
2. **`txmap` — a genuinely fast concurrent map — is the noisiest fast implementation.** It is 2nd place in the 3-thread String synchronization suite with MAD 5.5–7.2%. These are wall-time concurrent runs with pinned threads; the spread is likely inherent contention jitter, but a re-run with a longer measurement window would tighten the estimate.
3. **`concurrent-map` is unreliable in two ways:** its 3-thread u64 read-only measurement has 11.2% MAD, and its clone-then-write 1K measurement 22.9% MAD. Its wrapper (clone-per-thread via thread-locals, see §5) is an unusual harness shim, and its results vary wildly across workloads (best x1.8 of fastest, worst x34.5 in the concurrent suite).
4. **Small-iteration-count micro-benchmarks** (clone-then-write 1K: ~1–40 µs/iter) show the highest relative noise (dashmap 14.8%, imbl 10.1%, concurrent-map 22.9%) — these sit near the measurement floor for per-iteration times.
5. **Persistent `imbl`** shows elevated variance on large growth runs (8.4–14.9% std) — allocation/GC pressure during persistent-node churn.

## 5. Implementation Limitations

From inspection of the wrapper code in `src/maps/`. **Concrete name** = the `BenchMapName` used in the Criterion directory.

### `ahash` (`AhashBenchMap`, `ahash::AHashMap`)
- Requires `K: Hash + Eq` (and `V: Clone` for `get` / get-or-insert).
- Mutation only via `&mut` — not usable in concurrent benchmarks.
- Configurable hasher: ✅ (`new_with_hasher`).
- Get-or-insert only on `&mut` (returns a cloned value).

### `btreemap` (`BTreeMapBenchMap`, `std::collections::BTreeMap`)
- Requires `K: Ord` (ordered, no hashing). No configurable hasher — absent from all `same-hasher` runs.
- `V: Clone` bound on most ops; mutation via `&mut` only.

### `concurrent-map` (`ConcurrentMapBenchMap`, `concurrent_map::ConcurrentMap`)
- Requires `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`.
- **Ergonomically unusual:** `ConcurrentMap` is `Send` but **not `Sync`** (its EBR reclamation state lives in a `RefCell`). The wrapper keeps a "master" map in a `Mutex` and clones it into a thread-local once per iteration (tracked by a per-instance token); clones share the underlying tree via an internal `Arc`. All concurrent ops go through the thread-local clone.
- No `clear`, no get-or-insert API, no configurable hasher, no `Clone` at the wrapper level (replaced by the master/token dance).
- Results should be treated with caution (§4): wildly variable across workloads.

### `crossbeam-skiplist` (`CrossbeamSkiplistBenchMap`, `crossbeam_skiplist::SkipMap`)
- Requires `K: Ord`; writes additionally require `K: Send + 'static`, `V: Send + 'static`.
- Does **not** implement `Clone` (absent from `clone`/`clone-then-write`); no configurable hasher.
- Supports `&self` mutation (concurrent). No capacity retention on `clear` (slowest clear-and-reuse at 100K, x56.5).

### `dashmap` (`DashMapBenchMap`, `dashmap::DashMap`)
- Requires `K: Hash + Eq`; `H: Clone` for `get`/`insert` (entry ref-counting).
- Configurable hasher: ✅. Concurrent (`&self` ops).
- `get`/`get_or_insert` return clones of the value.

### `hashbrown` (`HashbrownBenchMap`, `hashbrown::HashMap`)
- SwissTable; `K: Hash + Eq` for ops; `V: Clone` for `get`/get-or-insert; mutation via `&mut`.
- Configurable hasher: ✅.

### `hashlink` (`HashlinkBenchMap`, `hashlink::LinkedHashMap`)
- Insertion-order linked hash map; `K: Hash + Eq`; mutation via `&mut`.
- Configurable hasher: ✅.

### `horde` (`HordeBenchMap`, `horde::SyncTable`)
- Concurrent hash table, but the wrapper **only exposes `&mut` insert/remove** (no `BenchMapInsert`), so it is absent from concurrent benches despite the crate being concurrent.
- Requires `K: Clone + Hash` (insert), `V: Clone` (get/remove); reads use `horde::collect::pin` (epoch-pinned guard).
- No get-or-insert API. Configurable hasher: ✅.
- `remove` replaces the whole table (`write().replace(...)`), giving it the fastest same-hasher String removal.

### `imbl` (`ImblBenchMap`, `imbl::HashMap`)
- Persistent/immutable (structural sharing). Mutation through `&mut`; `K: Hash + Eq + Clone`, `V: Clone`.
- Configurable hasher: ✅. No `&self` mutation, no get-or-insert on `&self`.
- Clone is O(1)-ish (14 ns) but writes are 2–4× slower than mutable maps; highest variance on big growth runs.

### `immutable-chunkmap` (`ImmutableChunkMapBenchMap`, `immutable_chunkmap::map::MapM`)
- Persistent, chunked, ordered (`K: Clone + Ord`, `V: Clone`); COW API (`insert_cow`, `remove_cow`, `get_or_insert_cow`).
- No configurable hasher; no `clear` (absent from clear-and-reuse); mutation via `&mut`.
- Slow at nearly everything (2–38× behind) except clone (15.6 ns, structural sharing).

### `indexmap` (`IndexMapBenchMap`, `indexmap::IndexMap`)
- Insertion-ordered; configurable hasher: ✅; mutation via `&mut`.
- **`remove` uses `swap_remove`** — removal does **not** preserve insertion order (semantics differ from `shift_remove`). If order preservation on removal matters, this wrapper's choice is a behavioural caveat.
- Fastest iteration by far (contiguous entry array).

### `intmap` (`IntMapBenchMap`, `intmap::IntMap`)
- Integer keys only (`K: IntKey`); no configurable hasher.
- `get`/`remove` take the key **by value** (`self.map.get(*key)`), and `iter` yields keys by value — a minor ergonomic quirk vs `&K`.
- Fastest u64 lookup-hit/miss/remove; poor iteration and growth.

### `leapfrog` (`LeapfrogBenchMap`, `leapfrog::LeapMap`)
- Requires `K: Eq + Hash + Copy` and `V: Value` (Copy) — **no String keys**, no non-Copy values.
- No `clear`, no `Clone`. Get-or-insert via `try_insert` (returns the existing value or the default).
- Concurrent (`&self` ops), configurable hasher: ✅.
- Very expensive `create` (1.18 ms/10K, x356) but the fastest concurrent u64 map.

### `papaya` (`PapayaBenchMap`, `papaya::HashMap`)
- Pin-based API (`map.pin()` for all ops); `K: Hash + Eq`, `V: Clone` for get/remove.
- Concurrent, configurable hasher: ✅.
- Best read-only single-key concurrency; weak write-heavy.

### `rpds` (`RpdsHashTrieMapBenchMap`, `rpds::HashTrieMap`)
- Persistent hash trie (`K: Eq + Hash`); `insert_mut` / `remove_mut` (in-place under the hood but exposed through `&mut`).
- **No get-or-insert, no clear, no Clone trait** (absent from those benches except clone where the wrapper implements `BenchMapClone` via `map.clone()`).
- Configurable hasher: ✅. Clone is O(1) (1.3 ns); everything else 2–40× slower.

### `rustc-hash` (`RustCHashBenchMap`, `rustc_hash::FxHashMap`)
- **No configurable hasher** (FxHasher fixed) — absent from all `same-hasher` runs. Mutation via `&mut`.
- `K: Hash + Eq`. Not concurrent. FxHasher is fast but not DoS-resistant.

### `scc` (`SccBenchMap`, `scc::HashMap`)
- Concurrent; the wrapper uses the **synchronous** API (`read_sync`, `entry_sync`, `upsert_sync`, `iter_sync`, `remove_sync`, `clear_sync`), which blocks rather than parking.
- `K: Hash + Eq`; configurable hasher: ✅.
- Wins 3-thread String synchronization and String write-heavy throughput.

### `starshard` (`StarshardBenchMap`, `starshard::ShardedHashMap`)
- Hardcoded **8 shards** (`with_shards_and_hasher(8, ...)`).
- Requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: Clone + Send + Sync`; `get`/`remove` return/require clones.
- Configurable hasher: ✅. Concurrent. Never fastest; weak on lookups (x7–x36) and 1K iteration (x151).

### `std` (`StdBenchMap`, `std::collections::HashMap`)
- SipHash-1-3 by default (slow out-of-the-box), configurable hasher: ✅. `K: Hash + Eq`; mutation via `&mut`.

### `txmap` (`TxMapBenchMap`, `txmap::TxMap`)
- Transactional concurrent map (`txmap::MutexPolicy`); `K: Hash + Eq` for most ops; get-or-insert additionally needs `K: Clone` (via `get_with_or_insert`).
- Configurable hasher: ✅. Concurrent.
- Very slow `create` (2.9 ms/10K, x887), mediocre serial performance, but the dominant concurrent String map. Elevated noise in 3-thread String sync runs (§4).

### `concread` / `flurry` (excluded, not benchmarked)
- `concread`: requires `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`; transactional read/write (`map.read()`, `map.write()/commit()`); no custom hasher, no Clone. Excluded as too slow.
- `flurry`: requires `K: Hash + Ord` (unusual — needs `Ord`), `V: Sync + Send`; pin-based; no get-or-insert API. Excluded as too slow.

## 6. Recommendations

### Further investigation

1. **`concurrent-map` wrapper and results.** Its clone-per-thread harness (master map + mutex + thread-local + token) is a non-trivial shim around a non-`Sync` crate. Results span x1.8 to x34.5 of the fastest across concurrent workloads (and x2712 on `create`), and two measurements have 11–23% MAD. Validate whether the wrapper matches the crate's intended usage and re-measure with more samples.
2. **`txmap` noise in 3-thread String synchronization.** txmap is 2nd in 5 of these runs with MAD 5.5–7.2%. If txmap is a serious contender for hot-key workloads, re-run with longer measurement time to tighten the estimate.
3. **`papaya` write-heavy variance** (6.6–6.8% MAD in 1-thread write-heavy throughput) — check for pin/epoch reclamation effects.
4. **`imbl` large-growth variance** (up to 14.9% std) — likely allocator pressure; worth a re-run with a longer window.
5. **Same-hasher String growth at scale.** `indexmap` wins 1K–1M same-hasher String growth but is beaten by hashbrown at u64 sizes — investigate why String growth favours indexmap (possibly allocation pattern of the index array).
6. **`horde`'s replace-on-remove design.** Its `clear` and `remove` both rebuild the table; it wins same-hasher String removal and insert but is weak elsewhere. Whether the rebuild strategy is a net win depends on workload — worth targeted investigation.

### Measurement quality issues that could affect conclusions

1. **No baseline/change data.** Only absolute medians exist; nothing here measures regressions or improvements over time.
2. **`out-of-the-box` vs `same-hasher` must not be conflated.** Out-of-the-box runs include hasher choice (`std` with SipHash is 2–8× slower than with the CommonHasher; `rustc-hash` is absent from same-hasher because it cannot take a hasher). Structure-vs-hasher conclusions should only come from the `same-hasher` groups.
3. **Per-iteration vs per-element units.** All numbers are per benchmark iteration (e.g. 10,000 maps for `create`, 1M inserts for `growth` 1M, 100 lookups for lookup-hit). Per-element costs are noted inline where meaningful.
4. **`create` measures 10K maps/iteration**, so sub-ns-per-map results (rustc-hash 0.33 ns/map) sit near the timing floor — treat absolute values, not ratios, with care there.
5. **Clone benchmark mixes two fundamentally different semantics.** Persistent maps (rpds 1.3 ns, imbl 14 ns, immutable-chunkmap 15.6 ns) clone via refcount bump while all mutable maps deep-copy (150 µs+ at 100K). The "fastest" label is semantically expected, not a surprise to benchmark.
6. **`starshard` uses a fixed 8 shards** — its scaling conclusions are specific to that configuration.
7. **Thread-pinned concurrent runs** are wall-clock measurements of parallel execution; absolute times are machine-dependent. Ratios within a group are the meaningful signal, and cross-machine comparisons should not be attempted.
