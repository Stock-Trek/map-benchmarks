### Trade-offs (different implementations excel at different operations)

- **indexmap**: ~3–4× faster iteration than any hash map, but 2–7× slower lookup/insert/remove — buy iteration speed with access cost.
- **leapfrog**: mediocre in serial benches (2.7–3.6× slower than rustc-hash for insert), excellent in concurrent ones; requires `Copy` keys.
- **txmap**: best at 2 threads, competitive at 3–4, but loses at 4-thread/100k where leapfrog/papaya/scc pull ahead.
- **rustc-hash**: fastest serial map but not thread-safe and hasher is fixed (FxHash) — not usable in same-hasher or concurrent benches.
- **horde**: clearly fastest remover under a shared hasher but unremarkable elsewhere; writes need `&mut`.
- **papaya / dashmap / scc**: papaya wins high-contention 100k/4-thread cases; dashmap is the most balanced concurrent all-rounder; scc is a close runner-up at 4 threads/100k but never wins outright.
- **Persistent maps (rpds / imbl / immutable-chunkmap)**: instant clone but 5–50× slower insert/get-or-insert and slow iteration; only worth it for snapshot semantics.
- **crossbeam-skiplist / starshard**: never competitive in these workloads (~3–13× behind); starshard only has 8 shards and requires `Send + Sync + Clone` keys/values.

### Consistently close implementations

- **hashbrown** and **ahash** are within 10 % of `rustc-hash` in nearly every serial benchmark (20 and 18 close appearances respectively) — the practical choice when you need a non-Fx hasher.
- **leapfrog** is within 10 % of the fastest in 36 of 106 groups — the most broadly competitive concurrent map.
- **txmap** is within 10 % in 21 concurrent groups, making txmap/leapfrog a near-tie in many concurrent scenarios.
- **std** is within 10 % of the fastest in all same-hasher serial groups (17 appearances), i.e., with a decent hasher std's HashMap is competitive.

### Key stability findings

- **The 4-thread / 100k-entry concurrent groups are the noisiest in the entire report.** The three winners there — leapfrog (balanced 100k t4: 169 % rel std), papaya (read-heavy 100k t4: 115 % rel std), dashmap (read-heavy 100k t4: 80 % rel std) — all have very large spreads, so **rankings at this corner of the matrix should be treated as provisional**.
- **leapfrog, the most frequent concurrent winner, is also the noisiest winner**: rel std 47–169 % across several 4-thread groups and a 102 % relative MAD in get-or-insert 100k t4 (where papaya beat it). Its median times are still the lowest, but the margin over txmap/scc/papaya is frequently smaller than the measurement noise.
- **scc** shows outlier contamination (write-heavy 100k t1: rel std 62 % but MAD only 5 %, i.e., a few slow samples drag the std).
- **rpds-hash-trie-map** has rel std 52–62 % in the 100k workloads — noisy, but it trails the leaders by 30–200× there, so it does not affect conclusions.
- **imbl** insert at 100k has 16 % MAD (10 ms median) — moderate bimodality, probably GC/path-copying effects.
- The serial benchmarks and same-hasher microbenchmarks are generally very stable (relative MAD mostly < 2 %).

## 5. Implementation Limitations (from `src/maps/` wrappers)

Per wrapper (`src/maps/<module>.rs`), as exercised by the benches:

- **ahash** (`ahash_benchmap.rs`): requires `K: Hash + Eq`, `V: Clone` for reads; supports custom hashers (`BenchMapNewWithHasher`). No thread-safe shared mutation.
- **btreemap** (`btreemap_benchmap.rs`): requires `K: Ord`; no custom hasher (excluded from same-hasher benches); not concurrent.
- **concread** (`concread_benchmap.rs`): requires `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`; no `Clone` for the map itself (excluded from clone bench); excluded from all benches as "too slow".
- **concurrent-map** (`concurrent_map_benchmap.rs`): requires `K: 'static + Clone + Minimum + Send + Sync`; `get_or_insert` is **emulated** as get-then-insert (not atomic); `Send` but **not `Sync`** — cannot share `&ConcurrentMap` across threads, so excluded from concurrent benches; no custom hasher.
- **crossbeam-skiplist** (`crossbeam_skiplist_benchmap.rs`): requires `K: Ord` (+ `Send + 'static` for writes); no `Clone` impl (excluded from clone bench); no custom hasher.
- **dashmap** (`dashmap_benchmap.rs`): `K: Hash + Eq`, hasher must be `Clone`; full shared-read/shared-write support; custom hasher OK.
- **flurry** (`flurry_benchmap.rs`): requires `K: Sync + Send + Clone + Hash + Ord`; excluded from all benches as "too slow" (creates a `seize::Collector` per map).
- **hashbrown** (`hashbrown_benchmap.rs`): `K: Hash + Eq`; custom hasher OK; not concurrent in this harness (mutation via `&mut`).
- **hashlink** (`hashlink_benchmap.rs`): `LinkedHashMap` — maintains insertion order (extra bookkeeping); custom hasher OK; mutation requires `&mut`, so excluded from concurrent benches.
- **horde** (`horde_benchmap.rs`): `SyncTable`; `get_or_insert` is emulated as read-then-write (not atomic); mutation requires `&mut`, so excluded from concurrent benches; custom hasher OK.
- **imbl** (`imbl_benchmap.rs`): persistent `GenericHashMap`; `V: Clone`, `K: Hash + Eq + Clone` for mutation; mutation requires `&mut`, so excluded from concurrent benches; custom hasher OK.
- **immutable-chunkmap** (`immutable_chunkmap_benchmap.rs`): `K: Clone + Ord`, `V: Clone`; persistent ordered map (COW `MapM`); no custom hasher (excluded from same-hasher); mutation via `&mut` (excluded from concurrent); no `BenchMapClear`.
- **indexmap** (`indexmap_benchmap.rs`): `IndexMap`; remove uses `swap_remove` (order-changing); custom hasher OK; not concurrent.
- **leapfrog** (`leapfrog_benchmap.rs`): requires **`K: Eq + Hash + Copy`** and `V: leapfrog::Value` — a hard constraint (excluded from String-key benches and clone); default hasher is `BuildHasherDefault<DefaultHasher>`; concurrent-capable; `get_or_insert` uses `try_insert`.
- **papaya** (`papaya_benchmap.rs`): `K: Hash + Eq`; pin-based API (`pin().get/insert/remove`); concurrent; custom hasher OK.
- **rpds-hash-trie-map** (`rpds_benchmap.rs`): persistent `HashTrieMap` with `archery::RcK` — clone is O(1) but the Rc pointer is **not `Send`/`Sync`** (excluded from concurrent benches); mutation returns new map / requires `&mut`; `get_or_insert` emulated as get-then-insert; no `clear`.
- **rustc-hash** (`rustc_hash_benchmap.rs`): `FxHashMap`; hasher is fixed — no `BenchMapNewWithHasher` (excluded from same-hasher benches); not thread-safe.
- **scc** (`scc_benchmap.rs`): `K: Hash + Eq`; concurrent via `_sync` entry APIs; custom hasher OK.
- **starshard** (`starshard_benchmap.rs`): requires **`K/V: Clone + Send + Sync`**; fixed **8 shards** (`with_shards_and_hasher(8, ...)`); concurrent; custom hasher OK (default FxBuildHasher).
- **std** (`std_benchmap.rs`): `HashMap`; `K: Hash + Eq`; custom hasher OK; not concurrent.
- **txmap** (`txmap_benchmap.rs`): `TxMap` with `MutexPolicy`; `K: Clone + Hash + Eq` for get-or-insert; concurrent; custom hasher OK.

Ergonomic oddities worth noting:
- `get_or_insert` is **not atomic** in `concurrent-map`, `horde`, and `rpds-hash-trie-map` (emulated get-then-insert) — their get-or-insert numbers reflect a non-atomic emulation.
- `indexmap`'s `remove` uses `swap_remove`, which reorders the iteration order.
- `leapfrog`'s `Copy`-key bound and `starshard`'s fixed 8-shard configuration are structural constraints, not benchmark artifacts.
- `concurrent-map` cannot be used through a shared reference (`&`), which excludes it from exactly the workloads it was designed for in this harness.

## 6. Recommendations

### Implementations / benchmarks needing further investigation

1. **leapfrog — serial vs concurrent gap.** leapfrog is the best concurrent map here yet 2.7–3.6× slower than rustc-hash for serial bulk insert. Verify whether this is inherent (locking protocol) or a harness artifact (e.g., `with_capacity_and_hasher(0, …)` starting from an empty/ungrown table).
2. **4-thread / 100k-entry concurrent results are not trustworthy yet.** The winners (leapfrog 169 % rel std, papaya 115 %, dashmap 80 %) have extreme spreads. Re-run these groups with longer measurement time and more samples before quoting them; consider pinning the main thread as well.
3. **papaya vs scc at 100k/4-thread get-or-insert.** papaya won by only 1.3 % over scc — statistically a tie given the noise (papaya rel std 48 %). Re-run to decide.
4. **horde's remove advantage.** horde is 1.3–1.5× faster at same-hasher remove — worth checking whether the wrapper's `remove` path is doing less work (e.g., not cloning) than competitors'.
5. **Zipfian `_2`/`_3` duplicates.** The zipfian groups contain two extra copies of each concurrent implementation. Re-run `workload_zipfian_concurrent` against the current source to regenerate clean data (and to restore the truncated group names).
6. **concread and flurry** are absent from every group. If they matter to consumers, add them back (with longer measurement budgets) or document their exclusion explicitly.

### Measurement-quality issues that could affect conclusions

- **Warm-up/measurement times are short** (1 s warm-up, 2 s measurement in `src/config.rs`). For the 100k-entry concurrent workloads this yields very few samples and the high variance seen in Section 4.
- **Thread pinning** is used correctly (`PinThread::try_pin` per worker, workers reused across iterations, setup outside the timed region), so the noise is workload/scheduling, not harness bookkeeping.
- **`base/` vs `new/` estimates**: each group contains both `base/` and `new/` estimate sets; this report uses `new/` per the project convention. Comparing against `base/` would silently compare two different runs.
- **Truncated zipfian directory names** make the report tree ambiguous; the directory paths in `target/criterion/` are the only reliable identifiers for those groups.
- **Tiny-timing benches** (clone at ~2 ns) have sub-nanosecond absolute spreads; only order-of-magnitude conclusions (persistent vs deep-copy) should be drawn from them.
- **Serial winner margins are small but consistent**: rustc-hash's lead over hashbrown/ahash is often 10–30 %, within the "close contender" band in several groups; for production decisions treat rustc-hash/hashbrown/ahash as a family, with rustc-hash the fastest in this environment.
