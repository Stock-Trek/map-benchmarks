### 3.1 Who is fastest, and how often?

Across the 132 groups there is a **three-way tie** for "most often fastest" (22 groups each), but in *disjoint domains*:

| Implementation | # times fastest | # times within 10% | Notes |
|---|---|---|---|
| `rustc-hash` | 22 | 26 | Dominates **serial** workloads with the default hasher (growth, insert, throughput, lookups, get-or-insert, clear-and-reuse). Not configurable; FxHash is not collision-hardened. |
| `scc` | 22 | 28 | Dominates **concurrent write-heavy / String-key / hot-key** workloads (synchronization 16/24, throughput write-heavy, contention Uniform). Also within 10% on many read workloads. |
| `leapfrog` | 22 | 25 | Dominates **concurrent u64 read/balanced** workloads (contention 6/6 u64, synchronization u64 reads, throughput u64 balanced/read-heavy). u64/Copy keys only. |

| `indexmap` | 11 | 15 | Wins **iterate** (6/6, clearly ahead) and String-key `insert`/`growth` with common hasher. Not concurrent. |
| `papaya` | 9 | 10 | Best for **read-only / read-heavy** concurrency and high-skew Zipfian(2.0) contention. |

### 3.2 Recommendations by use case

| Use case | Recommended implementation(s) |
|---|---|
| Single-threaded, general purpose, default hasher | **rustc-hash** (fastest); `hashbrown`/`ahash` within ~4–10% |
| Single-threaded, shared hasher or hash-quality concerns | **ahash**, `hashbrown`, `std` — near parity (≤8% spread) |
| Insertion-ordered iteration | **indexmap** (iterate wins by ~2.5×, fast String inserts); `hashlink` as backup |
| Ordered / range queries | **btreemap** (only ordered impl measured); `immutable-chunkmap` if persistence needed |
| Cheap clones / persistent snapshots | **rpds-hash-trie-map** (O(1) clone); `imbl`, `immutable-chunkmap` |
| u64 keys, concurrent read-heavy / balanced | **leapfrog** (Copy-key constraint) |
| u64 keys, concurrent write-heavy | **scc** (3 threads); **txmap** (2 threads) |
| String keys, concurrent read-mostly / read-only | **papaya**; `txmap` (default hasher) |
| String keys, concurrent balanced/mixed | **scc** (3 threads, common hasher); **txmap** (default hasher) |
| Hot-key skew (Zipfian 2.0) contention | **papaya** |
| Concurrent get-or-create cache | **papaya** / **txmap**; `leapfrog` for u64 |
| Reusable pool / clear-and-refill | **std** / `ahash` (common hasher); **rustc-hash** (default hasher) |
| u64 lookups / removes (default hasher) | **intmap** |
| Worst-case single-key synchronization, writes | **scc** |

### 3.3 Trade-offs: different implementations excel in different operations

The clearest specializations:

- **leapfrog** is unbeatable on *concurrent u64 reads* (uniform contention 268 µs vs. 0.6–4.3 ms for the rest of the field: scc 629 µs, txmap 763 µs, dashmap 843 µs, papaya 1.08 ms, starshard 4.27 ms; synchronization read-only 69 µs vs. papaya 114 µs and 1.1–3.4 ms for the others) but requires `K: Copy` and so is **inapplicable to String keys entirely**.
- **scc** is the write-side counterweight: it wins every write-majority/write-only synchronization group (both key types) and write-heavy throughput at 3 threads, but loses read-only to papaya (String) and leapfrog (u64).
- **papaya** dominates read-mostly/read-only concurrency with String keys and extreme Zipfian(2.0) skew — readers are cheap, writes are the cost.
- **txmap** is the default-hasher String concurrent winner at 2 threads but yields to scc at 3 threads on write-heavy.
- **rustc-hash** is the serial default-hasher winner but has no configurable hasher and no interior mutability — it cannot be used concurrently in this harness.
- **indexmap** trades concurrency and removal order (uses `swap_remove`) for superb cache-friendly iteration.
- **horde** wins serial *writes* (insert/remove/write-heavy) via copy-on-write, but the harness can't use it concurrently (`&mut`-only wrapper) and it lacks `get_or_insert`.

### 3.4 Consistently close implementations

- **ahash** is within 10% of the fastest in **30 of 132** groups — more than any other implementation — despite being fastest only 7 times. Together with `hashbrown` (24) and `std` (21) it forms a tight cluster of serial maps that are near-interchangeable once the hasher is fixed.
- **scc** is within 10% in 28 groups, spanning both read and write concurrent workloads — the most versatile concurrent map.
- **leapfrog** (25) and **rustc-hash** (26) round out the top; their closeness is confined to their domains (concurrent u64 / serial default-hasher).

### 4.2 Noisy fast implementations

- **dashmap** — the noisiest winner. ## 5. Implementation Limitations

Findings from inspecting the wrappers in `src/maps/`:

- **ahash** (`ahash_benchmap.rs`): requires `K: Hash + Eq`, `V: Clone`. Configurable hasher (`BenchMapNewWithHasher`). `&mut`-only mutation — not usable in concurrent benches. All serial traits implemented.
- **btreemap** (`btreemap_benchmap.rs`): requires `K: Ord`; no hasher concept (ordered). `&mut`-only. Only ordered implementation — cannot use it for hash-based workloads.
- **concread** (`concread_benchmap.rs`): requires `K: Clone + Debug + Hash + Eq + Send + Sync + 'static`, `V: Clone + Send + Sync + 'static`. Supports `&self` insert/remove (COW transaction), but implements **no `get_or_insert`**. No custom hasher in the wrapper. **Excluded from the benches as "too slow" — no measurements exist.**
- **concurrent-map** (`concurrent_map_benchmap.rs`): requires `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`. The underlying `ConcurrentMap` is `Send` but **not `Sync`** (EBR state in `RefCell`). The wrapper compensates with a mutex-serialized "master" map plus per-thread lazy clones stored in thread-local storage (re-cloned once per iteration). This workaround means: no `get_or_insert`, no custom hasher, and concurrent mutating access goes through per-thread clones rather than one shared map — its numbers reflect that design constraint.
- **crossbeam-skiplist** (`crossbeam_skiplist_benchmap.rs`): requires `K: Ord`; inserts need `K: Ord + Send + 'static`, `V: Send + 'static`; gets/removes need `V: Clone`. No custom hasher. Supports `&self` mutation.
- **dashmap** (`dashmap_benchmap.rs`): requires `K: Hash + Eq`; hasher must be `Clone + BuildHasher` (+ `Default` for `new`). Full `&self` mutation support; value clones on read. No unusual bounds beyond those.
- **flurry** (`flurry_benchmap.rs`): requires `K: Sync + Send + Clone + Hash + Ord` for inserts — note the extra **`Ord`** bound — `V: Sync + Send`. Configurable hasher, `&self` mutation, but implements **no `get_or_insert`** and **no `BenchMapMutGetOrInsert`**. **Excluded as "too slow" — no measurements exist.**
- **hashbrown** (`hashbrown_benchmap.rs`): `K: Hash + Eq` for mutations; configurable hasher; `&mut`-only.
- **hashlink** (`hashlink_benchmap.rs`): `K: Hash + Eq`; configurable hasher; `&mut`-only. Insertion-order linked list adds overhead on iteration/removal relative to indexmap.
- **horde** (`horde_benchmap.rs`): `K: Hash + Eq`, `V: Clone`; configurable hasher. Reads require a pin guard (`horde::collect::pin`). Implements **no `get_or_insert`**. Despite the crate's concurrent COW design, the wrapper only exposes **`&mut` mutation**, so the harness treats it as serial (excluded from all concurrent benches).
- **imbl** (`imbl_benchmap.rs`): `K: Hash + Eq + Clone` for mutations, `V: Clone`; hasher must be `BuildHasher + Clone`. `&mut`-only; persistent (structural sharing). `clear` on a persistent map is O(n) — hence poor clear-and-reuse results.
- **immutable-chunkmap** (`immutable_chunkmap_benchmap.rs`): requires `K: Clone + Ord`, `V: Clone`; no custom hasher; `&mut`-only COW (MapM). No `clear` trait implemented. Persistent ordered structure.
- **indexmap** (`indexmap_benchmap.rs`): `K: Hash + Eq`; configurable hasher; `&mut`-only. **`remove` uses `swap_remove`**, which changes iteration order (swap-with-last) — a semantic caveat for users who care about order stability on removal.
- **intmap** (`intmap_benchmap.rs`): requires `K: IntKey` — **integer keys only** (no String support). No custom hasher; `&mut`-only.
- **leapfrog** (`leapfrog_benchmap.rs`): requires `K: Eq + Hash + Copy` and `V: leapfrog::Value` (Copy-like bound) — **u64 keys only in these benches; no String keys**. Configurable hasher (`BuildHasher + Default`). Supports `&self` mutation. Implements **no `clone` and no `clear`** traits.
- **papaya** (`papaya_benchmap.rs`): `K: Hash + Eq`; configurable hasher; `&self` mutation via pin guards (hazard-pointer reclamation). Full trait coverage, no unusual bounds.
- **rpds-hash-trie-map** (`rpds_benchmap.rs`): `K: Eq + Hash`; hasher must be `BuildHasher + Clone`. `&mut`-only mutation (`insert_mut`/`remove_mut`); **`remove` performs a get followed by remove_mut (two traversals)**; no `clear`; no `get_or_insert`. Clone is O(1) via `RcK` sharing.
- **rustc-hash** (`rustc_hash_benchmap.rs`): `K: Hash + Eq`; **no configurable hasher** (fixed FxHash — fast but not collision-hardened). `&mut`-only.
- **scc** (`scc_benchmap.rs`): `K: Hash + Eq`; configurable hasher; `&self` mutation (`entry_sync`, `upsert_sync`, `remove_sync`, `iter_sync`). Full trait coverage. All operations are synchronous (`*_sync`) rather than async.
- **starshard** (`starshard_benchmap.rs`): requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync` — **`Clone` required on both keys and values for all operations** (incl. lookups/iteration); hasher must be `Clone + Send + Sync`. Fixed **8 shards**. Default hasher is FxBuildHasher.
- **std** (`std_benchmap.rs`): `K: Hash + Eq`; configurable hasher; `&mut`-only.
- **txmap** (`txmap_benchmap.rs`): `K: Hash + Eq` for get/insert; **`K: Clone + Hash + Eq` for `get_or_insert`**; configurable hasher; `&self` mutation (transactional, `MutexPolicy`). Full trait coverage.

Cross-cutting notes:

- **No custom hasher:** btreemap, concread, concurrent-map, crossbeam-skiplist, immutable-chunkmap, intmap, rustc-hash — these only ran with the `default-hasher` configuration.
- **Not usable with String keys:** intmap (`IntKey` only), leapfrog (`K: Copy` only).
- **No `get_or_insert`:** concread, concurrent-map, flurry, horde, rpds-hash-trie-map — excluded from the get-or-insert benches.
- **No `clear`:** immutable-chunkmap, leapfrog, rpds-hash-trie-map — excluded from clear-and-reuse.
- **No measurements at all:** concread, flurry (both commented out of the benches as "too slow").

## 6. Recommendations

### 6.1 Implementations / benchmarks needing further investigation

1. **dashmap's noisy wins.** Its 2-thread String throughput wins (esp. the 18.1%-MAD balanced group) need re-measurement with longer measurement time / more samples before being trusted. Its overall winner-noise (6.5% avg) is the highest of any winning implementation.
2. **horde's serial write performance.** horde winning serial insert/remove/write-heavy deserves scrutiny — verify it isn't an artifact of its COW design deferring work (e.g. uncommitted writes or lazy reclaim). Also consider adding a `&self` mutation wrapper so it can be compared fairly in the concurrent benches.
3. **leapfrog's domain.** It is only benchmarked with u64 (Copy) keys. Evaluate with small `Copy` struct keys to see whether its concurrent-read dominance generalizes beyond integers.
4. **concread and flurry** were excluded as "too slow". Re-run with reduced map sizes or longer measurement budgets so the report covers all 22 wrappers.
5. **indexmap's iterate/insert wins** (2.5× over the field) should be re-confirmed with more samples; the 10K iterate group showed 10.4% MAD. Also note `swap_remove` semantics when recommending it.
6. **rpds clone at the measurement floor** — the ~1 ns clone is a single refcount increment; characterize it at larger sizes or with `RcK` vs `ArcK` pointer kinds.
7. **scc vs. papaya vs. txmap** read/write split is stark (scc wins writes, papaya/txmap win reads). A finer-grained read/write mix sweep (10% steps) would pin down the crossover points.

### 6.2 Measurement-quality issues affecting conclusions

- **No baseline/change data.** Only absolute single-run measurements exist; inter-run machine variance is unquantified. The MAD values are *within-run* and may understate run-to-run differences, especially for concurrent benchmarks.
- **Very short benchmarks are noisy.** Sub-200 ns operations (lookups) and 1K-map benches show MAD ratios up to 21% (e.g. hashlink iterate 1K 21.4%, lookup-miss 10.6%). Differences of a few ns at this scale are within noise; the "winner by 1–2%" rows in §2 should be read as ties.
- **The 1 ns clone floor** makes the clone benchmark's absolute numbers uninformative beyond "O(1)".
- **Concurrent harness details.** The concurrent benches use a pre-spawned, pinned worker pool with a fresh map published per iteration; per-iteration `Arc` publishing and the `Cell`-based done-counter live outside the timed region, but OS scheduling of 3 pinned threads still dominates absolute numbers. Only 2 and 3 threads were tested — no scaling beyond 3.
- **Coverage asymmetry.** The common-hasher configurations run fewer implementations (12–14) than default-hasher (16–20) because several maps have no configurable hasher; comparing "fastest" across hasher configurations is apples-to-oranges and the report keeps them separate.
- **SipHash vs FxHash.** The `default-hasher` results for rustc-hash and starshard embed a fast-but-DoS-vulnerable hasher; conclusions about "rustc-hash is fastest" apply only when FxHash's collision resistance is acceptable.
