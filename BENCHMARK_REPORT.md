| Map pooling — repeatedly clear and refill | `std`, `ahash`, `hashbrown` (capacity retention); `rustc-hash` out-of-the-box |
| get-or-insert / memoization | `rustc-hash`; `std`/`hashbrown` with a shared hasher |
| Clone/snapshot-heavy workloads | `rpds-hash-trie-map` (single-threaded), then `imbl`/`immutable-chunkmap` |
| Concurrent read-only | `papaya` (both key types) |
| Concurrent read-mostly, u64 keys | `leapfrog` (fastest) with `papaya`/`txmap` as safer alternatives |
| Concurrent mixed / write-heavy | `txmap`; `scc` at 3 threads and for String keys |
| Concurrent single-hot-key synchronization, u64 | `leapfrog` |
| Concurrent single-hot-key synchronization, String | `dashmap` (2 threads), `scc` (3 threads) |

### 3.3 Trade-offs — different implementations excel at different operations

- **Persistent maps trade mutation cost for near-free copies.** `rpds-hash-trie-map` clones a 1K/10K/100K
  map in ~1.1 ns (structural sharing) versus ~143 µs for `std` and ~8 ms for `papaya` at 100K. The same
  property makes them unattractive for heavy insert/growth paths, where they do not appear near the top.
- **`indexmap` is the iteration specialist.** It wins all six iterate configurations by a wide margin
  (2.80 µs vs the field at 10K) but pays for it with an additional index structure and uses `swap_remove`,
  so removal does not preserve insertion order.
- **`intmap` is the integer specialist.** It wins u64 `lookup-hit`, `lookup-miss` and `remove`, but cannot
  accept String keys at all.
- **`leapfrog` is the concurrent-u64 specialist.** It wins 18 configurations, all u64 concurrent ones, but
  requires `Copy` keys, a `leapfrog::Value` value type, cannot be cloned or cleared, and is compiled with
  the `stable_alloc` feature (preallocated memory). Its lead disappears on String keys.
- **`txmap` is the concurrent generalist.** It wins 17 configurations across contention, throughput and
  synchronization, for both key types, at the cost of never being dramatically ahead.
- **No single map dominates.** The single-threaded winners (`rustc-hash`, `intmap`, `indexmap`, `rpds`) and
  the concurrent winners (`txmap`, `leapfrog`, `scc`, `dashmap`, `papaya`) are essentially disjoint sets.
- **`create` is dominated by allocation strategy.** `immutable-chunkmap` (no allocation until first insert)
  and `rustc-hash` construct 10K maps in ~2.9 µs, while `concurrent-map` needs ~8.9 ms (≈3,100×) because it
  sets up per-map epoch-reclamation state.

### 3.4 Implementations that are consistently close to the fastest

`hashbrown` (26/64 configurations within 10%), `ahash` (27/64) and `std` (20/64) form a dependable second
tier: they rarely win outright but are almost always within 10% of the winner when a shared hasher is used.
For u64 single-threaded work these three are nearly interchangeable. `rustc-hash` has the highest hit rate
(28/37 configurations within 10%) but only participates in non-concurrent configurations.

### 4.3 The clone measurement floor

`rpds-hash-trie-map` reports a median of **1.1 ns with MAD = 0 and SD = 0** for cloning 1K/10K/100K-entry

for persistent data structures (clone is a reference-count increment plus structural sharing), but the
1.1 ns figure is at Criterion's resolution floor and has literally zero observed variance, so it should be
read as "effectively free / O(1)" rather than as a precise 1.1 ns.

## 5. Implementation Limitations

The notes below come from the wrapper code in `src/maps/`. All wrappers require `V: Clone` in practice
because the harness clones values out on reads, and the hash-map-like wrappers require `K: Hash + Eq`.

- **`ahash`** — `K: Hash + Eq`. No shared-reference mutation (`&mut` only). Custom hasher supported.
  Implements `get_or_insert` only through `&mut`. No `BenchMapGetOrInsert` (shared) implementation.
- **`btreemap`** — requires `K: Ord` instead of `Hash`; no custom-hasher support. No shared-reference
  mutation. Only ordered map in the set, but never competitive here.
- **`concurrent-map`** — requires `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send
  + Sync`. The underlying `ConcurrentMap` is `Send` but **not `Sync`** (EBR state is in a `RefCell`), so
  the wrapper keeps a `Mutex`-protected master and lazily clones it into a thread-local for each worker.
  This is an ergonomically unusual, per-thread-clone usage pattern; the clone itself shares the tree. No
  custom hasher and no `clear` (hence absent from clear-and-reuse). Very expensive to construct.
- **`crossbeam-skiplist`** — requires `K: Ord + Send + 'static`, `V: Send + 'static`. No `Clone`
  implementation (so absent from the clone benchmarks) and no custom-hasher support. Shared-reference
  mutation works. No `BenchMapGetOrInsert`-style entry API beyond `get_or_insert`.
- **`dashmap`** — `K: Hash + Eq`, custom hasher supported. Shared-reference mutation works. `clone_map`
  deep-copies all entries, which is why it is far behind the persistent maps in the clone benchmarks.
- **`hashbrown`** — `K: Hash + Eq`, custom hasher supported. No shared-reference mutation.
- **`hashlink`** — `K: Hash + Eq`, custom hasher supported, insertion-ordered. No shared-reference
  mutation; `insert` needs `&mut`. Its same-hasher insert of String keys was noticeably noisy.
- **`horde`** — `K: Hash + Eq` (plus `Clone` for insert), custom hasher supported. Reads and iteration
  require pinning via `horde::collect::pin`. **Writes require `&mut self`**, so it cannot mutate through a
  shared reference and is excluded from concurrent-mutation benchmarks. `clear` is emulated by replacing
  all entries with an empty iterator.
- **`imbl`** — persistent HAMT; custom hasher supported. Mutation takes `&mut self`; `insert`/`remove`/
  `get_or_insert` additionally require `K: Clone`. Clone is O(1) structural sharing. No clear caveats.
- **`immutable-chunkmap`** — requires `K: Clone + Ord`; **no custom hasher, no `clear`, no shared
  mutation.** Mutation is copy-on-write (`insert_cow`, `remove_cow`, `get_or_insert_cow`). Cheapest empty
  constructor, but not competitive on write paths.
- **`indexmap`** — `K: Hash + Eq`, custom hasher supported. No shared-reference mutation. Removal is
  implemented with `swap_remove`, so it does **not** preserve insertion order on removal. Iteration is its
  standout strength.
- **`intmap`** — requires `K: IntKey` (integer keys only); no custom hasher and no String support. Lookups
  dereference the key by value (`get(*key)`). No shared-reference mutation.
- **`leapfrog`** — requires `K: Eq + Hash + Copy` (no String) and `V: leapfrog::Value`; hasher must be
  `BuildHasher + Default`. Uses the `stable_alloc` feature (preallocated memory). Shared-reference mutation
  works, but the map is **not `Clone`** and has **no `clear`** (absent from clone and clear-and-reuse).
- **`papaya`** — `K: Hash + Eq`, custom hasher supported. Shared-reference mutation requires acquiring a
  `pin()` guard on every operation (done inside the wrapper). Clone is a deep copy.
- **`rpds-hash-trie-map`** — persistent HAMT using `archery::RcK`, i.e. **`Rc`, so not thread-safe**.
  Custom hasher supported. Mutation takes `&mut self`. **No `clear`**. `remove_mut` returns `()`, so the
  wrapper does `get` then `remove_mut` to return the removed value (an extra lookup per removal). Clone is
  O(1) and by far the fastest measured.
- **`rustc-hash`** — `FxHashMap`; the hasher is fixed (`FxBuildHasher`), so **no custom-hasher support**.
  No shared-reference mutation. Extremely strong single-threaded, but not usable where DoS-resistant or
  custom hashing is required.
- **`scc`** — `K: Hash + Eq`, custom hasher supported. All operations use the `_sync` APIs; no `pin` guard.
  Shared-reference mutation works. Cannot express `get_or_insert` without an entry lock; `clone_map`
  deep-copies.
- **`starshard`** — requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`. Fixed 8
  shards, custom hasher supported. `get_or_insert` is `compute_if_absent` (no entry API). Entered every
  configuration but never within 10% of the winner.
- **`std`** — `K: Hash + Eq`, custom hasher supported. No shared-reference mutation. SwissTable; the
  benchmark default baseline.
- **`txmap`** — `K: Hash + Eq` (and `K: Clone` for `get_or_insert`), custom hasher supported, built with
  `MutexPolicy`. Shared-reference mutation works. Broadest applicability of the concurrent maps.

## 6. Recommendations

### 6.1 Further investigation

- **Re-run the 1M growth benchmarks.** MAD is 4–8% for the leading maps and `hashbrown` is within ~8.5% of
  `rustc-hash`/`ahash`, so the ordering at 1M is not yet settled. A dedicated, longer measurement (or
  multiple runs) would firm up conclusions for large-map growth.
- **Investigate the concurrent synchronization outliers.** `dashmap`'s write-mostly 2-thread String win has
  8.2% MAD and `scc`'s 3-thread String write-heavy win has 4.3% MAD; `crossbeam-skiplist` and
  `concurrent-map` read-only runs are also >8% MAD. Re-run the synchronization family with more samples to
  confirm the 2-thread vs 3-thread crossover between `dashmap` and `scc`.
- **Confirm the `leapfrog` lead under realistic usage.** Its wins are large and consistent on u64, but it
  imposes `Copy` keys, a fixed value trait, no clone/clear, and `stable_alloc`. A memory-footprint and
  long-running-stability check is warranted before recommending it broadly.
- **Investigate `concurrent-map` and `indexmap` construction variance** (31% and 13% MAD respectively) — the
  `create` and 1K clone-then-write numbers are the least trustworthy in the suite.
- **`starshard` and `crossbeam-skiplist` deserve a focused look** — they enter 112 and 79 configurations
  respectively and never place within 10%, which suggests either a mis-tuned configuration (e.g. 8 shards,
  or the skiplist wrapper's extra `Ord`/`Send` bounds) or genuine unsuitability for these workloads.

### 6.2 Measurement-quality issues that could affect conclusions

- **No baseline data.** Only absolute `new` estimates exist, so nothing here can be attributed to a code
  change or regression; all conclusions are relative, within-run comparisons.
- **The `clone` benchmark saturates for persistent maps.** `rpds-hash-trie-map` measures 1.1 ns with zero
  variance at every map size; `imbl` and `immutable-chunkmap` are also size-independent. These are real O(1)
  clones, but the exact value is at the measurement floor and should not be quoted as a precise latency.
- **`create` is dominated by allocation policy.** `immutable-chunkmap`'s 2.86 µs for 10K maps is ~0.3 ns per
  map, i.e. effectively a no-op constructor; the benchmark measures "does this map allocate on `new`", not
  general performance. It should be read together with the growth benchmarks.
- **Concurrent benchmarks remain wall-clock noisy** even with thread pinning; treat sub-10% margins there
  as ties rather than orderings.
- **`out-of-the-box` and `same-hasher` results are not interchangeable.** `rustc-hash`'s out-of-the-box wins
  partly reflect the Fx hasher rather than the map; under a shared hasher the leaders shift to
  `std`/`ahash`/`hashbrown`. Recommendations should always state which comparison they are based on.

### 6.3 Bottom line

- For **single-threaded** work, default to `rustc-hash` for raw speed, or `std`/`ahash`/`hashbrown` when a
  custom or DoS-resistant hasher is needed; use `intmap` for integer keys and `indexmap` for iteration.
- For **concurrent** work, `txmap` is the broadest safe choice; `leapfrog` is the u64 speed choice with
  API caveats; `papaya` is best for read-only and `scc`/`dashmap` for String hot-key workloads.
- For **snapshot/clone-heavy** work, `rpds-hash-trie-map` (single-thread) and `imbl`/`immutable-chunkmap`
  offer O(1) clones unmatched by the deep-copying maps.
- `btreemap`, `crossbeam-skiplist`, `concurrent-map`, `imbl` and `starshard` were never within 10% of the
  fastest in any measured operation and should not be selected for these workloads without further
  evidence.
