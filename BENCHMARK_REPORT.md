### 3.3 Trade-offs (different implementations excel at different things)

- **Serial vs concurrent:** rustc-hash (and std/hashbrown/ahash) are faster than every concurrent map in single-threaded benchmarks, but the gap is highly implementation-specific: txmap/dashmap/horde/starshard are only ~2× behind, while papaya (~6×) and crossbeam-skiplist (~16×) are far more expensive. Conversely, rustc-hash/std/etc. cannot be used concurrently at all.
- **txmap vs leapfrog:** txmap wins 2–3-thread workloads and read-heavy; leapfrog wins 4-thread and write-heavy/100K cells. Neither dominates.
- **indexmap's iteration speed** comes at the cost of a slower insert path; it is a poor choice for insert-heavy workloads (out-of-the-box insert at 100K: indexmap 4.13 ms vs rustc-hash 1.97 ms, ~2.1×).
- **Persistent maps** (rpds, imbl, immutable-chunkmap) win clone/create but are far behind on mutation-heavy workloads (e.g. rpds insert 100K ~13.2 ms vs rustc-hash 1.97 ms, ~6.7×).
- **horde** shows a genuinely interesting trade-off: a concurrent map that is also competitive or best on serial remove (same-hasher) and within 10% on same-hasher insert.
- **rustc-hash's dominance is hasher-driven**: with its FxHasher it wins all out-of-the-box serial benchmarks; under the shared ahash hasher it is not even benchmarked (no custom-hasher support) and std/hashbrown/ahash tie.

### 3.4 Consistently close to the fastest

Threads-2 and threads-3 cells are much cleaner (rel MAD mostly < 1–3%), so the noise is scheduling/contention-related rather than a property of a single implementation.

### 4.2 Fast implementations with unusually noisy measurements

- **leapfrog** — the fastest (or top-2) in many 4-thread cells, but its threads-4 measurements have rel MAD up to 77% and rel std up to 190%. Its top rankings at 4 threads rest on noisy data; only the 100K write-heavy threads-2/3 cells (rel MAD ~1%) are statistically firm.
- **txmap** — the dominant concurrent winner, but its threads-4 cells are noisy too (rel MAD up to 41.7%, rel std up to 61.3%). Its 2–3-thread wins are clean (rel MAD < 1.5%).
- **scc** — fastest in the 100K threads-4 get-or-insert cell, but rel std 59.2% there; that win should be treated as provisional.
- **papaya** — fastest in the read-heavy 100K threads-4 cell with rel std 86.8%; provisional.
- **rpds-hash-trie-map** — high rel MAD (43–51%) on 100K serial workloads, driven by GC/refcount effects in the Rc-based persistent structure.
- The serial champions (rustc-hash, std, ahash, hashbrown, indexmap) are all very stable (rel MAD < 3.5% in every cell they win).

## 5. Implementation Limitations (from `src/maps/` wrappers)

Per implementation, based on the wrapper code in `src/maps/`:

- **ahash** (`ahash_benchmap.rs`, `ahash::AHashMap`)
  - Requires `K: Hash + Eq` for all ops; `V: Clone` for lookup/get-or-insert.
  - Supports a custom hasher (`BenchMapNewWithHasher`).
  - Serial only: no shared-reference mutation API, so excluded from concurrent benchmarks.
- **btreemap** (`btreemap_benchmap.rs`, `std::collections::BTreeMap`)
  - Requires `K: Ord`; `V: Clone` for lookups.
  - **No custom-hasher support** — absent from all same-hasher benchmarks.
  - Serial only; no entry API on shared reference.
- **concurrent-map** (`concurrent_map_benchmap.rs`, `concurrent_map::ConcurrentMap`)
  - Requires `K: 'static + Clone + Minimum + Send + Sync`, `V: 'static + Clone + Send + Sync`.
  - **`Send` but not `Sync`** — cannot share `&ConcurrentMap` across threads; excluded from all concurrent (threads ≥ 2) benchmarks.
  - No custom hasher; no entry API — get-or-insert is emulated as get-then-insert, which is **not atomic**.
  - Not benchmarked in several other ops; excluded from clear-and-reuse (no `clear`) and key-sensitivity.
- **crossbeam-skiplist** (`crossbeam_skiplist_benchmap.rs`, `crossbeam_skiplist::SkipMap`)
  - Requires `K: Ord` (plus `Send + 'static` for mutation); `V: Clone` for lookup/remove.
  - No custom hasher; **no `Clone`** — excluded from the clone benchmark.
  - Lock-free skiplist; participates in all concurrent benchmarks (but never fastest).
- **dashmap** (`dashmap_benchmap.rs`, `dashmap::DashMap`)
  - Requires `K: Hash + Eq`; `H: BuildHasher + Clone`; `V: Clone` for lookup/get-or-insert.
  - Custom hasher supported; concurrent (sharded); has a proper entry API for get-or-insert.
- **flurry** (`flurry_benchmap.rs`, `flurry::HashMap`) — **not benchmarked** ("too slow" — creates a `seize::Collector` per map).
  - Requires `K: Hash + Ord` for mutation paths (and `Send + Sync` for shared ops).
  - Supports a custom hasher; concurrent (epoch/pin based).
- **hashbrown** (`hashbrown_benchmap.rs`, `hashbrown::HashMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookups.
  - Custom hasher supported. Serial only.
- **hashlink** (`hashlink_benchmap.rs`, `hashlink::LinkedHashMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookups. Default hasher `hashlink::DefaultHashBuilder`.
  - Custom hasher supported. Serial only; maintains insertion order (extra bookkeeping).
- **horde** (`horde_benchmap.rs`, `horde::SyncTable`)
  - Requires `K: Hash + Eq` (`Clone` for insert/get-or-insert); `V: Clone`.
  - Custom hasher supported; concurrent, but mutations go through a **`write()` handle** — no entry API, so get-or-insert is emulated as read-then-write (not atomic).
  - The wrapper's get-or-insert does two lookups on the miss path (one read, one write).
- **imbl** (`imbl_benchmap.rs`, `imbl::GenericHashMap` — persistent/COW)
  - Requires `K: Hash + Eq + Clone`, `V: Clone` for mutation; `H: BuildHasher + Clone`.
  - Custom hasher supported; mutation requires `&mut` (COW), so **not usable in shared-reference concurrent benchmarks**.
- **immutable-chunkmap** (`immutable_chunkmap_benchmap.rs`, `immutable_chunkmap::map::MapM`)
  - Requires `K: Clone + Ord`, `V: Clone` (ordered persistent chunked map).
  - **No custom hasher**; no `clear` — excluded from clear-and-reuse.
  - Mutation is via COW methods (`insert_cow`, `remove_cow`) requiring `&mut`; excluded from concurrent benchmarks.
- **indexmap** (`indexmap_benchmap.rs`, `indexmap::IndexMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookups.
  - Custom hasher supported; serial only; preserves insertion order (fast iteration, contiguous storage).
  - `remove` uses `swap_remove` (order-destroying) in the wrapper.
- **leapfrog** (`leapfrog_benchmap.rs`, `leapfrog::LeapMap`)
  - Requires **`K: Eq + Hash + Copy`** and `V: leapfrog::Value` — **String keys are unsupported** (absent from String key-sensitivity).
  - No custom hasher (default `BuildHasherDefault<DefaultHasher>`); **no `Clone`** and **no `clear`** — excluded from clone and clear-and-reuse.
  - Concurrent; get-or-insert is implemented via `try_insert`, which is correct but not an `entry`-style API.
- **papaya** (`papaya_benchmap.rs`, `papaya::HashMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookup/remove.
  - Custom hasher supported; concurrent (epoch-based, pin-based API — every op acquires a `pin`).
- **rpds-hash-trie-map** (`rpds_benchmap.rs`, `rpds::HashTrieMap` with **`archery::RcK`** pointer)
  - Requires `K: Eq + Hash`, `V: Clone`, `H: BuildHasher + Clone`.
  - **`RcK` is not `Send`/`Sync`** — excluded from all concurrent benchmarks.
  - No entry API — get-or-insert emulated as get-then-insert (not atomic); no `clear` — excluded from clear-and-reuse.
  - `clone` is O(1) (refcount bump) — the clone "win" is structural sharing, not a deep copy.
- **rustc-hash** (`rustc_hash_benchmap.rs`, `rustc_hash::FxHashMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookups.
  - **No custom hasher** (fixed FxHasher) — absent from all same-hasher benchmarks. Serial only.
- **scc** (`scc_benchmap.rs`, `scc::HashMap`)
  - Requires `K: Hash + Eq`; `H: BuildHasher`.
  - Custom hasher supported; concurrent; has `entry_sync` for get-or-insert; sync variants of all ops.
- **starshard** (`starshard_benchmap.rs`, `starshard::ShardedHashMap`)
  - Requires `K: Clone + Hash + Eq + Send + Sync`, `V: Clone + Send + Sync`, `H: BuildHasher + Clone + Send + Sync` — **stricter bounds than most**.
  - Default hasher is `rustc_hash::FxBuildHasher`; fixed **8 shards** (not configurable via the wrapper).
- **std** (`std_benchmap.rs`, `std::collections::HashMap`)
  - Requires `K: Hash + Eq`; `V: Clone` for lookups.
  - Custom hasher supported (default `RandomState`/SipHash-13 — the reason it loses out-of-the-box). Serial only.
- **txmap** (`txmap_benchmap.rs`, `txmap::TxMap<K, V, MutexPolicy, H>`)
  - Requires `K: Clone + Hash + Eq`; `H: BuildHasher`.
  - Custom hasher supported; concurrent; built via `TxMapBuilder`.

**Benchmark-participation consequences:** same-hasher mode has 14 participants (no btreemap, concurrent-map, crossbeam-skiplist, immutable-chunkmap, leapfrog, rustc-hash); concurrent mode has 7 (crossbeam-skiplist, dashmap, leapfrog, papaya, scc, starshard, txmap); clone has 17; clear-and-reuse has 15; key-sensitivity has 14 (13 for String keys, no leapfrog); create has 19.

## 6. Recommendations

### 6.1 Implementations/benchmarks needing further investigation

1. **leapfrog vs txmap at 4 threads.** Both are top-2 in most concurrent cells, but their threads-4 measurements are the noisiest in the suite (rel std up to 190% for leapfrog, rel MAD up to 42% for txmap). Re-run the threads-4 workload/get-or-insert benchmarks with longer measurement time (currently 2 s) and more samples before trusting the ranking.
2. **horde.** A concurrent map that won all same-hasher remove benchmarks and came within 10% on same-hasher inserts is worth investigating further — it is under-represented in the current workload set (its wrapper lacks an atomic get-or-insert, which may hide its true write-path advantage).
3. **scc and papaya** single wins at 100K/threads-4 (rel std 59% and 87% respectively) need confirmation.
4. **rpds-hash-trie-map on large maps** — rel MAD 43–51% on 100K serial workloads; investigate whether the Rc pointer kind (vs `Arq`/`Arc`) causes allocation/refcount jitter under Criterion's per-iteration batches.
5. **rustc-hash vs same-hasher mode**: the entire out-of-the-box serial picture is driven by FxHasher. Users choosing `rustc-hash` should be aware the advantage is hashing cost, not table layout; a follow-up comparing FxHasher-based std/hashbrown vs rustc-hash would separate the two factors.

### 6.2 Measurement-quality issues affecting conclusions

- **Concurrent benchmarks are noisy**, especially threads-4: several top-cell rankings (leapfrog, txmap, scc, papaya at threads-4) sit on data with rel MAD 10–77% / rel std up to 190%. Only 2–3-thread concurrent results are firm.
- **Warm-up/measurement time is short** (1 s warm-up, 2 s measurement per benchmark, from `src/config.rs`). For sub-microsecond iterations (lookup/remove/key-sensitivity) this limits sample counts; for concurrent workloads it limits averaging over scheduling noise.
- **Iteration times vs per-op times**: lookup-hit/miss/remove/key-sensitivity report per-iteration times for batches of 100 ops (tens to hundreds of ns per iteration). The medians are precise (rel MAD < 3.5%) but the absolute scale is small; sub-ns-level differences between `std`/`ahash`/`hashbrown` (1–2% apart) should be treated as equivalent.
- **clone comparisons are apples-to-oranges**: persistent maps (rpds, imbl, immutable-chunkmap) clone in O(1) via structural sharing; the ~76 µs–8.3 ms figures for the other maps are deep copies. The 2 ns "win" for rpds should not be read as a general clone-performance statement.
- **create benchmarks empty maps only** — `Map::new()` for persistent structures is nearly free (immutable-chunkmap 3.12 µs per 10,000 creations ≈ 0.3 ns each); this measures allocation laziness, not practical map creation cost.
- **No baseline/change data exists**; all conclusions are from absolute medians of a single run per benchmark. Between-run variance (e.g. CPU frequency, turbo) is not quantified, so sub-10% differences should be treated as noise unless confirmed.
- Multi-threaded benchmarks pin workers to CPUs 0..N-1 and amortize thread spawn (good practice), but the main thread's signalling overhead and shared-L3 contention are still in the timed region.
