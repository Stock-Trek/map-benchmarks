# Executive Summary — Map Implementation Benchmark

**Prepared:** 2026-08-22 · **Source:** Criterion.rs medians from `target/criterion/` (1,469 measurements across 132 benchmark groups, 20 implementations) · Full analysis: [`BENCHMARK_REPORT.md`](BENCHMARK_REPORT.md)

## Headline: there is no single fastest map — the winner is workload-shaped

Across 132 benchmark groups the fastest implementation is a three-way tie — **rustc-hash** (serial, default hasher), **scc** (concurrent writes / String keys / hot-key contention) and **leapfrog** (concurrent u64 reads) each take 22 groups — but they win in **disjoint domains**:

- **Serial, general-purpose:** `rustc-hash` wins nearly every default-hasher group (growth, insert, throughput, lookups, get-or-insert, clear-and-reuse). When a shared/configurable hasher is required, `ahash`, `hashbrown` and `std` are within ~8% of each other in almost every serial group — the hasher, not the map, becomes the differentiator (confirmed by the key-sensitivity sweep).
- **Concurrent, u64 keys, read-heavy/balanced:** `leapfrog` is dominant (e.g. 68.9 µs for single-key read-only synchronization vs. 114 µs for `papaya` and 1.1–3.4 ms for the other locked/sharded maps; 268 µs vs. 0.6–4.3 ms for the field on uniform-contention u64). This is conditional on its `K: Copy` bound — it cannot be used with String keys at all.
- **Concurrent, write-heavy or String keys:** `scc` is the clear winner (every write-majority/write-only synchronization group, write-heavy throughput at 3 threads, uniform contention). `papaya` wins read-mostly/read-only concurrency and extreme Zipfian(2.0) skew; `txmap` wins default-hasher String throughput at 2 threads; `dashmap` wins common-hasher String at 2 threads but is noisy (see below).
- **Specialised niches:** `indexmap` dominates iteration (2.5× over the field) and String inserts/growth; `rpds-hash-trie-map` has O(1) clone (persistent structure, ~1 ns vs. ~150 µs deep copies); `intmap` is fastest for u64 lookups/removes; `immutable-chunkmap` is cheapest to create.

`ahash` is the most consistently-close implementation (within 10% of the winner in 30 of 132 groups), with `hashbrown` (24), `std` (21) and `scc` (28) close behind — for teams that must pick one map for mixed workloads, `ahash`/`hashbrown` (serial) and `scc` (concurrent) are the safest bets.

## Practical guidance

Choose by contract and workload, not by headline speed:

- **Serial + default hasher:** `rustc-hash`, accepting FxHash's lack of collision-hardening and non-configurable hasher.
- **Serial + shared hasher / DoS-sensitive:** `ahash`, `hashbrown` or `std` — statistically interchangeable here.
- **Concurrent u64 reads:** `leapfrog` (Copy keys); **concurrent writes/String:** `scc`; **read-mostly/read-only concurrency:** `papaya`; **ordered or range access:** `btreemap`; **cheap snapshots:** `rpds`/`imbl`/`immutable-chunkmap`; **u64 lookups:** `intmap`.

## Caveats worth acting on

1. **dashmap's wins are noisy** — one 2-thread String win had 18.1% MAD (median absolute deviation), the worst of any winning result; re-measure before relying on it.
2. **Coverage gaps:** `concread` and `flurry` were excluded ("too slow") and have no measurements; `horde` — surprisingly fast at serial writes via copy-on-write — is handicapped by a `&mut`-only wrapper and lacks `get_or_insert`, so it never ran in the concurrent benches; `leapfrog` was only tested with u64 keys.
3. **No baseline data exists** — these are single-run absolute numbers; sub-10% differences (especially sub-200 ns lookups) are within noise and should be treated as ties.
4. **Measurement hygiene:** overall winner-noise is healthy (median MAD 1.1%, p90 4.3%), but the 1 ns rpds clone is a measurement-floor artifact, and the concurrent suite only covers 2–3 pinned threads.

**Bottom line:** for serial use, pick `ahash`/`hashbrown`/`rustc-hash` and move on. For concurrent use, there is a real read-vs-write trade-off: `papaya`/`txmap`/`leapfrog` for reads, `scc` for writes and String keys. No single implementation is the fastest across the board, so the recommendation is to select by the dominant access pattern and re-validate dashmap's noisy results before finalising any decision.
