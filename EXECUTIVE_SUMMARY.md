# Executive Summary — Rust Map Benchmarks

This summary condenses `BENCHMARK_REPORT.md`, which analyses 112 Criterion benchmark groups covering 19 map implementations. Every figure below is a Criterion median from that single data set; the full report contains the per-variant tables, ratios and stability statistics.

## Headline

There is no single best map. The results split cleanly into a **serial** contest and a **concurrent** contest, and the winners are different populations.

- **Serial (64 groups):** `rustc-hash` is fastest most often (22 wins), `indexmap` dominates iteration and large-String growth (11 wins), and the SwissTable family (`std`, `hashbrown`, `ahash`) is the reliable generalist. `std`/`hashbrown`/`ahash` are effectively interchangeable once the hasher is held constant: u64 lookups differ by 0.1% (hashbrown 226.8 ns vs std 227.1 ns per 100 lookups), and String inserts by ~1%.
- **Concurrent (48 groups):** `txmap` is the broad winner — fastest in 37 of 48 groups, within 10% in 44 of 48, and 1.02–1.83× ahead when it wins. `leapfrog` is the only sustained challenger, taking 8 concurrent groups — 4 of 6 `u64` contention variants, 2 of 6 `u64` throughput variants and 2 synchronization variants — with up to 2.26× over `txmap`. `papaya` wins read-only String synchronization by 1.10×, `scc` wins 3-thread String write-heavy throughput by 1.04×, and `dashmap` edges one String Zipfian contention case by 1.01×.

## What drives the rankings

**Hasher choice is a first-order effect.** `std` moves from 1.40 µs to 227 ns per 100 `u64` lookups when SipHash is replaced by ahash — 6.2×. Out-of-the-box tables compare map+hasher combinations; the same-hasher tables (all maps using `ahash::RandomState`) are the correct lens for data-structure decisions.

**Dense layout wins iteration, loses point access.** `indexmap` iterates 100K entries in 27.85 µs (0.28 ns/entry), 2.59× ahead of the runner-up; ordered/skiplist designs trail badly (`crossbeam-skiplist` 77.9×). The same layout costs it ~30% on String point lookups versus `std`.

**Structural sharing moves cost from clone to write.** `rpds` clones 100K entries in 1.4 ns, roughly 34,000× faster than `std`'s 47.44 µs deep copy. But the first 10K writes to that clone cost 3.62 ms, 30.9× `rustc-hash`; `imbl` and `immutable-chunkmap` show the same 17–33× penalty. Persistent maps only pay off when clones are read-mostly.

**Specialists beat generalists inside their niche, and lose outside it.** `intmap` is 1.19× ahead on `u64` lookups but 4.24× behind on `u64` inserts. `horde` is 1.69× ahead on String removal but has no get-or-insert API. `indexmap` wins 6/6 iteration groups and 5 growth groups and no lookup, insert or remove group. None is a general-purpose substitute.

**Concurrency machinery taxes serial throughput.** `leapfrog` needs 208.86 µs for 10K serial `u64` read-heavy operations (7.86× `rustc-hash`), yet wins 8 concurrent groups. Conversely, the serial champions (`rustc-hash`, `intmap`, `horde`, `indexmap`) expose only `&mut` mutation and therefore cannot enter any concurrent group — a coverage effect, not a performance verdict.

## Confidence and caveats

- **Single run, no baseline.** These are one Criterion run with no before/after comparison. Differences below 10% are treated as ties throughout; 42 of 112 groups have the runner-up within 10% of the winner, and 18 are within 2%. Re-run before making a close call.
- **Growth and clone are the noisy corners.** The noisiest group (`growth`, 1M `u64`) has a median relative MAD of 5.25%, and individual `growth` entries reach 15.31%; the top ranks there are not resolved. `rpds` clone entries sit at Criterion's 1.4 ns sampling floor with 9–10% MAD — read them as "constant time, sub-5 ns", not as a ranking.
- **`create` has an optimizer artifact.** `immutable-chunkmap`'s 2.73 µs per 10K maps (0.27 ns/map) is below one cycle per map and is best treated as work the optimizer removed, not as a 2× win.
- **Coverage is uneven.** 19 maps were measured; `concread`, `concurrent-map` and `flurry` produced no usable data (all three are marked too slow, and each also has an API or runtime constraint). Only 7 maps support shared-reference writes, and `leapfrog` is `u64`-only, so concurrent groups contain 6–7 implementations.
- **Not measured:** memory footprint, p99/tail latency, 8–16 thread scaling, per-map tuning (shard counts, `txmap` policy, hasher seeds). A map that wins the median can still lose on memory or tail latency.

**Bottom line:** use the SwissTable family for general serial work and pick the hasher deliberately; use `rustc-hash` for mixed serial workloads that can use FxHash; use `indexmap` for iteration, `horde` for removal and `rpds` for read-mostly snapshots. For concurrent code, start with `txmap` and treat `leapfrog` (`u64`), `papaya` (read-only) and `scc` (String write-heavy) as targeted alternatives. Ordered and persistent maps should be chosen for their semantics, not for speed on these workloads.
