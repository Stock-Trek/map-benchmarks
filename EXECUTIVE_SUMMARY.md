# Executive Summary: Map Implementation Benchmarks

**Bottom line:** No single map implementation is fastest for every workload. The right choice depends on three things: key type, whether the map is used from one thread or many, and whether cheap cloning or fast iteration matters. For ordinary single-threaded hash-map work, `rustc-hash` is usually the fastest out of the box, but `ahash`, `hashbrown`, and `std` are close when hashing is held constant and are safer choices when randomised hashing is required. For specialised workloads, the winners are clearly different: `indexmap` for iteration, `rpds-hash-trie-map` for read-only snapshots, `intmap` for integer keys, and `leapfrog` for concurrent `u64` workloads.

## What we measured

The Criterion report contains **19 map implementations**, **112 benchmark scenarios**, and **1,323 measurements** across 15 workload families. It covers single-threaded and concurrent reads, writes, removals, iteration, cloning, growth, construction, hot-key contention, and mixed real-world-style workloads.

Two comparison modes are used:

- **Out of the box:** each map uses its own default hasher. This reflects what a team gets by adopting the map with minimal tuning.
- **Same hasher:** every map that supports it uses the same hashing algorithm. This isolates the map data structure from the hasher.

All timing figures below are Criterion median estimates from the current benchmark machine. They are not production load tests.

## Key findings

### 1. `rustc-hash` is the most frequent single-threaded winner, but its advantage is partly the hasher

`rustc-hash` was fastest in **25 of the 37 serial comparisons where it was eligible**. Examples:

- 10,000 `u64` inserts: **127.8 µs**
- 10,000 mixed `u64` read-heavy operations: **21.0 µs**

However, once every map uses the same hasher, `ahash`, `hashbrown`, and `std` win or tie many of the same rows. `rustc-hash` uses the Fx hasher, which is fast but not randomised and not resistant to hash-flooding denial-of-service attacks. If randomised hashing is a requirement, `ahash`, `hashbrown`, or `std` are the better default.

### 2. `indexmap` is the clear choice for full scans

`indexmap` won **all six iteration benchmarks**, with no other implementation within 10%:

- 10,000 entries: **2.599 µs**
- 100,000 entries: **50.177 µs**

That advantage comes from its dense, order-preserving storage. It does not translate into the fastest point lookups or updates, so it should be selected specifically for iteration-heavy workloads.

### 3. Cheap cloning is a specialist trade-off

`rpds-hash-trie-map` cloned maps of 1K, 10K, and 100K entries in about **1.04 ns** each, because its persistent structure shares data instead of copying it. `imbl` and `immutable-chunkmap` were also cheap at roughly **11–13 ns**.

The trade-off appears as soon as the clone is modified. After cloning a 100K-entry map and inserting 10% new entries:

- `rpds-hash-trie-map`: **4.183 ms**
- `rustc-hash`: **0.233 ms**

So persistent maps are excellent for read-only snapshots, but not for clone-then-write workflows. `rpds-hash-trie-map` is also not thread-safe in this wrapper.

### 4. `intmap` dominates integer-key point operations

For 100-operation batches on integer keys:

- Lookup hit: **0.117 µs**
- Lookup miss: **0.085 µs**
- Remove: **0.340 µs**

It is the clear winner for integer-keyed workloads, but it cannot accept String keys or a custom hasher. It is not a general-purpose replacement for the other maps.

### 5. `leapfrog` dominates concurrent `u64` workloads

`leapfrog` was fastest in **19 of 24 concurrent `u64` scenarios** and within 10% in **21 of 24**. For example, 2-thread Uniform contention took **0.386 ms**.

Its constraints are significant: keys must be `Copy`, and the wrapper has no clone or clear. It is the right choice for concurrent integer-key work, not for String keys or general-purpose persistence.

### 6. Concurrent String workloads have no single winner

The String results split by access pattern:

- `txmap` is the most consistent all-rounder: **13 wins** and **21 of 48** results within 10%.
- `scc` wins String balanced and both write-heavy throughput rows; 3-thread String write-heavy took **2.034 ms**.
- `papaya` wins read-heavy and read-only workloads; 3-thread String read-heavy took **1.028 ms**.
- `dashmap` wins high-skew, 3-thread write-mostly/write-only scenarios.
- `txmap` won 3-thread String Uniform contention at **1.262 ms**.

The correct choice depends on the read/write mix and how skewed the key distribution is. A single "fastest concurrent map" does not exist in this data.

### 7. Construction cost varies enormously

For 10,000 empty-map constructions:

- `immutable-chunkmap`: **2.624 µs**
- `papaya`: **5.328 ms**
- `starshard`: **2.478 ms**
- `txmap`: **2.324 ms**

If an application creates many maps, construction can matter as much as steady-state operation speed. Sharded concurrent maps pay substantial setup cost and only make sense when that cost is amortised over concurrent work.

## Risks and caveats

- **Differences under 10% should be treated as ties.** The benchmark ranks medians; it does not prove that two implementations are meaningfully different in production.
- **Concurrent write-heavy results are noisy.** Relative run-to-run variation reached about 9.5–14% for several write-only results, including two fastest rows, and over 20% for one non-winning implementation. Do not pick a map from a narrow win in those rows without a workload-specific test.
- **Coverage is uneven.** Only 19 of the 22 wrappers have benchmark results. `concread`, `concurrent-map`, and `flurry` are excluded because they were too slow or needed wrapper workarounds that distorted the measurement.
- **`get-or-insert` is a 90/10 hit/miss workload.** The mix follows `GET_OR_INSERT_HIT_RATIO` = 0.90 in `src/config.rs`; a production hit ratio closer to 50% would need its own measurement.
- **Values are cloned on lookup.** The benchmark uses small `u64` values, so expensive value types may change the ranking.
- **Some derived per-element costs are below timer resolution.** The persistent maps clone in roughly 1–13 ns, and the fastest `create` batch implies about 0.26 ns per empty map. Treat these as effectively O(1) or very cheap, not as precise rankings.
- **These are current-machine numbers, not production guarantees.** Key size, value size, concurrency level, and workload mix should be validated on the target system.

## Recommendation

Adopt **workload-specific defaults** rather than standardising on one map:

1. Use `rustc-hash` for latency-sensitive single-threaded hash-map work where Fx hashing is acceptable.
2. Use `ahash`, `hashbrown`, or `std` when randomised hashing is required.
3. Use `indexmap` for scans, `rpds-hash-trie-map` for read-only snapshots, and `intmap` for integer keys.
4. Use `leapfrog` for concurrent integer workloads; use `txmap`, `scc`, `papaya`, or `dashmap` for concurrent String workloads according to the read/write mix and skew.
5. Run a short pilot on production-like data before locking in any choice, especially for concurrent write-heavy and clone-then-write workloads.
